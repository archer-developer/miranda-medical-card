## Проблема

Сейчас есть проблема с обработкой данных профиля на стороне Миранда. Например: я прошу Миранду показать мне данные профиля
и она показывает только часть или не правильно группирует данные, когда я прошу ее создать PDF на базе данных профиля.

## Идея:

Сделать ответ MCP профиля структурированным JSON который будет удобнее для анализа со стороны Миранды.

## Что было сделано

Структурированный, типизированный `ProfileOutput` в `medical.profile` уже существовал (`internal/mcpserver/profile.go`,
сериализуется MCP SDK в `structuredContent`) — проблема была не в отсутствии структуры, а в том, что параллельно с ней
в `content` (текстовый блок, который многие MCP-клиенты передают модели как есть) отправлялась вручную собранная
однострочная сводка только по 3 из 7 разделов профиля («N active diagnoses, N active medications, N allergies.»).
Если клиент (Миранда) читает `content`, а не `structuredContent`, до модели физически не доходили ни аллергии
(кроме счётчика), ни последние анализы, ни показатели жизнедеятельности, ни прививки, ни хронические заболевания —
это и объясняет «показывает только часть» и неверную группировку при генерации PDF (модели просто нечем было
группировать).

Исправлено:

1. `profileHandler` (`internal/mcpserver/profile.go`) больше не строит вручную усечённый текст — при `Content == nil`
   MCP SDK (`go-sdk/mcp`, см. `toolForErr`) сам сериализует уже провалидированный `structuredContent` в текстовый блок,
   так что `content` и `structuredContent` теперь физически один и тот же JSON и не могут разойтись.
2. Отдельно обнаружена связанная проблема неверной группировки: `LabResultSummaryOutput`/`VitalSignSummaryOutput` не
   содержали informацию о том, из какого документа взят показатель, хотя `profile.Builder` уже вычисляет это
   (`DocumentTitle`, добавлено ранее). Одноимённые показатели из разных типов документов (например «Белок» в анализе
   крови и в анализе мочи) были неотличимы. Добавлено поле `documentSource` в оба типа, см. `docs/mcp/05-profile.md` §9-10.

Тесты: `internal/mcpserver/profile_test.go` (`TestServer_Profile_ContentMirrorsStructuredContent`, сквозной через
реальный MCP-протокол) проверяет, что `content` и `structuredContent` идентичны и что `documentSource` заполняется.
