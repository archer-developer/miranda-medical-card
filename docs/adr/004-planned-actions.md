## Проблема

Документы часто содержат рекомендации на будущее: "Повторный анализ крови через полгода",
"сдать кровь на глюкозу", "нужно выполнить прививки А/Б/В в течение месяца". Сегодня это долетает
только до `extraction.ExtractionResult.Recommendations []string` — полностью неструктурированный
текст, который никогда не превращается в Domain Entity и нигде не появляется как список "что
предстоит сделать".

У медкарты нет и не будет собственного движка напоминаний — это зона ответственности Miranda
(календарь, push-уведомления и т.д., см. `../CLAUDE.md`'s разделение "Miranda — оркестратор,
Medical Service — медицинский эксперт"). Но чтобы Miranda могла расставить свои напоминания, ей
нужно откуда-то узнать, что вообще запланировано, с каким сроком и что из этого уже выполнено.
`Timeline` для этого не подходит — она строго ретроспективна (см. `../domain/04-timeline.md`),
концепции "будущее событие" в модели нет вообще.

## Идея

Новая Domain Entity `PlannedAction` — по образцу того, как `SelfReportedEvent`/`MedicationIntake`
(`../domain/12-self-reported-events.md`) уже параллельны document-derived фактам: у факта может
быть два независимых источника — документ (Structured Extraction) или прямая реплика
пользователя в диалоге с Miranda (`medical.log_event`).

### 1. Диапазон дат, а не точечная дата

Источник почти всегда даёт лишь грубый срок ("через полгода", "в течение месяца"), а не
абсолютную дату. Вместо того чтобы просить LLM самостоятельно посчитать календарную дату
(ненадёжно и недетерминированно — см. уже описанную в `../architecture/02-processing-pipeline.md`
§11 нестабильность Structured Extraction), LLM извлекает только относительную величину
(`dueAmountMin/Max` + `dueUnit`: day/week/month/year), а фактическая арифметика
(`documentDate`/момент диалога + offset → `dueDateFrom/dueDateTo`) выполняется детерминированно
в Go, в `internal/normalization`, тем же способом, каким там уже работает `parseOptionalDate`.
Рекомендация без указанного срока ("сдать кровь на глюкозу") — тоже валидный `PlannedAction`,
просто с `dueDateFrom/To == nil` — не имеет смысла требовать выдумывать дату там, где её нет.

### 2. Завершение определяется автоматически, а не вручную

Изначально предполагался write-tool "отметить пункт плана выполненным", но у медкарты уже есть
все данные, чтобы не спрашивать пользователя: если позже приходит документ, чьи нормализованные
данные (`LabResult`/`Procedure`) совпадают по типу и канонизированному имени/показателю
(переиспользуется уже существующая инфраструктура алиасов индикаторов, та же, что канонизирует
`LabResult.IndicatorName`) с ещё не выполненным пунктом плана, пункт автоматически помечается
`completed` с обратной ссылкой на документ/сущность, которая его закрыла. Отдельного write-tool'а
на "выполнено" в v1 нет.

Ограничение v1: сопоставление реально работает только со стороны Document Pipeline —
`medical.log_event`'s пайплайн сегодня не производит `LabResult`/`Procedure`, поэтому сказать
"я поставил прививку" в диалоге пункт плана автоматически не закроет — закрыть его может только
последующий документ (например скан сертификата).

### 3. Источник — документ или диалог, статус — pending/completed/declined

`PlannedAction.SourceType`/`SourceID` ("document"|"self_reported") — прямое переиспользование
уже существующего в этой кодовой базе паттерна `MedicationIntake.SourceType/SourceID`, а не новое
изобретение. Создание из диалога ("запиши в медкарту, что мне нужно сделать прививку от
бешенства в течение полугода") идёт через уже существующий `medical.log_event`, а не через новый
write-tool — по той же логике, что там уже есть прецедент "структурированная под-сущность,
извлекаемая независимо от `category`" (`medicationIntake`).

Отмена пункта плана по описанию ("отмени прививку от бешенства") — новый write-tool
`medical.decline_planned_action(userId, text)`, а не расширение `medical.ask`. `medical.ask`'s
Agent Loop сегодня принципиально read-only (вызывает только Knowledge Providers, возвращающие
данные, и никогда не мутирует состояние, см. `../architecture/03-knowledge-providers.md`) —
добавление туда мутирующего инструмента было бы самостоятельным архитектурным решением, которое
здесь сознательно не принимается. Вместо этого — отдельный tool в духе `medical.log_event`:
текст на входе, сервис сам через одну небольшую Structured LLM-call сопоставляет его с одним из
текущих `pending`-пунктов плана пользователя (список кандидатов уже короткий — pending-пункты
одного человека, — так что это прямой LLM-выбор из явного перечня, а не полноценный поиск).
`declined` — терминальный статус: не участвует ни в `Overdue`, ни в автозавершении, чтобы
отменённый пункт не "довыполнился" неожиданно более поздним документом.

### 4. Идемпотентность при reprocess

`PlannedAction` — первая сущность в этом сервисе, у которой состояние (`status`,
`matched_document_id`) осмысленно переживает переобработку *другого* документа, а не только
своего собственного — остальные сущности реплейсятся вслепую при reprocess именно потому, что у
них нет состояния, накапливаемого извне документа
(`../architecture/02-processing-pipeline.md` §6). Отсюда два места, где реализация не может
просто скопировать существующий паттерн `ReplaceForDocument`:

- reprocess документа-источника плана не должен убивать уже установленное `completed`-состояние
  слепым delete+reinsert — `ReplaceForSource` reconciles по ключу (тип + канонизированное имя),
  а не удаляет всё подряд;
- reprocess документа, который был источником завершения, должен снять это завершение
  (`ClearMatchesFromDocument`, выполняется безусловно в начале обработки любого документа) —
  иначе пункт плана может остаться навсегда "выполненным" тем, чего в текущих данных документа
  уже нет.
