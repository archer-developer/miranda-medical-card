# 1. Назначение

Medical Service предоставляет набор MCP Tools для работы с персональной медицинской историей пользователя.

Основной потребитель сервиса — Miranda.

MCP API проектируется вокруг пользовательских возможностей (Capabilities), а не вокруг внутренней модели данных или CRUD-операций.

Miranda использует сервис как специализированного медицинского эксперта, которому можно делегировать задачи анализа и работы с медицинскими данными.

---

# 2. Философия

Архитектура Medical Service строится вокруг простого принципа.

> **Miranda — оркестратор. Medical Service — медицинский эксперт.**

Miranda отвечает за:

- взаимодействие с пользователем;
- память;
- планирование диалога;
- координацию нескольких MCP-сервисов.

Medical Service отвечает за:

- хранение медицинской информации;
- анализ документов;
- медицинский поиск;
- понимание медицинских вопросов;
- построение медицинских выводов.

Miranda никогда не должна самостоятельно анализировать медицинские данные.

Все медицинские рассуждения выполняются внутри Medical Service.

---

# 3. Capability First

Каждый MCP Tool представляет собой законченную пользовательскую возможность.

Например:

```
medical.ask
```

означает:

> Ответь на медицинский вопрос пользователя.

А не:

```
findMedication()

↓

findTimeline()

↓

findDocuments()
```

Miranda никогда не должна самостоятельно строить подобные цепочки.

---

# 4. Минимальный внешний API

Внутри сервиса могут существовать десятки компонентов:

- Pipeline
- OCR
- LLM
- Knowledge Providers
- Timeline Engine
- Search Engine
- Embeddings
- FTS
- SQLite
- Domain Services

Однако наружу экспортируются только пользовательские возможности.

Внутреннее устройство сервиса не является частью MCP API.

---

# 5. Доверенная модель безопасности

Medical Service полностью доверяет Miranda.

При каждом вызове Miranda передает:

```
userId
```

Medical Service обязан только:

- проверить существование пользователя;
- загрузить его конфигурацию;
- выполнить запрос.

Авторизация, аутентификация и разграничение доступа являются ответственностью Miranda.

---

# 6. Пользователи

Список пользователей хранится в статическом YAML-файле.

Например:

```yaml
users:
  - id: alex
    name: Alexander
    locale: ru
    timezone: Europe/Amsterdam

  - id: anna
    name: Anna
```

Обязательным является только поле:

```
id
```

Дополнительные поля используются внутренней логикой сервиса.

---

# 7. Категории MCP Tools

Все инструменты делятся на пять логических групп.

## Files

Работа с бинарными файлами.

```
medical.download_file
```

Загрузка файла — не отдельный Tool этой группы, а побочный эффект `medical.upload_document(fileUri)` (см. §10, `03-documents.md` §4).

Получение оригинала доступно двумя способами (см. `02-files.md` §5): поле `fileUri` в ответе `medical.get_document` (группа Documents ниже), по которому Miranda выполняет обычный HTTP `GET` вне MCP — быстрый путь без повторной проверки доступа; либо `medical.download_file`, который заново проверяет владение/`shared_with` при каждом вызове.

---

## Documents

Работа с медицинскими документами.

```
medical.upload_document

medical.reprocess_document

medical.list_documents

medical.get_document
```

---

## Events

Медицинские факты, зафиксированные пользователем напрямую, без исходного документа — см. `07-events.md`. `medical.decline_planned_action`/`medical.complete_planned_action` (`08-planned-actions.md` §4-5) и `medical.resolve_diagnosis` (`09-diagnoses.md`) — тот же принцип "текст на входе, сервис сам разбирает" применённый к отмене/завершению пункта плана и к подтверждению разрешения диагноза, а не к их созданию.

```
medical.log_event

medical.delete_event

medical.decline_planned_action

medical.complete_planned_action

medical.resolve_diagnosis
```

---

## Medical Intelligence

Интеллектуальные возможности сервиса.

```
medical.ask
```

Именно этот инструмент является основной точкой входа для большинства пользовательских запросов.

---

## Medical Data

Получение структурированных медицинских данных.

```
medical.profile

medical.timeline

medical.planned_actions
```

Эти инструменты предназначены главным образом для построения пользовательского интерфейса и интеграции с другими сервисами Miranda. `medical.planned_actions` (`08-planned-actions.md`) — единственный из трёх, чья выдача перспективна, а не ретроспективна: список того, что ещё предстоит сделать, для расстановки Miranda собственных напоминаний.

---

# 8. Главный Tool

Центральным инструментом Medical Service является:

```
medical.ask
```

Он принимает вопрос пользователя на естественном языке.

Например:

> Какие лекарства я принимал прошлой зимой?

> Почему врач отменил статины?

> Когда впервые повысился ALT?

> Были ли у меня проблемы с печенью?

Внутри сервиса автоматически выполняется Agent Loop — единый диалог с LLM, который сам решает, какие Knowledge Providers (Search, Timeline и другие) вызвать и когда сформировать финальный ответ (см. `04-medical.md` §7).

Для Miranda это остается полностью прозрачным.

---

# 9. Структурированные данные

Не вся информация должна возвращаться в виде текста.

Некоторые сценарии требуют структурированных данных.

Например:

```
medical.profile
```

возвращает агрегированное текущее состояние пользователя.

```
medical.timeline
```

возвращает последовательность медицинских событий.

Эти инструменты не выполняют анализ.

Они лишь предоставляют данные в стабильной структуре.

---

# 10. Работа с файлами

Передача содержимого файла как аргумента MCP-вызова не используется — ни в одну, ни в другую сторону загрузки.

Вместо этого Miranda передаёт `fileUri` — адрес, по которому сервис сам скачивает файл:

```
medical.upload_document(fileUri)
```

Сервис выполняет HTTP GET по `fileUri`, сохраняет результат как `File` и сразу же импортирует его в медицинскую базу знаний — см. `02-files.md` §2 и `03-documents.md` §4 за обоснованием (кратко: base64 в аргументах MCP-вызова ненадёжен для файлов от нескольких сотен КБ).

При необходимости оригинальный файл можно получить двумя способами (см. `02-files.md` §5):

```
medical.get_document(documentId) → fileUri
                                       │
                                       ▼
                             GET fileUri (обычный curl, без повторной MCP-проверки доступа)
```

```
medical.download_file(fileId) → байты файла (с проверкой владения/shared_with на момент вызова)
```

# 11. Общие параметры

Практически все инструменты используют общий обязательный параметр.

## userId

Тип:

```
string
```

Идентификатор пользователя, от имени которого выполняется вызов (тот, о ком идёт речь в текущем диалоге с Miranda).

## subjectId (только у Tools для чтения)

Тип:

```
string, необязательный, по умолчанию равен userId
```

Идентификатор пользователя, чьи данные требуется получить, если он отличается от `userId`. Используется, когда один член семьи спрашивает о данных другого — например, родитель спрашивает про здоровье ребёнка.

Поддерживается только Tools для чтения агрегированных данных: `medical.ask`, `medical.profile`, `medical.timeline`, `medical.planned_actions`, `medical.list_documents`. Не поддерживается у `medical.upload_document`, `medical.reprocess_document`, `medical.log_event`, `medical.delete_event`, `medical.decline_planned_action`, `medical.complete_planned_action`, `medical.resolve_diagnosis` — совместный доступ никогда не даёт права изменять, удалять или добавлять чужие данные.

Если `subjectId` отличается от `userId`, сервис проверяет, что пользователь `subjectId` явно разрешил доступ (`shared_with` в своей конфигурации, см. `../architecture/01-overview.md` §4). Если доступ не разрешён, сервис отвечает так же, как если бы `subjectId` не существовал (`USER_NOT_FOUND`) — не раскрывая, что пользователь существует, но доступ запрещён.

Для Tools, работающих с конкретным ресурсом по идентификатору (`fileId`, `documentId` — `medical.download_file`, `medical.get_document`), отдельный параметр `subjectId` не нужен: сервис определяет владельца ресурса самостоятельно и разрешает доступ, если `userId` совпадает с владельцем либо владелец включил `userId` в свой `shared_with` (доступ только для чтения). При отказе в доступе Tool ведёт себя так же, как при отсутствии ресурса — см. `02-files.md` и `03-documents.md`.

Получение оригинального файла по `fileUri` (см. §10, `02-files.md` §5.1) — единственное исключение из этой схемы: эта проверка не проходит заново на каждый `GET`, а выполняется один раз, при вызове `medical.get_document`, который выдал URI; сам HTTP-эндпойнт `GET /files/{fileId}` полагается только на bearer-токен, общий с `/mcp`. `medical.download_file` (§5.2), в отличие от него, проверяет доступ на каждый вызов, как и все прочие Tools в этом разделе.

Все остальные параметры определяются конкретным Tool.

---

# 12. Ошибки

Все инструменты используют единый формат ошибок.

Например:

```json
{
    "code": "DOCUMENT_NOT_FOUND",
    "message": "Medical document not found."
}
```

Сообщения предназначены для разработчиков.

Формирование пользовательских сообщений выполняет Miranda.

---

# 13. Чего нет в MCP API

Следующие компоненты никогда не экспортируются наружу.

- SQL
- Repository
- Search Engine
- Embeddings
- OCR
- Prompt
- Agent Loop
- Knowledge Providers
- Pipeline
- Timeline Builder
- LLM

Все они являются деталями внутренней реализации.

---

# 14. Что не является MCP Tool

Административные операции не входят в MCP API.

Например:

- перестроение Embeddings;
- массовая переобработка документов (после смены модели/промпта);
- перестроение Timeline;
- переиндексация поиска;
- обслуживание базы данных.

Подобные операции выполняются через CLI самого сервиса и не предназначены для использования Miranda.

Точечная переобработка *одного* документа по инициативе пользователя ("переделай, результат выглядит неполным") — не административная операция, а обычный пользовательский сценарий, поэтому доступна через MCP как `medical.reprocess_document` (см. `03-documents.md` §6).

Это позволяет сохранить MCP API компактным и ориентированным исключительно на пользовательские сценарии.

---

# 15. Архитектурные принципы

Каждый новый MCP Tool должен соответствовать следующим требованиям.

- Представлять законченную пользовательскую возможность.
- Не раскрывать внутреннюю архитектуру сервиса.
- Не требовать знания медицинской модели данных.
- Использовать стабильную схему параметров.
- Использовать стабильную схему ответа.
- Быть понятным без знания внутреннего устройства сервиса.

Если предполагаемый Tool описывает внутреннюю реализацию, а не пользовательскую возможность, вероятнее всего ему не место в MCP API.

# 16. Состав MCP API

На текущий момент Medical Service предоставляет следующий набор инструментов.

| Tool | Назначение |
|------|------------|
| `medical.download_file` | Получение бинарного файла (с проверкой доступа на каждый вызов) |
| `medical.upload_document` | Скачивание файла по `fileUri` и импорт медицинского документа |
| `medical.reprocess_document` | Повторная обработка документа по запросу пользователя |
| `medical.list_documents` | Получение списка документов |
| `medical.get_document` | Получение информации о документе |
| `medical.log_event` | Фиксация самостоятельно сообщённого медицинского события |
| `medical.delete_event` | Удаление самостоятельно зафиксированного события |
| `medical.decline_planned_action` | Отмена пункта плана по тексту пользователя |
| `medical.complete_planned_action` | Отметка пункта плана выполненным по тексту пользователя |
| `medical.resolve_diagnosis` | Подтверждение разрешения диагноза по тексту пользователя |
| `medical.ask` | Ответ на медицинский вопрос |
| `medical.profile` | Получение агрегированной медицинской карточки |
| `medical.timeline` | Получение временной шкалы медицинских событий |
| `medical.planned_actions` | Получение списка предстоящих медицинских действий |

Все остальные возможности сервиса являются внутренними компонентами и недоступны через MCP.

Кроме MCP Tools, сервис отдаёт один HTTP-эндпойнт вне протокола MCP — `GET /files/{fileId}` (см. `02-files.md` §5.1), на том же сервере и с той же bearer-авторизацией, что и `/mcp`. Он не является MCP Tool и не перечислен в таблице выше; на него ссылается `fileUri` в ответе `medical.get_document`.
