# 1. Назначение

Events API отвечает за медицинские факты, которые пользователь сообщает напрямую через диалог с Miranda — без исходного документа. Например:

> Приступ головной боли, принял 400 мг ибупрофена.

> Давление поднялось выше обычного, принял 20 мг моксонидина.

В отличие от Documents API (`03-documents.md`), здесь нет файла, нет OCR, нет дедупликации. Есть только текст и момент времени.

---

# 2. Почему не через medical.upload_document

`upload_document` требует `fileUri`, по которому сервис сам скачивает файл (см. `02-files.md`), и запускает полный цикл обработки бинарного файла. Короткая фраза, произнесённая пользователем в диалоге, — не файл, и заворачивать её в файл только ради переиспользования Documents API усложнило бы обе стороны без пользы. См. `../domain/12-self-reported-events.md` §2.

# 3. Tool: medical.log_event

Фиксирует медицинское событие, о котором сообщил пользователь, и запускает его обработку.

Во время обработки сервис самостоятельно:

- классифицирует событие (симптом, наблюдение, приём лекарства, другое);
- при упоминании лекарства — извлекает и канонизирует действующее вещество и дозу;
- строит одно или несколько событий Timeline;
- индексирует событие для поиска (FTS и Embeddings).

Все эти этапы полностью скрыты от Miranda — Miranda передаёт текст ровно так, как его произнёс пользователь, и не пытается сама разбирать его на составляющие (см. `01-overview.md` §2 "Miranda никогда не должна самостоятельно анализировать медицинские данные").

---

## Параметры

| Поле | Тип | Обязательно | Описание |
|------|-----|-------------|----------|
| `userId` | string | ✅ | Идентификатор пользователя. |
| `text` | string | ✅ | Текст события на естественном языке, как его сообщил пользователь. |
| `occurredAt` | datetime | ❌ | Момент, когда событие произошло. По умолчанию — момент вызова (для ретроспективных записей, например "вчера болела голова", Miranda должна передать вычисленную дату явно). |

`log_event` не поддерживает `subjectId` — событие всегда фиксируется от имени `userId` и никогда не записывается в карту другого пользователя, даже расшарившего свои данные на чтение (см. `01-overview.md` §11: совместный доступ даёт только чтение).

---

## Ответ

```json
{
    "eventId": "selfevt_01J...",
    "status": "completed",
    "category": "symptom",
    "timelineEventIds": ["evt_01J...", "evt_01J..."],
    "medicationIntake": {
        "drugName": "Ibuprofen",
        "dose": "400 mg"
    }
}
```

`timelineEventIds` содержит одно или два значения — второе появляется, если в тексте распознан также факт приёма лекарства (см. `../domain/12-self-reported-events.md` §5). `medicationIntake` присутствует только в этом случае.

---

## Возможные ошибки

| Код | Описание |
|------|----------|
| `USER_NOT_FOUND` | Неизвестный пользователь |
| `INVALID_EVENT` | Пустой или бессмысленный `text` |
| `STORAGE_ERROR` | Ошибка хранения |

Обратите внимание: неудачная попытка структурировать текст (LLM не смог распознать ни категорию, ни факт приёма лекарства) — **не ошибка**. Событие сохраняется как есть, `category` и `medicationIntake` остаются пустыми. Пользовательский текст никогда не теряется только потому, что автоматическая структуризация не удалась (в отличие от `PIPELINE_FAILED` у документов, см. `03-documents.md` §4, — там ошибка Pipeline действительно блокирует результат, поскольку оригинал остаётся доступен по `fileUri` независимо от исхода, см. `02-files.md` §5).

---

## Синхронность

Как и `upload_document` (см. `03-documents.md` §5), обработка синхронна: `log_event` возвращает результат только после завершения всех этапов. Объём работы здесь меньше, чем при обработке документа (нет OCR), поэтому это не создаёт дополнительной задержки сверх той, что уже принята для документов.

# 4. Tool: medical.delete_event

Удаляет самостоятельно зафиксированное событие.

Сервис самостоятельно удаляет связанные `MedicationIntake` и события Timeline (см. `../domain/12-self-reported-events.md` §8).

## Параметры

| Поле | Тип | Обязательно | Описание |
|------|-----|-------------|----------|
| `userId` | string | ✅ | Идентификатор пользователя. |
| `eventId` | string | ✅ | Идентификатор события. |

## Ответ

```json
{
  "deleted": true
}
```

## Идемпотентность

`delete_event` идемпотентен: повторное удаление того же события возвращает тот же результат, не портит данные и не создаёт дублей. Несовпадение владельца неотличимо от отсутствия события — возвращается `{"deleted": false}` без указания причины (см. `01-overview.md` §11).

---

# 5. Чего нет в этом Tool

Редактирования события не существует — исправление ошибки в тексте выполняется через `delete_event` + новый `log_event`, а не через `update_event`. Это сохраняет тот же принцип неизменности первичного источника, что и для документов (см. `../architecture/01-overview.md` §6 "Оригинальные документы никогда не изменяются" — здесь распространён на `SelfReportedEvent.rawText`).

Просмотр событий отдельным Tool не предоставляется — для этого уже существует `medical.timeline` (см. `06-timeline.md`), которая включает `symptom`/`medication_taken` наравне с событиями, построенными из документов.

---

# 6. Типичный сценарий

```text
Пользователь

↓

"Заболела голова, выпил ибупрофен 400"

↓

Miranda

↓

medical.log_event(userId, text)

↓

Medical Service

↓

Structured Extraction (текст, не OCR)

↓

MedicationIntake создан

↓

Timeline обновлён (symptom + medication_taken)

↓

Событие доступно для medical.ask() и medical.timeline()
```

# 7. Архитектурные решения

Events API — второй, помимо Documents API, вход в медицинскую базу знаний, со своим, более коротким вариантом Processing Pipeline (без OCR и File Storage) — см. `../architecture/02-processing-pipeline.md` §17. Оба входа сходятся в одних и тех же производных слоях (Timeline, Search, Knowledge Providers), поэтому `medical.ask` и `medical.timeline` не различают, откуда взят факт, кроме как в ссылках на источник (см. `../domain/12-self-reported-events.md` §6).
