# 1. Назначение

Диагнозы читаются через `medical.profile` (`05-profile.md` §7 "Active Diagnoses") и `medical.ask` —
отдельного read-tool для них нет. `medical.resolve_diagnosis`, описанный здесь, — единственный
write-путь: пользователь может напрямую подтвердить, что диагноз разрешился ("да, ОРВИ прошла,
можешь отметить"), не дожидаясь нового документа, который бы это подтвердил.

Как и создание пункта плана (`08-planned-actions.md` §1), у этого действия нет отдельного tool'а
для "постановки" диагноза — диагнозы создаются только через `medical.upload_document`/
`medical.reprocess_document` (Extraction, см. `../architecture/02-processing-pipeline.md`).
`medical.resolve_diagnosis` — единственный tool, где статус меняется вне обработки документа, тот
же принцип "текст на входе, сервис сам разбирает", что и у `medical.decline_planned_action`.
(`status = superseded` — не-tool'овый способ смены статуса: его выставляет автоматическая
Diagnosis Reconciliation при обработке нового документа, а не пользователь через MCP — см.
`../domain/07-diagnosis-and-allergy.md`.)

# 2. Tool: medical.resolve_diagnosis

Помечает один из текущих (не `resolved` и не `superseded`) диагнозов пользователя разрешённым — по
тому, что сказал пользователь ("да, ОРВИ прошла", "простуда прошла"), а не по `diagnosisId`:
Miranda передаёт текст ровно так, как его произнёс пользователь, сервис сам находит подходящий
диагноз (одним небольшим Structured LLM-вызовом над коротким списком текущих не-`resolved`/
не-`superseded` диагнозов, см. `internal/decline` — тот же матчер, что и у
`medical.decline_planned_action`, обобщённый для переиспользования между обоими tool'ами).
`superseded`-диагноз не предлагается кандидатом: у него уже есть более новый диагноз-преемник, и
пользователь не станет говорить о нём "прошло".

## Параметры

| Поле | Тип | Обязательно | Описание |
|------|-----|-------------|----------|
| `userId` | string | ✅ | Идентификатор пользователя |
| `text` | string | ✅ | Что сказал пользователь, на естественном языке — не `diagnosisId` |

`resolve_diagnosis` не поддерживает `subjectId` — как и `log_event`/`decline_planned_action`,
действует только от имени `userId`, никогда не над данными другого пользователя, даже
расшарившего доступ на чтение (см. `01-overview.md` §11: совместный доступ даёт только чтение).

## Ответ

```json
{
  "diagnosisId": "dx_01J...",
  "name": "ОРВИ",
  "status": "resolved",
  "actualResolutionAt": "2026-03-10"
}
```

`actualResolutionAt` — момент вызова этого tool'а, а не дата из документа. Он независим от
`expectedResolutionFrom`/`expectedResolutionTo` (оценки, сделанной при Extraction) — подтверждение
разрешения не стирает эту оценку, а фиксируется рядом с ней, чтобы потом можно было сравнить
ожидание с фактом (см. `../domain/07-diagnosis-and-allergy.md`).

## Возможные ошибки

| Код | Описание |
|------|----------|
| `DIAGNOSIS_NOT_FOUND` | У пользователя нет ни одного не-`resolved`/не-`superseded` диагноза, либо ни один из текущих не соответствует уверенно тексту `text`. Сообщение перечисляет текущие названия, чтобы Miranda могла переспросить пользователя, какой именно диагноз он имел в виду, вместо тихого no-op. |
| `USER_NOT_FOUND` | Неизвестный пользователь |
| `INVALID_EVENT` | Пустой `text` |
| `STORAGE_ERROR` | Ошибка хранения |

## Чего нет в этом tool'е

Нет `diagnosisId`-based варианта — Miranda никогда не должна сама разбирать текст пользователя на
составляющие (тот же принцип, что и у `medical.log_event`/`medical.decline_planned_action`), только
передавать его как есть. Нет способа перевести диагноз в `suspected`/`chronic`/обратно в `active`
через этот tool, и нет ручного способа перевести диагноз в `superseded` вообще — только в
`resolved` через этот tool, и в `superseded` автоматически через Diagnosis Reconciliation; более
сложные ручные правки статуса, если понадобятся, проектируются отдельно.
