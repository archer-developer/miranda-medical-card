# 1. Назначение

Files API отвечает за хранение и получение бинарных файлов.

Файлы сами по себе не являются медицинскими документами.

Они представляют собой универсальные бинарные объекты, которые впоследствии могут использоваться различными компонентами системы.

Например:

- PDF;
- фотография анализа крови;
- фотография рецепта;
- выписка из больницы;
- результаты МРТ;
- ZIP-архив.

После загрузки файл получает уникальный `fileId`, который может использоваться другими MCP Tool.

---

# 2. Почему Files отделены от Documents

Импорт медицинского документа является длительной операцией.

Он может включать:

- OCR;
- анализ изображений;
- извлечение структуры;
- нормализацию;
- построение Timeline;
- генерацию Embeddings;
- обновление Medical Profile.

Все эти операции не должны выполняться во время загрузки файла.

Поэтому процесс разделён на два независимых этапа.

```
medical.upload_file

↓

fileId

↓

medical.upload_document(fileId)
```

Это позволяет:

- повторно использовать один файл;
- импортировать документ позже;
- выполнять предварительную проверку;
- использовать одинаковый механизм хранения файлов в других сервисах Miranda.

---

# 3. Жизненный цикл файла

```text
          upload_file
                │
                ▼
         Binary Storage
                │
                ▼
            fileId
                │
      ┌─────────┴──────────┐
      ▼                    ▼
upload_document      download_file
      │
      ▼
Medical Document
```

Файл существует независимо от медицинского документа.

---

# 4. Tool: medical.upload_file

Загружает бинарный файл в файловое хранилище.

Файл сохраняется без какой-либо обработки.

Никакой OCR, анализа содержимого или построения медицинской модели на этом этапе не выполняется.

---

## Параметры

| Поле | Тип | Обязательно | Описание |
|------|-----|-------------|----------|
| `userId` | string | ✅ | Идентификатор пользователя |
| `filename` | string | ✅ | Оригинальное имя файла |
| `contentType` | string | ✅ | MIME Type |
| `data` | bytes | ✅ | Содержимое файла |

---

## Ответ

```json
{
    "fileId": "file_01J9V...",
    "size": 2841934,
    "sha256": "...",
    "contentType": "application/pdf"
}
```

---

## Пример

```json
{
    "userId": "alex",
    "filename": "blood-test.pdf",
    "contentType": "application/pdf",
    "data": "<binary>"
}
```

---

## Возможные ошибки

| Код | Описание |
|------|----------|
| `USER_NOT_FOUND` | Неизвестный пользователь |
| `INVALID_FILE` | Некорректный файл |
| `FILE_TOO_LARGE` | Превышен допустимый размер |
| `UNSUPPORTED_CONTENT_TYPE` | Тип файла не поддерживается |
| `STORAGE_ERROR` | Ошибка файлового хранилища |

---

# 5. Идемпотентность

`upload_file` не является идемпотентным.

Повторная загрузка одинакового файла допускается.

Однако реализация может выполнять дедупликацию по SHA-256 и возвращать существующий `fileId`, если это соответствует выбранной стратегии хранения.

Дедупликация обязана быть скопирована по пользователю: ключ — пара `(userId, sha256)`, а не глобальный SHA-256. Глобальная дедупликация привела бы к тому, что один пользователь мог бы получить `fileId`, изначально принадлежащий другому члену семьи, просто загрузив байт-идентичный файл (например, типовой бланк направления) — это утечка факта существования и владения чужим файлом.

Конкретная стратегия определяется реализацией Storage Layer.

---

# 6. Tool: medical.download_file

Возвращает ранее загруженный файл.

Файл возвращается в исходном виде.

Medical Service не модифицирует содержимое файла.

---

## Параметры

| Поле | Тип | Обязательно | Описание |
|------|-----|-------------|----------|
| `userId` | string | ✅ | Идентификатор пользователя |
| `fileId` | string | ✅ | Идентификатор файла |

---

## Ответ

```json
{
    "filename": "blood-test.pdf",
    "contentType": "application/pdf",
    "size": 2841934,
    "data": "<binary>"
}
```

---

## Возможные ошибки

| Код | Описание |
|------|----------|
| `USER_NOT_FOUND` | Неизвестный пользователь |
| `FILE_NOT_FOUND` | Файл не найден, либо принадлежит другому пользователю, который не разрешил доступ через `shared_with` (см. `01-overview.md` §11) |
| `STORAGE_ERROR` | Ошибка файлового хранилища |

Отдельный код для "файл существует, но принадлежит другому пользователю" намеренно не используется — иначе сам факт существования и владения чужим файлом становится наблюдаемым. Если `userId` не совпадает с владельцем и владелец не включил `userId` в свой `shared_with`, ответ идентичен случаю отсутствующего файла.

---

# 7. Удаление файлов

Отдельный Tool для удаления файлов отсутствует.

Файл является частью медицинского документа.

Удаление происходит через:

```
medical.delete_document
```

Во время удаления документа сервис самостоятельно определяет, можно ли удалить связанный бинарный файл.

Например:

- если файл больше нигде не используется — он удаляется;
- если файл используется несколькими документами — удаляется только связь.

Это решение полностью скрыто от Miranda.

---

# 8. Ограничения

Files API не накладывает ограничений на тип содержимого файла.

Однако реализация может ограничивать:

- максимальный размер файла;
- допустимые MIME-типы;
- количество файлов на пользователя.

Эти ограничения определяются конфигурацией сервиса.

---

# 9. Гарантии

После успешного выполнения `medical.upload_file` сервис гарантирует:

- сохранность бинарного содержимого;
- неизменность файла;
- возможность последующего получения через `download_file`;
- возможность использования файла при импорте медицинского документа.

---

# 10. Что НЕ делает Files API

Files API не выполняет:

- OCR;
- анализ изображений;
- извлечение медицинских данных;
- генерацию Embeddings;
- построение Timeline;
- обновление Medical Profile;
- определение типа медицинского документа.

Все перечисленные операции начинаются только после вызова `medical.upload_document`.

---

# 11. Типичный сценарий использования

```text
Miranda

↓

medical.upload_file()

↓

fileId

↓

medical.upload_document(fileId)

↓

Medical Service

↓

Document Pipeline
```

Если пользователю впоследствии потребуется оригинальный файл:

```text
Miranda

↓

medical.download_file(fileId)

↓

Original Binary File
```

---

# 12. Архитектурные решения

Files API специально отделён от логики обработки медицинских документов.

Это обеспечивает:

- простую модель хранения файлов;
- повторное использование бинарных данных;
- независимость файлового хранилища от Pipeline;
- возможность повторного импорта документа без повторной загрузки файла;
- расширяемость для других сервисов Miranda, использующих тот же механизм хранения.

Files API рассматривает файл исключительно как бинарный объект и не делает никаких предположений о его содержимом.
