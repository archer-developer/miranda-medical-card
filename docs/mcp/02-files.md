# 1. Назначение

Files API отвечает за хранение и получение бинарных файлов.

Файлы сами по себе не являются медицинскими документами.

Они представляют собой универсальные бинарные объекты.

Например:

- PDF;
- фотография анализа крови;
- фотография рецепта;
- выписка из больницы;
- результаты МРТ;
- ZIP-архив.

`File` получает уникальный `fileId` в момент создания и остаётся доступен для последующего получения через `medical.download_file(fileId)` (см. §5).

---

# 2. Почему нет отдельного Tool для загрузки файла

У Files API нет собственного MCP Tool для создания `File` — сервис никогда не принимает содержимое файла как аргумент MCP-вызова.

Причина: base64 в аргументах MCP-вызова годится только для содержимого, которое LLM уже держит в собственном текстовом контексте. Для документа на несколько сотен килобайт (обычный размер отсканированного бланка анализов) это ненадёжно — ничто не гарантирует, что модель дословно воспроизведёт такую строку в своём выводе, а передача байт между сервисами — механическая задача, не требующая понимания естественного языка.

Поэтому единственный способ передать файл сервису — не отправить его байты, а сообщить, **где** их взять. Это выражено единственным входом в систему — `medical.upload_document(fileUri)` (см. `03-documents.md` §4): сервис получает URI, сам выполняет по нему HTTP GET и создаёт `File` как побочный эффект перед тем, как импортировать его как `MedicalDocument`. Кто именно хостит файл по этому URI (Miranda, любой другой сервис) и как этот URI получила LLM — вне ответственности Files API; единственное требование — URI должен быть доступен сервису по обычному HTTP(S) GET без дополнительной серверной авторизации (доверие обеспечивается тем, что сам вызов `medical.upload_document` уже прошёл bearer-auth `/mcp`).

`File` и `MedicalDocument` при этом остаются раздельными сущностями на уровне хранения (см. `../domain/03-files-and-documents.md` §1-2) — дедупликация по содержимому (см. §4), независимое скачивание оригинала (см. §5) и явное разделение уровней хранения (`../architecture/06-storage.md` §3-4) по-прежнему требуют этого разделения, даже при том что снаружи, через MCP, оно больше не выражено двумя последовательными вызовами.

---

# 3. Жизненный цикл файла

```text
        fileUri (внешний, не Files API)
                │
                ▼
    medical.upload_document(fileUri)
                │
                ▼
         Binary Storage
                │
                ▼
             fileId
                │
                ▼
        MedicalDocument
```

После создания `File` доступен независимо от `MedicalDocument` через `medical.download_file(fileId)` (см. §5).

---

# 4. Дедупликация

Создание `File` внутри `medical.upload_document` не идемпотентно в смысле "второй вызов ничего не создаёт" — за это отвечает отдельная проверка на уровне документа (`DOCUMENT_ALREADY_IMPORTED`, см. `03-documents.md` §4).

На уровне самого файла реализация выполняет дедупликацию по SHA-256 и возвращает существующий `fileId`, если содержимое уже было загружено этим же пользователем — например, если `fileUri` в двух вызовах разный, но указывает на байт-идентичное содержимое.

Дедупликация обязана быть скопирована по пользователю: ключ — пара `(userId, sha256)`, а не глобальный SHA-256. Глобальная дедупликация привела бы к тому, что один пользователь мог бы получить `fileId`, изначально принадлежащий другому члену семьи, просто загрузив байт-идентичный файл (например, типовой бланк направления) — это утечка факта существования и владения чужим файлом.

Конкретная стратегия определяется реализацией Storage Layer.

# 5. Tool: medical.download_file

Возвращает ранее загруженный файл.

Файл возвращается в исходном виде.

Medical Service не модифицирует содержимое файла.

---

## Параметры

| Поле | Тип | Обязательно | Описание |
|------|-----|-------------|----------|
| `userId` | string | ✅ | Идентификатор пользователя |
| `fileId` | string | ✅ | Идентификатор файла |

---

## Ответ

```json
{
    "filename": "blood-test.pdf",
    "contentType": "application/pdf",
    "size": 2841934,
    "data": "<binary>"
}
```

---

## Возможные ошибки

| Код | Описание |
|------|----------|
| `USER_NOT_FOUND` | Неизвестный пользователь |
| `FILE_NOT_FOUND` | Файл не найден, либо принадлежит другому пользователю, который не разрешил доступ через `shared_with` (см. `01-overview.md` §11) |
| `STORAGE_ERROR` | Ошибка файлового хранилища |

Отдельный код для "файл существует, но принадлежит другому пользователю" намеренно не используется — иначе сам факт существования и владения чужим файлом становится наблюдаемым. Если `userId` не совпадает с владельцем и владелец не включил `userId` в свой `shared_with`, ответ идентичен случаю отсутствующего файла.

# 6. Удаление файлов

Отдельный Tool для удаления файлов отсутствует.

Файл является частью медицинского документа.

Удаление происходит через:

```
medical.delete_document
```

Во время удаления документа сервис самостоятельно определяет, можно ли удалить связанный бинарный файл.

Например:

- если файл больше нигде не используется — он удаляется;
- если файл используется несколькими документами — удаляется только связь.

Это решение полностью скрыто от Miranda.

---

# 7. Ограничения

Files API не накладывает ограничений на тип содержимого файла.

Однако реализация может ограничивать:

- максимальный размер файла, скачиваемого по `fileUri` (`files.max_size_bytes` в конфигурации сервиса);
- допустимые MIME-типы;
- количество файлов на пользователя.

Эти ограничения определяются конфигурацией сервиса.

---

# 8. Гарантии

После того, как `medical.upload_document` успешно скачал файл по `fileUri` и сохранил его как `File`, сервис гарантирует:

- сохранность бинарного содержимого;
- неизменность файла;
- возможность последующего получения через `download_file`.

---

# 9. Что НЕ делает Files API

Files API не выполняет:

- OCR;
- анализ изображений;
- извлечение медицинских данных;
- генерацию Embeddings;
- построение Timeline;
- обновление Medical Profile;
- определение типа медицинского документа.

Все перечисленные операции начинаются только после успешного создания `MedicalDocument` внутри `medical.upload_document`.

---

# 10. Типичный сценарий использования

```text
Внешний сервис (например, Miranda)

↓

хостит файл, выдаёт fileUri

↓

medical.upload_document(fileUri)

↓

Medical Service скачивает файл по fileUri

↓

File создан (fileId)

↓

Document Pipeline
```

Если пользователю впоследствии потребуется оригинальный файл:

```text
Miranda

↓

medical.download_file(fileId)

↓

Original Binary File
```

# 11. Архитектурные решения

`File` как отдельная от `MedicalDocument` сущность сохраняется на уровне хранения (см. `../domain/03-files-and-documents.md` §1-2), даже без отдельного MCP Tool для его создания. Это обеспечивает:

- дедупликацию бинарных данных по содержимому (см. §4);
- независимость файлового хранилища от Pipeline;
- возможность получить оригинал документа отдельно от его медицинского содержимого (`download_file`).

Единственный вход, создающий `File`, — `medical.upload_document(fileUri)` (см. `03-documents.md` §4). Это сознательное сужение внешнего API: пока не существует ни одного MCP Tool, принимающего байты файла как аргумент, у LLM физически нет возможности передать сюда что-либо, кроме реального содержимого, полученного самим сервисом по URI.

Files API рассматривает файл исключительно как бинарный объект и не делает никаких предположений о его содержимом.
