# 1. Назначение

Documents API отвечает за управление медицинскими документами.

Под медицинским документом понимается любой файл, содержащий информацию о состоянии здоровья пользователя.

Например:

- результаты лабораторных исследований;
- выписки из стационара;
- назначения врача;
- рецепты;
- заключения специалистов;
- результаты МРТ, КТ, УЗИ;
- фотографии медицинских документов.

В отличие от Files API, Documents API запускает полный цикл обработки документа и превращает его в часть медицинской базы знаний.

---

# 2. Общая схема

```text
fileUri (файл хостится вовне, не в Medical Service)

↓

medical.upload_document(fileUri)

↓

Medical Service скачивает файл, создаёт File

↓

Pipeline

↓

Medical Knowledge Base
```

После завершения обработки документ становится доступен:

- для `medical.ask`;
- при построении Timeline;
- в Medical Profile;
- при поиске внутри сервиса.

---

# 3. Жизненный цикл документа

```text
          fileUri
             │
             ▼
    upload_document
             │
             ▼
      MedicalDocument
             │
             ▼
        Processing Pipeline
             │
             ▼
     Medical Knowledge Base
```

Импорт документа выполняется только один раз.

Повторная обработка бывает двух разных видов, которые не стоит путать:

- **массовая/административная** — переобработка множества документов после смены модели, промпта или версии Embeddings. Это внутренняя операция, доступная только через CLI (см. `../cli/*`), недоступна через MCP;
- **точечная, по инициативе пользователя** — "переделай этот документ, извлечение выглядит неполным". Это обычный пользовательский сценарий (см. §6 `medical.reprocess_document`), а не административная операция, и поэтому доступен через MCP.

# 4. Tool: medical.upload_document

Импортирует файл в медицинскую базу знаний.

Единственный способ передать файл — предоставить `fileUri`, а не его содержимое: сервис сам выполняет HTTP GET по этому адресу и получает байты. Никакой MCP Tool этого сервиса не принимает содержимое файла как аргумент вызова — см. `02-files.md` §2 за обоснованием (кратко: base64 в аргументах MCP-вызова ненадёжен для файлов от нескольких сотен КБ, поскольку требует, чтобы LLM дословно воспроизвела такую строку в собственном выводе).

Во время обработки сервис самостоятельно:

- скачивает файл по `fileUri` (см. "Как происходит скачивание" ниже) и создаёт `File` (см. `02-files.md` §4 про дедупликацию по содержимому);
- определяет тип документа;
- извлекает текст (OCR при необходимости);
- извлекает медицинские сущности;
- обновляет Timeline;
- обновляет Medical Profile;
- индексирует документ;
- строит Embeddings.

Все эти этапы полностью скрыты от Miranda.

---

## Параметры

| Поле | Тип | Обязательно | Описание |
|------|-----|-------------|----------|
| `userId` | string | ✅ | Идентификатор пользователя |
| `fileUri` | string | ✅ | `http(s)` URI, по которому сервис самостоятельно скачивает содержимое файла |

---

## Как происходит скачивание

Сервис выполняет обычный `GET fileUri` без какой-либо дополнительной авторизации на этом адресе — доверие обеспечивается тем, что сам вызов `medical.upload_document` уже прошёл bearer-auth `/mcp` (см. `01-overview.md` §5). Запрос ограничен таймаутом и размером ответа (`files.max_size_bytes` в конфигурации сервиса, см. `02-files.md` §7); `filename` и `contentType` определяются из заголовков ответа (`Content-Disposition`, `Content-Type`), с разумными запасными значениями, если сервер по `fileUri` их не прислал.

---

## Ответ

```json
{
    "documentId": "doc_01J9...",
    "status": "READY",
    "summary": "Консультативное заключение. Диагнозы: эссенциальная гипертензия (I10), нарушение липидного обмена (E78). Рекомендации по физической активности и питанию.",
    "extractedCounts": {
        "diagnoses": 9,
        "medications": 0,
        "labResults": 0,
        "instrumentalFindings": 0,
        "procedures": 0,
        "allergies": 0,
        "vitalSigns": 0,
        "recommendations": 4,
        "plannedActions": 1
    },
    "plannedActions": [
        {
            "plannedActionId": "plan_01J9...",
            "type": "lab_test",
            "description": "Контроль липидного профиля",
            "dueDateFrom": "2026-09-12",
            "dueDateTo": "2026-09-12",
            "overdue": false,
            "status": "pending",
            "sourceType": "document",
            "sourceId": "doc_01J9..."
        }
    ]
}
```

`summary` — то же значение, что хранится в `MedicalDocument.summary` (см. `../domain/03-files-and-documents.md` §3), возвращается сразу, чтобы Miranda могла показать пользователю, что именно распознано, не дожидаясь отдельного запроса.

`extractedCounts` — количество сущностей каждого типа, извлечённых из документа. Назначение — дать пользователю (через Miranda) возможность на глаз оценить, не выглядит ли результат подозрительно неполным (например, все категории пустые при явно содержательном документе), и при необходимости запросить `medical.reprocess_document` (см. §6). Это чисто механическая проверка (сравнение чисел), а не медицинская интерпретация — Miranda по-прежнему не анализирует содержимое.

`plannedActions` — та же форма, что у `medical.planned_actions` (см. `08-planned-actions.md` §4), но ограниченная только пунктами плана, добавленными или обновлёнными именно этим документом, — чтобы Miranda могла сразу сказать пользователю, что добавилось в план, не делая отдельный запрос `medical.planned_actions`. Пусто, если документ не содержал ни одной рекомендации с извлекаемым будущим действием.

---

## Повторная загрузка того же файла после сбоя

Если предыдущая попытка обработать этот файл (по содержимому — `(userId, sha256)`, см. `02-files.md` §4) закончилась `FAILED` (`PIPELINE_FAILED` — OCR/Structured Extraction не смогли получить содержательный результат, см. "Автоматический ретрай" ниже и `../architecture/02-processing-pipeline.md` §5), повторный вызов `upload_document` с тем же `fileUri` не возвращает `DOCUMENT_ALREADY_IMPORTED` — он **переобрабатывает тот же самый документ** (то же `documentId`, новая версия `Extraction`, как у `medical.reprocess_document`, см. §6) и возвращает обычный результат, если на этот раз обработка прошла успешно, либо снова `PIPELINE_FAILED`. `DOCUMENT_ALREADY_IMPORTED` возвращается только когда для файла уже существует документ в статусе, отличном от `FAILED` — то есть когда файл был успешно (или всё ещё) импортирован, а не просто когда-то упомянут.

---

## Возможные ошибки

| Код | Описание |
|------|----------|
| `USER_NOT_FOUND` | Пользователь не существует |
| `INVALID_FILE` | `fileUri` пуст либо не является `http(s)` URL |
| `FILE_NOT_FOUND` | По `fileUri` получен `404` — файла там нет |
| `FILE_FETCH_FAILED` | Не удалось скачать файл по `fileUri` (сетевая ошибка, таймаут, неожиданный код ответа, содержимое превышает допустимый размер) |
| `DOCUMENT_ALREADY_IMPORTED` | Файл (по содержимому) уже **успешно** импортирован — существующий `MedicalDocument` для этого файла в статусе, отличном от `FAILED` (см. ниже). |
| `UNSUPPORTED_DOCUMENT` | Документ не удалось обработать |
| `PIPELINE_FAILED` | Ошибка обработки документа |

---

## Автоматический ретрай при подозрении на сбой извлечения

Прежде чем вернуть ответ, Pipeline самостоятельно проверяет правдоподобность результата Structured Extraction: если распознанный текст документа содержательный (превышает пороговую длину), а категории, которые для данного `documentType` реально ожидаются, пусты — это рассматривается как вероятный сбой (см. `../architecture/02-processing-pipeline.md` §5 за обоснованием и конкретными наблюдениями), и соответствующий этап перезапускается автоматически (ограниченное число раз), прежде чем документ будет считаться обработанным.

Проверяется не любая пустая категория, а именно та, что типична для данного `documentType` (например, `labResults` для `lab_report`, `medications` для `prescription`) — `documentType` сам является обязательным полем результата, поэтому известен уже после первой попытки. Так проверка не вводится в заблуждение попутно заполненным, но нерелевантным полем (например, общей фразой в `recommendations`) при том, что интересующая категория так и осталась пустой. Для типов документа без известного заранее набора ожидаемых категорий (`other`) проверка более консервативна — требуется, чтобы были пусты все категории сразу.

Для находок инструментальных исследований (`InstrumentalFinding`, см. `../domain/13-instrumental-finding.md`) та же проверка неприменима напрямую: пустой результат для этой категории — норма для подавляющего большинства документов (в лабораторном бланке или рецепте инструментальных находок и не должно быть), поэтому слепой ретрай при пустом результате тратил бы вызовы LLM впустую на каждый документ, не относящийся к визуализации. Ретрай для этой категории включается только если сам документ уже классифицирован как `imaging_report`.

Это работает только против одного конкретного, наиболее частого паттерна сбоя — пустоты ожидаемой для этого типа документа категории при содержательном тексте. Более тонкие частичные пропуски (например, не все строки таблицы лабораторных показателей попали в `labResults`) эта проверка не ловит; для них предназначены `extractedCounts` в ответе и `medical.reprocess_document` (см. §6).

---

# 5. Синхронность выполнения

Для первой версии сервиса предполагается синхронная обработка документа.

Tool возвращает управление только после завершения Pipeline.

Это гарантирует, что сразу после успешного завершения:

- документ доступен в `medical.ask`;
- Timeline обновлён;
- Medical Profile актуален.

В будущем допускается переход на асинхронную обработку без изменения внешнего контракта.

---

# 6. Tool: medical.reprocess_document

Заново прогоняет уже импортированный документ через Pipeline, используя тот же оригинальный файл — без повторной загрузки.

Предназначен для одного конкретного пользовательского сценария: результат `upload_document` выглядит неполным (см. `extractedCounts` в §4), и пользователь просит "переделай" через диалог с Miranda.

**Это не то же самое, что административная переобработка** (см. §3): не меняет модель, промпт или их версии — использует ровно ту же конфигурацию, что и обычный `upload_document`. Единственная причина, по которой второй запуск может дать другой (лучший) результат — вариативность самой LLM (см. `../architecture/02-processing-pipeline.md` §5).

---

## Параметры

| Поле | Тип | Обязательно | Описание |
|------|-----|-------------|----------|
| `userId` | string | ✅ | Идентификатор пользователя |
| `documentId` | string | ✅ | Идентификатор документа |

`reprocess_document` не поддерживает `subjectId` — как и все операции записи, доступен только для собственных документов (см. `01-overview.md` §11).

---

## Ответ

Та же форма, что у `upload_document` (см. §4) — `documentId`, `status`, `summary`, `extractedCounts`.

---

## Что происходит внутри

Сервис самостоятельно:

- создаёт новую версию `Extraction` поверх того же `Artifact`/`File` (см. `../domain/03-files-and-documents.md` §4) и делает её активной;
- полностью заменяет Domain Entities, Timeline Events и `InstrumentalFinding` для этого документа (документ-скоуп replace, тот же принцип идемпотентности, что и при первичной обработке — см. `../architecture/02-processing-pipeline.md` §2);
- пересчитывает Medical Profile и поисковые индексы, как после любого изменения документа.

Предыдущая версия `Extraction` не удаляется — сохраняется неактивной, для отладки и сравнения качества (см. `../domain/03-files-and-documents.md` §4 "Версионирование").

---

## Возможные ошибки

| Код | Описание |
|------|----------|
| `USER_NOT_FOUND` | Пользователь не существует |
| `DOCUMENT_NOT_FOUND` | Документ не найден, либо принадлежит другому пользователю |
| `PIPELINE_FAILED` | Ошибка обработки документа |

# 7. Tool: medical.list_documents

Возвращает список всех медицинских документов пользователя.

Инструмент предназначен прежде всего для построения пользовательского интерфейса.

Он не возвращает содержимое документов.

---

## Параметры

| Поле | Тип | Обязательно | Описание |
|------|-----|-------------|----------|
| `userId` | string | ✅ | Идентификатор пользователя |
| `subjectId` | string | ❌ | Чьи документы получить, если не свои — см. `01-overview.md` §11 |

---

## Ответ

```json
[
  {
    "documentId": "doc_01J9...",
    "title": "Общий анализ крови",
    "documentType": "lab_report",
    "documentDate": "2025-03-12",
```

Это делает список более естественным для пользователя.

# 8. Tool: medical.get_document

Возвращает информацию о конкретном медицинском документе.

Инструмент предназначен для отображения информации о документе в интерфейсе Miranda.

---

## Параметры

| Поле | Тип | Обязательно | Описание |
|------|-----|-------------|----------|
| `userId` | string | ✅ | Идентификатор пользователя |
| `documentId` | string | ✅ | Идентификатор документа |

Владелец документа определяется по самому `documentId`; отдельный параметр `subjectId` здесь не нужен. Если документ принадлежит другому пользователю и его владелец не включил `userId` в свой `shared_with`, ответ идентичен `DOCUMENT_NOT_FOUND` — см. `01-overview.md` §11.

---

## Ответ

```json
{
  "documentId": "doc_01J9...",
  "title": "Общий анализ крови",
  "documentType": "lab_report",
  "documentDate": "2025-03-12",
  "uploadedAt": "2025-03-13T18:42:00Z",
  "fileUri": "https://<host>/files/file_01J9..."
}
```

`fileUri` — абсолютная HTTP(S) ссылка на оригинальный файл документа, обслуживаемая отдельным HTTP-эндпойнтом сервиса (не MCP Tool, см. `02-files.md` §5.1): обычный `GET`, тот же bearer-токен, что и у `/mcp`. Доступ (владение/`shared_with`) проверяется один раз, в момент этого вызова `get_document`, а не заново при самом `GET` — если нужна проверка на момент запроса файла (например, доступ мог быть отозван позже), используйте `medical.download_file(fileId)` (см. `02-files.md` §5.2).

---

## Почему Tool не возвращает содержимое документа

Medical Service не предполагает отображение полного текста документа через MCP.

Если пользователю требуется оригинал документа, Miranda может использовать либо `fileUri` из ответа этого Tool, либо `medical.download_file(fileId)` (см. `02-files.md` §5).

Если пользователю нужен анализ содержимого документа, следует использовать:

```
medical.ask()
```

Таким образом разделяются:

- оригинальный файл;
- медицинские знания;
- пользовательское представление.

> документа пока не входит в MCP API (см. `01-overview.md` §16 за актуальным списком Tools). Нумерация
> секций ниже сохранена как есть, без сдвига, чтобы не ломать существующие ссылки на §11 и далее из
> других документов.

# 10. Идемпотентность

`reprocess_document` (см. §6) идемпотентен в смысле "безопасно вызывать многократно, никогда не портит данные и не создаёт дублей" (документ-скоуп replace, как и при первичной обработке), но **не** в смысле "возвращает тот же результат" — сама цель повторного запуска в том, что результат может отличаться от предыдущего (см. `../architecture/02-processing-pipeline.md` §5).

---

# 11. Что считается документом

Medical Service не накладывает жёстких ограничений на тип документа.

Во время обработки Pipeline самостоятельно определяет его назначение.

Например:

- лабораторное исследование;
- выписка;
- рецепт;
- консультация;
- снимок;
- направление;
- произвольный медицинский документ.

Miranda не обязана определять тип документа заранее.

---

# 12. Связь с Pipeline

Documents API является единственной точкой входа в Processing Pipeline — `upload_document` (первичный запуск) и `reprocess_document` (повторный запуск того же документа, см. §6). Ни один другой MCP Tool не может запускать Pipeline.

Это гарантирует единый жизненный цикл всех медицинских данных.

---

# 13. Типичный сценарий

```text
Пользователь

↓

Отправляет PDF

↓

Miranda хостит файл, получает fileUri

↓

upload_document(fileUri)

↓

Medical Service скачивает файл по fileUri

↓

Pipeline

↓

Timeline обновлён

↓

Medical Profile обновлён

↓

Документ доступен для medical.ask()
```

---

# 14. Что НЕ делает Documents API

Documents API не:

- отвечает на вопросы пользователя;
- выполняет поиск;
- возвращает медицинские выводы;
- показывает Timeline;
- возвращает Medical Profile;
- позволяет управлять Pipeline.

Все эти возможности предоставляются отдельными MCP Tools.

---

# 15. Архитектурные решения

Documents API имеет единственную ответственность — превратить внешний файл в часть медициной базы знаний.

После успешного импорта документ становится полноправным источником знаний для всей системы.

Ни Miranda, ни пользователь не управляют отдельными этапами обработки.
