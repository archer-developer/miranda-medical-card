# 1. Назначение

`medical.ask` является главным MCP Tool Medical Service.

Именно через него Miranda получает экспертные ответы на медицинские вопросы пользователя.

В отличие от остальных MCP Tool, данный инструмент не предоставляет доступ к данным напрямую.

Он самостоятельно:

- понимает вопрос пользователя;
- определяет необходимые источники знаний;
- собирает медицинский контекст;
- анализирует информацию;
- формирует итоговый ответ.

Для Miranda этот процесс полностью прозрачен.

---

# 2. Основная идея

Medical Service рассматривается как медицинский эксперт.

Miranda не анализирует медицинские данные самостоятельно.

Вместо этого она делегирует вопрос специалисту.

```text
User

↓

Miranda

↓

medical.ask()

↓

Medical Expert

↓

Answer
```

---

# 3. Ответственность Tool

`medical.ask` отвечает за:

- понимание вопроса;
- выбор необходимых Knowledge Providers;
- поиск информации;
- анализ медицинских данных;
- построение логических выводов;
- генерацию понятного ответа.

Все перечисленные этапы выполняются внутри сервиса.

---

# 4. Что НЕ делает Miranda

Miranda никогда не должна:

- искать документы;
- выбирать анализы;
- определять нужные лекарства;
- анализировать лабораторные показатели;
- искать события Timeline;
- объединять медицинские данные;
- выполнять медицинские выводы.

Единственная задача Miranda — передать вопрос пользователя.

# 5. Интерфейс

## Параметры

| Поле | Тип | Обязательно | Описание |
|------|-----|-------------|----------|
| `userId` | string | ✅ | Идентификатор пользователя |
| `subjectId` | string | ❌ | О чьих данных вопрос, если не о своих (например, вопрос родителя о здоровье ребёнка) — см. `01-overview.md` §11 |
| `question` | string | ✅ | Вопрос пользователя на естественном языке |
| `sessionId` | string | ✅ | Идентификатор сессии/беседы — собственный идентификатор беседы Miranda, переданный без изменений, чтобы внутренняя беседа агента «Медкарты» оставалась синхронизирована с беседой Miranda и уточняющие вопросы понимались в контексте предыдущего вопроса/ответа (см. §7.1). Сессия определяется только этим идентификатором — смена `subjectId` в рамках одной сессии (например, "а что насчёт анализов сына?") не начинает новую беседу. **Важно**: это поле подставляется бэкендом Miranda (её уже разрешённым `conversationID`), а не заполняется моделью, вызывающей инструмент — модель не должна сама придумывать значение (см. jsonschema-описание `internal/mcpserver/ask.go`'s `AskInput.SessionID`). Реализовано на стороне Miranda по аналогии с инъекцией ключа шифрования для miranda-diary — см. `setSessionIDArg`/`setEncryptionKeyArg` в `miranda/internal/httpapi/agent_loop.go`, `miranda/docs/medical-card-session-injection.md`; та подстановка безусловно перезаписывает значение перед отправкой запроса, так что required-ность здесь не рискует вынудить модель самой придумывать значение — что бы модель ни написала (или не написала), в медкарту всегда уходит настоящий `conversationID`. Пустая строка тоже отклоняется отдельной проверкой в `askHandler` (required в JSON Schema гарантирует только присутствие поля, не непустоту). Единственный легитимный вызывающий без сессии — `medical-dev`'s CLI-команда `ask` (`cmd/medical-dev/main.go`), которая обращается к `ask.Asker.Ask` напрямую в Go, минуя эту MCP-схему целиком. |

---

## Ответ

```json
{
    "answer": "...",
    "sources": [
        {
            "documentId": "doc_01J9...",
            "eventId": "evt_01J...",
            "title": "Общий анализ крови от 12 марта 2025",
            "excerpt": "ALT 54.7 U/L (норма 10-40 U/L)"
        }
    ]
}
```

`sources` — структурированный список записей, на основе которых построен ответ. Каждый элемент ссылается на `documentId` и/или `eventId` (Timeline), если ответ на них опирался; поля `title`/`excerpt` предназначены для отображения. Массив может быть пустым, если ответ не опирается на конкретные записи (например, при ответе "информация не найдена").

Это позволяет Miranda показывать ссылки на первоисточник рядом с ответом (например, кнопку "открыть документ") и упрощает тестирование качества ответов — см. `../architecture/05-llm.md` §16 про эталонные вопросы и ожидаемые ответы.

# 7. Внутренний Agent Loop

`medical.ask` обслуживается внутренним агентом — одним открытым диалогом с LLM (см. `../architecture/05-llm.md` §3, `../adr/001-internal-agent-loop-implementation.md`), а не фиксированной последовательностью отдельных вызовов:

```text
Question (+ история сессии, если sessionId уже встречался ранее)

↓

Agent Loop: модель решает, вызвать ли Knowledge Provider

↓ (да — результат возвращается в диалог, возможен ещё один вызов)
↓ (нет — ответ готов)

Answer
```

Модель сама решает, какие Knowledge Providers вызвать, с какими параметрами, и может вызвать ещё один Provider на основании результата предыдущего — вместо того чтобы фиксировать план один раз в начале. Как только модель отвечает обычным текстом без нового вызова инструмента, этот текст становится ответом.

Весь Agent Loop является внутренней реализацией сервиса.

Miranda ничего не знает о его существовании — она передаёт вопрос и `sessionId` и получает готовый ответ.

---

# 7.1 Сессии и уточняющие вопросы

`sessionId` (см. §5) — обязательный параметр, подставляемый бэкендом Miranda её собственным разрешённым `conversationID` (реализация — `miranda/docs/medical-card-session-injection.md`). Сервис сохраняет историю вопросов, ответов и промежуточных вызовов инструментов этой сессии и учитывает её при обработке следующего вопроса с тем же `sessionId` — это то, что делает уточняющие вопросы ("а когда это началось?", "а что насчёт анализов?") осмысленными без повторения полного контекста в каждом вопросе.

При первом обращении с новым, ранее не встречавшимся `sessionId` (начало новой беседы в Miranda) `medical.ask` естественным образом ведёт себя так же, как при отсутствии истории — сохранённых предыдущих вопросов/ответов для этого `sessionId` попросту ещё нет.

Сессия, к которой долго не обращались, считается устаревшей — новый вопрос с тем же `sessionId` после длительного перерыва начинает беседу заново, а не продолжает давно забытый разговор.

Единственный вызывающий, у которого в принципе нет `sessionId` — `medical-dev`'s диагностическая CLI-команда `ask` (см. `docs/cli/medical_dev.md`): она обращается к внутреннему Go API медкарты напрямую, минуя MCP и, соответственно, требование обязательности этого поля.

# 8. Knowledge Providers как инструменты

Каждый зарегистрированный Knowledge Provider — это инструмент (LLM tool), который модель может вызвать в любой момент диалога, любое число раз, с параметрами, специфичными для этого Provider.

Например, для вопроса:

> Почему врач отменил статины?

модель может вызвать:

- Timeline Provider;
- Medication Provider;
- Lab Provider;
- Document Provider —

в любом порядке, и не обязательно все сразу: например, сначала Medication Provider, а затем, увидев в его ответе дату отмены, ещё раз Timeline Provider, чтобы уточнить, что происходило в это время.

При этом Miranda ничего не знает о выборе источников — как и раньше, это полностью внутренняя деталь реализации.

---

# 9. Формирование ответа

Результат каждого вызова Provider возвращается обратно в диалог с моделью — сервис никогда не показывает LLM внутреннее устройство хранения (SQL, структуру таблиц), только уже подготовленные, человекочитаемые факты (см. `../architecture/03-knowledge-providers.md` §12).

Модель работает исключительно с этими подготовленными знаниями и никогда не анализирует документы напрямую. Как только накопленных знаний достаточно, модель формирует финальный ответ в рамках того же диалога — без отдельного, изолированного от выбора источников вызова.

---

# 10. Ограничения

Если необходимая информация отсутствует в базе знаний, сервис должен честно сообщить об этом.

Например:

> В медицинской истории нет информации о данном заболевании.

или

> Не удалось найти документы за указанный период.

LLM не должна придумывать отсутствующие факты.

---

# 11. Использование Timeline

Практически любой медицинский вопрос имеет временной контекст.

Поэтому Timeline является одним из наиболее часто используемых Knowledge Providers.

Например.

> Что происходило после операции?

> Когда начали принимать препарат?

> Что изменилось летом прошлого года?

Все подобные вопросы решаются через Timeline.

---

# 12. Использование Profile

При вопросах о текущем состоянии здоровья автоматически используется Medical Profile.

Например.

> Какие лекарства я сейчас принимаю?

> Какие хронические заболевания у меня есть?

> Какие аллергии известны?

Использование агрегированного профиля позволяет избежать анализа всей истории болезни.

---

# 13. Источники знаний

Во время обработки вопроса сервис может использовать одновременно:

- Timeline;
- Self-Reported Events;
- Medical Profile;
- Medications;
- Diagnoses;
- Procedures;
- Lab Results;
- Documents;
- Embeddings.

Выбор источников полностью определяется агентом (Agent Loop, см. §7) по ходу диалога.

---

# 14. Производительность

Каждый Provider работает независимо.

Если требуется несколько источников знаний, они выполняются параллельно.

После завершения результаты объединяются в единый контекст.

---

# 15. Ответ

Ответ формируется специально для пользователя.

Он должен быть:

- понятным;
- структурированным;
- основанным на найденных данных;
- не содержать необоснованных предположений.

При необходимости сервис должен указывать источник своих выводов.

Например:

> Согласно результатам анализа крови от 12 марта 2025 года...

или

> В выписке после госпитализации указано...

или, если факт взят из самостоятельно зафиксированного события (см. `07-events.md`), а не из документа:

> По вашей собственной записи от 3 августа...

Формулировка должна давать понять, что источник — неверифицируемая запись пользователя, а не документ, подтверждённый врачом или лабораторией (см. `../domain/12-self-reported-events.md` §6).

---

# 16. Чего не гарантирует Tool

`medical.ask` не предоставляет медицинских рекомендаций, выходящих за пределы известных сервису данных.

Он не заменяет врача.

Если вопрос требует профессиональной диагностики, сервис должен явно указать на это.

Например:

> По имеющимся документам невозможно определить причину повышения ALT. Для интерпретации результатов рекомендуется обсудить их с лечащим врачом.

---

# 17. Архитектурные решения

`medical.ask` является единственной точкой входа для интеллектуального анализа медицинской информации.

Это позволяет:

- изменять внутренний Pipeline;
- заменять модели LLM;
- добавлять новые Knowledge Providers;
- изменять алгоритмы поиска;
- совершенствовать медицинскую модель.

Все эти изменения происходят без изменения MCP API.

---

# 18. Будущие расширения

В будущем возможности `medical.ask` могут быть расширены без изменения интерфейса.

Например:

- анализ изображений, приложенных к вопросу;
- учет информации из других сервисов Miranda (питание, сон, фитнес);
- построение долгосрочных трендов;
- сравнение показателей за разные периоды;
- объяснение медицинских терминов;
- анализ лекарственных взаимодействий;
- использование специализированных медицинских моделей.

Все эти возможности должны оставаться внутренней реализацией сервиса и не изменять внешний контракт MCP Tool.
