# 1. Назначение

`medical.profile` возвращает агрегированное текущее состояние здоровья пользователя.

В отличие от `medical.ask`, данный Tool не выполняет анализ, рассуждения или поиск ответа на вопрос.

Он предоставляет структурированное представление медицинского профиля, пригодное для:

- отображения в пользовательском интерфейсе;
- использования другими сервисами Miranda;
- быстрого доступа к наиболее важной медицинской информации.

Medical Profile является производной сущностью и автоматически поддерживается в актуальном состоянии после обработки каждого нового документа.

---

# 2. Когда использовать

Используйте `medical.profile`, если необходимо получить текущее состояние здоровья пользователя в структурированном виде.

Например:

- показать карточку здоровья;
- отобразить список текущих лекарств;
- показать хронические заболевания;
- показать известные аллергии;
- показать последние важные показатели.

Если требуется ответить на вопрос пользователя или выполнить анализ медицинской информации, следует использовать `medical.ask`.

---

# 3. Что входит в профиль

Medical Profile представляет собой "снимок" текущего состояния здоровья.

Он не содержит полной истории болезни.

В профиль входят только актуальные данные.

Например:

- активные диагнозы;
- хронические заболевания;
- текущие лекарства;
- известные аллергии;
- последние жизненные показатели;
- последние результаты анализов;
- информация о прививках;
- перенесённые операции;
- диетические ограничения и рекомендации по питанию;
- основные сведения о пациенте.

---

# 4. Что НЕ входит в профиль

В профиль не включаются:

- история изменений;
- отменённые лекарства;
- старые назначения;
- архивные анализы;
- текст документов;
- рекомендации врачей;
- Timeline.

Для подобных данных используются другие MCP Tool.

---

# 5. Интерфейс

## Параметры

| Поле | Тип | Обязательно | Описание |
|------|-----|-------------|----------|
| `userId` | string | ✅ | Идентификатор пользователя |
| `subjectId` | string | ❌ | Чей профиль получить, если не свой — см. `01-overview.md` §11 |

---

## Ответ

```json
{
  "patient": {
    "name": "Alexander",
    "birthDate": "1989-05-17",
    "sex": "male"
  },

  "activeDiagnoses": [],

  "chronicConditions": [],

  "activeMedications": [],

  "allergies": [],

  "vaccinations": [],

  "surgeries": [],

  "latestLabResults": [],

  "latestVitalSigns": [],

  "nutritionGuidance": {
    "restrictions": [],
    "recommendations": []
  }
}
```

Приведённая структура является примером.

Конкретный состав профиля может расширяться в новых версиях сервиса без нарушения обратной совместимости.

MCP-ответ содержит эту структуру дважды — как `structuredContent`, так и как JSON-текст в `content` (текстовый блок) — и оба представления всегда идентичны. Ранее `content` был короткой человекочитаемой сводкой (например «3 диагноза, 2 лекарства, 1 аллергия»), из-за чего вызывающая сторона, читающая только `content`, получала лишь часть профиля — что и приводило к неполным ответам и неверной группировке данных при построении PDF (см. docs/adr/002-structured-profile-response.md). Теперь `content` — это ровно тот же полный JSON, что и `structuredContent`, поэтому не имеет значения, какое из двух полей читает клиент.

---

# 6. Active Medications

Содержит только препараты, которые считаются активными на текущий момент.

Например:

```json
[
  {
    "name": "Rosuvastatin",
    "dose": "10 mg",
    "frequency": "1 раз в день",
    "startedAt": "2025-05-14"
  }
]
```

История назначения препаратов в профиль не входит.

---

# 7. Active Diagnoses

Возвращаются только актуальные диагнозы.

Например:

```json
[
  {
    "code": "I10",
    "name": "Артериальная гипертензия",
    "overdue": false
  }
]
```

`overdue` — `true`, когда диагноз ещё числится `active`, но его оценочный срок разрешения (не из документа, общая
медицинская оценка — см. `../domain/07-diagnosis-and-allergy.md`) уже прошёл. Не меняет сам статус диагноза, только
подсказывает, что его стоит перепроверить.

Исторические диагнозы доступны через `medical.ask` или Timeline.

---

# 8. Allergies

Содержит известные аллергические реакции пользователя.

Например:

```json
[
  {
    "substance": "Penicillin",
    "reaction": "Rash"
  }
]
```

---

# 9. Latest Lab Results

Возвращаются последние значения наиболее важных лабораторных показателей.

Например:

```json
[
  {
    "name": "ALT",
    "value": 54.7,
    "unit": "U/L",
    "date": "2025-06-12",
    "documentSource": "Биохимический анализ крови"
  },
  {
    "name": "LDL",
    "value": 3.1,
    "unit": "mmol/L",
    "date": "2025-06-12",
    "documentSource": "Биохимический анализ крови"
  },
  {
    "name": "Группа крови",
    "qualitativeValue": "A(II) Rh+",
    "date": "2025-06-12",
    "documentSource": "Общий анализ крови"
  }
]
```

Показатель либо числовой (`value`+`unit`), либо описательный (`qualitativeValue`, без единицы измерения) — например группа крови или результат теста `положительно`/`отрицательно`. Ровно одно из двух обычно заполнено.

`documentSource` — название/тип исходного документа, из которого взято значение (например «Общий анализ крови» vs «Общий анализ мочи»). Без этого поля два одноимённых показателя из разных типов документов (например «Белок» в анализе крови и «Белок» в анализе мочи) неотличимы друг от друга — это приводило к неверной группировке данных на стороне Miranda (см. docs/adr/002-structured-profile-response.md). Пусто, если у исходного документа нет заголовка.

Это не история изменений.

Это текущее известное значение каждого показателя.

---

# 10. Latest Vital Signs

Возвращаются последние известные показатели жизнедеятельности.

Например:

```json
[
  {
    "name": "Blood Pressure",
    "value": "130/82",
    "date": "2025-05-30",
    "documentSource": "Консультация терапевта"
  },
  {
    "name": "Weight",
    "value": "84 kg",
    "date": "2025-05-30",
    "documentSource": "Консультация терапевта"
  }
]
```

`documentSource` — тот же смысл, что и у одноимённого поля Latest Lab Results (§9).

---

# 11. Nutrition Guidance

Диетические ограничения и рекомендации, выведенные из активных диагнозов/хронических состояний,
аллергий, активных лекарств, перенесённых операций, возраста/пола и симптомов, зафиксированных
пользователем за последний месяц — см. `../adr/006-nutrition-guidance.md`. Перенесённая операция
учитывается без ограничения по давности (например, холецистэктомия остаётся значимой независимо от
того, когда она была) — в отличие от симптомов, для которых важен только последний месяц.

Например:

```json
{
  "restrictions": [
    {
      "text": "Строго ограничить жирную пищу",
      "reason": "После холецистэктомии снижена выработка желчи, жир переваривается хуже"
    }
  ],
  "recommendations": [
    {
      "text": "Увеличить клетчатку в рационе",
      "reason": "Жалобы на запоры в последний месяц"
    }
  ]
}
```

Каждый пункт — короткое направление (`text`) плюс однострочное медицинское обоснование (`reason`),
**не** конкретное блюдо, продукт или норма КБЖУ — подбор конкретного меню с учётом этих ограничений
и калорийности остаётся на стороне Miranda, не этого сервиса (см. `../CLAUDE.md`'s разделение
"Miranda — оркестратор... Medical Service — медицинский эксперт").

`restrictions`/`recommendations` — оба пустые, если у пользователя нет ни одного диагноза, аллергии
или симптома за последний месяц, из которого можно было бы что-то вывести — это не ошибка, просто
означает "сейчас нет известных диетических ограничений".

В отличие от остальных разделов профиля, это единственный раздел, для формирования которого
используется LLM (`../adr/006-nutrition-guidance.md` §2) — остальной `medical.profile` остаётся
чистой агрегацией без каких-либо LLM-вызовов.

---

# 12. Автоматическое обновление

Medical Profile никогда не редактируется вручную.

После успешной обработки документа сервис автоматически:

- обновляет лекарства;
- обновляет диагнозы;
- обновляет лабораторные показатели;
- обновляет жизненные показатели;
- обновляет аллергии;
- обновляет диетические ограничения и рекомендации (§11);
- обновляет остальные агрегированные данные.

То же самое происходит и после `medical.log_event`/`medical.delete_event` — не только после обработки
документа, — поскольку раздел Nutrition Guidance (§11) зависит и от симптомов, зафиксированных
напрямую в диалоге.

---

# 13. Производительность

Medical Profile является материализованной агрегированной сущностью.

Для получения ответа не требуется анализировать всю медицинскую историю пользователя.

Это делает `medical.profile` одним из самых быстрых MCP Tool.

---

# 14. Использование внутри Medical Service

Во время обработки вопросов `medical.ask` профиль может использоваться как один из Knowledge Providers.

Например:

> Какие лекарства я сейчас принимаю?

В этом случае сервис может получить информацию непосредственно из Medical Profile без анализа всей истории документов.

---

# 15. Ограничения

Medical Profile не предназначен для анализа медицинской истории.

Если вопрос пользователя требует:

- анализа динамики;
- сравнения периодов;
- поиска причин;
- анализа документов;
- поиска закономерностей;

следует использовать `medical.ask`.

---

# 16. Обратная совместимость

Новые разделы профиля могут добавляться без изменения существующих полей.

Например:

- Family History;
- Genetic Risks;
- Implanted Devices;
- Insurance Information;
- Emergency Contacts.

Клиенты должны корректно обрабатывать появление новых разделов.

---

# 17. Архитектурные решения

Medical Profile является производной сущностью.

Он:

- автоматически перестраивается;
- не редактируется вручную;
- не является источником истины;
- служит оптимизированным представлением текущего состояния здоровья.

Источником истины всегда остаются структурированные медицинские сущности, извлечённые из документов.

---


# 19. Будущие расширения

Medical Profile может постепенно расширяться по мере развития сервиса.

Например:

- индекс массы тела;
- история курения;
- употребление алкоголя;
- уровень физической активности;
- сведения о сне;
- семейный анамнез;
- хронические факторы риска;
- имплантированные устройства;
- страховая информация.

Все новые разделы должны оставаться агрегированным представлением текущего состояния пользователя и не превращать Profile в полную медицинскую историю.
