# 1. Назначение

Планированные действия — будущие медицинские манипуляции (контрольный анализ, прививка, повторный
визит), извлечённые из рекомендаций в документах или сказанные пользователем напрямую в диалоге с
Miranda. У медкарты нет собственного механизма напоминаний — эта функция принадлежит Miranda.
`medical.planned_actions` отдаёт ей структурированный список для расстановки собственных
напоминаний (push-уведомления, календарь и т.д.).

Создание нового пункта плана из диалога идёт через уже существующий `medical.log_event`
(`07-events.md` §3), а не через отдельный write-tool — см. `../adr/004-planned-actions.md` §3 за
обоснованием. Отмена — через `medical.decline_planned_action`, ручная отметка "выполнено" — через
`medical.complete_planned_action`; оба описаны здесь.

Как и `medical.timeline`, оба тула здесь не выполняют анализ — только данные.

---

# 2. Timeline vs Planned Actions

`medical.timeline` (`06-timeline.md`) — строго ретроспективна: только то, что уже произошло.
`medical.planned_actions` — строго перспективна: только то, что ещё предстоит (или предстояло, но
уже выполнено/отменено — см. `includeResolved`). Пункт плана никогда не попадает в Timeline, и
наоборот; когда пункт плана автоматически завершается, в Timeline это отражается лишь тем, что
уже породила закрывшая его сущность (`LabResult`/`Procedure`) — отдельного события "план
выполнен" не создаётся.

# 3. Tool: medical.planned_actions

## Когда использовать

- построить список напоминаний на ближайшие N дней;
- ответить на "что мне нужно сделать?" структурированным списком (для диалогового ответа с
  анализом того же вопроса используйте `medical.ask` — он использует те же данные через свой
  Knowledge Provider, см. `../architecture/03-knowledge-providers.md`).

## Параметры

| Поле | Тип | Обязательно | Описание |
|------|-----|-------------|----------|
| `userId` | string | ✅ | Идентификатор пользователя |
| `subjectId` | string | ❌ | Чей план получить, если не свой — см. `01-overview.md` §11 |
| `includeResolved` | boolean | ❌ | Включить уже `completed`/`declined` пункты. По умолчанию — только `pending` (включая просроченные) |
| `limit` | integer | ❌ | Максимальное количество пунктов |

## Ответ

```json
{
  "actions": [
    {
      "plannedActionId": "plan_01J...",
      "type": "lab_test",
      "description": "Повторный анализ глюкозы крови",
      "dueDateFrom": "2026-01-19",
      "dueDateTo": "2026-03-19",
      "overdue": false,
      "status": "pending",
      "sourceType": "document",
      "sourceId": "doc_01J..."
    }
  ]
}
```

`dueDateFrom`/`dueDateTo` отсутствуют, если в исходном тексте не было указано время — такой пункт
всегда присутствует в выдаче и никогда не `overdue`. `matchedDocumentId`/`matchedAt` присутствуют
только при `status: completed`.

## Overdue

`overdue: true` означает `status == pending` и `dueDateTo` уже в прошлом. Это вычисляемое поле, не
хранимый статус — единственное место, где оно считается, это `PlannedAction.Overdue`
(`../domain/14-planned-action.md` §4), чтобы этот tool, `medical-dev planned-actions` и Knowledge
Provider не разошлись в определении.

## Автозавершение

`status` переходит в `completed` **автоматически**, без явного вызова какого-либо tool'а: когда
позже обрабатывается документ, чьи данные (например `LabResult` с тем же показателем) удовлетворяют
ещё не выполненному пункту плана, он помечается выполненным с обратной ссылкой на закрывший его
документ. Подробности алгоритма и его ограничения — `../domain/14-planned-action.md` §4.

Пример: пункт "Повторный анализ глюкозы через полгода" (создан из документа A от 2026-01-19) станет
`completed`, как только будет загружен документ B с результатом анализа на глюкозу — без какого-либо
дополнительного действия со стороны Miranda или пользователя.

Для фактов, о которых сервис никогда не узнает из документа (пользователь сам сделал прививку и не
принёс сертификат), есть ручная альтернатива — `medical.complete_planned_action` (§5).

# 4. Tool: medical.decline_planned_action

Отменяет один из текущих `pending` пунктов плана пользователя — по тому, что сказал пользователь
("отмени прививку от бешенства"), а не по `plannedActionId`: Miranda передаёт текст ровно так, как
его произнёс пользователь, сервис сам находит подходящий пункт (одним небольшим Structured
LLM-вызовом над коротким списком текущих `pending`-пунктов, см. `internal/decline`) — тот же
принцип, что и у `medical.log_event` (`07-events.md` §3).

## Параметры

| Поле | Тип | Обязательно | Описание |
|------|-----|-------------|----------|
| `userId` | string | ✅ | Идентификатор пользователя |
| `text` | string | ✅ | Что сказал пользователь, на естественном языке — не `plannedActionId` |

`decline_planned_action` не поддерживает `subjectId` — как и `log_event`/`delete_event`, действует
только от имени `userId`, никогда не над данными другого пользователя, даже расшарившего доступ на
чтение (см. `01-overview.md` §11: совместный доступ даёт только чтение).

## Ответ

```json
{
  "plannedActionId": "plan_01J...",
  "description": "Прививка от бешенства",
  "status": "declined"
}
```

## Возможные ошибки

| Код | Описание |
|------|----------|
| `PLANNED_ACTION_NOT_FOUND` | Нет ни одного `pending`-пункта плана у пользователя, либо ни один из текущих не соответствует уверенно тексту `text`. Сообщение перечисляет текущие `pending`-описания, чтобы Miranda могла переспросить пользователя, какой именно пункт он имел в виду, вместо тихого no-op. |
| `USER_NOT_FOUND` | Неизвестный пользователь |
| `INVALID_EVENT` | Пустой `text` |
| `STORAGE_ERROR` | Ошибка хранения |

## Чего нет в этом tool'е

Нет `plannedActionId`-based варианта отмены — Miranda никогда не должна сама разбирать текст
пользователя на составляющие (тот же принцип, что и у `medical.log_event`), только передавать его
как есть.

# 5. Tool: medical.complete_planned_action

Отмечает один из текущих `pending` пунктов плана пользователя выполненным по его собственному
сообщению в диалоге ("я сделал прививку от бешенства") — ручная альтернатива автозавершению (§3)
для случая, который оно не покрывает: self-reported факт не производит `LabResult`/`Procedure` и
потому не закрывает пункт плана сам (`../domain/14-planned-action.md` §4). Сопоставление текста с
пунктом плана устроено идентично `medical.decline_planned_action` (§4) — тот же
`internal/decline`, тот же принцип "текст на входе, сервис сам находит пункт".

## Параметры

| Поле | Тип | Обязательно | Описание |
|------|-----|-------------|----------|
| `userId` | string | ✅ | Идентификатор пользователя |
| `text` | string | ✅ | Что сказал пользователь, на естественном языке — не `plannedActionId` |

Как и `decline_planned_action`, не поддерживает `subjectId` — действует только от имени `userId`
(см. `01-overview.md` §11).

## Ответ

```json
{
  "plannedActionId": "plan_01J...",
  "description": "Прививка от бешенства",
  "status": "completed"
}
```

Помечает пункт `completed` с `matchedAt`, равным моменту вызова, но **без** `matchedDocumentId`/
`matchedEntityId` — в отличие от автозавершения (§3), здесь нет закрывшего документа/сущности,
только подтверждение пользователя.

## Возможные ошибки

| Код | Описание |
|------|----------|
| `PLANNED_ACTION_NOT_FOUND` | Нет ни одного `pending`-пункта плана у пользователя, либо ни один из текущих не соответствует уверенно тексту `text`. Сообщение перечисляет текущие `pending`-описания, чтобы Miranda могла переспросить пользователя, какой именно пункт он имел в виду, вместо тихого no-op. |
| `USER_NOT_FOUND` | Неизвестный пользователь |
| `INVALID_EVENT` | Пустой `text` |
| `STORAGE_ERROR` | Ошибка хранения |

## Чего нет в этом tool'е

Нет `plannedActionId`-based варианта — тот же принцип, что и у `decline_planned_action` выше.
Не создаёт и не изменяет `LabResult`/`Procedure` — только меняет `status` самого пункта плана;
если позже всё же будет загружен подтверждающий документ, автозавершение его уже не тронет (пункт
больше не `pending`).

# 6. Ограничения

- Не выполняет медицинский анализ — решение о том, действительно ли нужно повторить анализ,
  остаётся за врачом/пользователем; медкарта только фиксирует то, что уже сказано в документе или
  пользователем.
- Нет собственных напоминаний/уведомлений — это зона ответственности Miranda.
- Дедупликация одинаковых рекомендаций из разных документов (`../adr/005-planned-action-cross-source-dedup.md`)
  срабатывает только со стороны загрузки документа (`ReplaceForSource`) — если пользователь сначала
  произносит рекомендацию в диалоге (`medical.log_event`), а потом загружает документ с тем же
  содержанием, дубль не создастся; обратный порядок (документ уже создал пункт плана, а пользователь
  позже говорит то же самое в диалоге) сегодня не проверяется.
