# 1. Назначение

Препараты читаются через `medical.profile` (`05-profile.md`, поле `activeMedications`) и `medical.ask` —
отдельного read-tool для них нет. `medical.complete_medication`, описанный здесь, — единственный
write-путь: пользователь может напрямую подтвердить, что курс завершён ("я закончил принимать курс
антибиотиков"), не дожидаясь нового документа, который бы это подтвердил.

Как и у диагнозов (`09-diagnoses.md` §1) и пунктов плана (`08-planned-actions.md` §1), у этого действия
нет отдельного tool'а для "назначения" препарата — `Medication` создаётся только через
`medical.upload_document`/`medical.reprocess_document` (Extraction, см.
`../architecture/02-processing-pipeline.md`). `medical.complete_medication` — единственное исключение,
где статус меняется вне обработки документа, тот же принцип "текст на входе, сервис сам разбирает", что
и у `medical.decline_planned_action`/`medical.resolve_diagnosis`.

# 2. Tool: medical.complete_medication

Помечает один из текущих активных препаратов пользователя (см. `medical.profile`'s `activeMedications`)
завершённым — по тому, что сказал пользователь ("я закончил принимать курс антибиотиков", "закончил
пить витамины"), а не по `medicationId`: Miranda передаёт текст ровно так, как его произнёс пользователь,
сервис сам находит подходящий препарат (одним небольшим Structured LLM-вызовом над коротким списком
текущих активных препаратов, см. `internal/decline` — тот же матчер, что и у
`medical.decline_planned_action`/`medical.resolve_diagnosis`).

Кандидатами выступают только записи из текущего, агрегированного `Medication Resolver`'ом набора
(`../domain/06-medication.md` §3) — устаревшая `active`-запись, которую более поздний документ уже
отменил, никогда не предлагается.

## Параметры

| Поле | Тип | Обязательно | Описание |
|------|-----|-------------|----------|
| `userId` | string | ✅ | Идентификатор пользователя |
| `text` | string | ✅ | Что сказал пользователь, на естественном языке — не `medicationId` |

`complete_medication` не поддерживает `subjectId` — как и `log_event`/`resolve_diagnosis`, действует
только от имени `userId`, никогда не над данными другого пользователя, даже расшарившего доступ на
чтение (см. `01-overview.md` §11: совместный доступ даёт только чтение).

## Ответ

```json
{
  "medicationId": "med_01J...",
  "drugName": "Амоксициллин",
  "status": "completed",
  "endedAt": "2026-08-22"
}
```

`endedAt` — момент вызова этого tool'а, а не дата из документа. `status` всегда становится `completed`
независимо от того, был ли препарат отменён врачом или курс пройден полностью — этот tool не различает
эти два случая (см. §"Чего нет в этом tool'е"). Провенанс ("статус изменён документом или пользователем")
хранится не в `status`, а отдельно, в `confirmedEndedAt` (`../domain/06-medication.md` §3.1) — не
возвращается в ответе, так как MCP API не раскрывает эту деталь наружу.

## Возможные ошибки

| Код | Описание |
|------|----------|
| `MEDICATION_NOT_FOUND` | У пользователя нет ни одного активного препарата, либо ни один из текущих не соответствует уверенно тексту `text`. Сообщение перечисляет текущие названия, чтобы Miranda могла переспросить пользователя, какой именно препарат он имел в виду, вместо тихого no-op. |
| `USER_NOT_FOUND` | Неизвестный пользователь |
| `INVALID_EVENT` | Пустой `text` |
| `STORAGE_ERROR` | Ошибка хранения |

## Чего нет в этом tool'е

Нет `medicationId`-based варианта — Miranda никогда не должна сама разбирать текст пользователя на
составляющие (тот же принцип, что и у `medical.log_event`/`medical.resolve_diagnosis`), только передавать
его как есть. Нет способа отличить "курс пройден по плану" от "отменён/брошен" — оба случая переводят
`status` в `completed`; более тонкое разделение, если понадобится, проектируется отдельно. Нет способа
вернуть завершённый курс обратно в `active` через этот tool.
