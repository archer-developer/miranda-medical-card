# 1. Назначение

Препараты читаются через `medical.profile` (`05-profile.md`, поле `activeMedications`) и `medical.ask` —
отдельного read-tool для них нет. Два tool'а, описанные здесь, — единственные write-пути, каждый двигает
`Medication.status` на один шаг вперёд по его жизненному циклу `prescribed → active → completed`
(`../domain/06-medication.md` §3):

- `medical.start_medication` — пользователь подтверждает, что фактически начал принимать препарат,
  который до этого был только назначен ("я начал принимать антибиотик").
- `medical.complete_medication` — пользователь подтверждает, что курс завершён ("я закончил принимать
  курс антибиотиков").

Как и у диагнозов (`09-diagnoses.md` §1) и пунктов плана (`08-planned-actions.md` §1), у этих действий
нет отдельного tool'а для "назначения" препарата — `Medication` создаётся только через
`medical.upload_document`/`medical.reprocess_document` (Extraction, см.
`../architecture/02-processing-pipeline.md`), всегда начиная со статуса `prescribed`, если сам документ
не подтверждает, что приём уже начат. Оба tool'а — исключение, где статус меняется вне обработки
документа, тот же принцип "текст на входе, сервис сам разбирает", что и у
`medical.decline_planned_action`/`medical.resolve_diagnosis`.

# 2. Tool: medical.start_medication

Помечает один из назначенных, но ещё не начатых препаратов пользователя как начатый — по тому, что
сказал пользователь ("я начал принимать антибиотик", "начал пить витамины со вчерашнего дня"), а не по
`medicationId`: Miranda передаёт текст ровно так, как его произнёс пользователь, сервис сам находит
подходящий препарат (одним небольшим Structured LLM-вызовом над коротким списком текущих назначенных
препаратов, см. `internal/decline` — тот же матчер, что и у остальных tool'ов этого семейства).

Кандидатами выступают только записи со статусом `prescribed` из текущего, агрегированного
`Medication Resolver`'ом набора (`../domain/06-medication.md` §3) — устаревшая `prescribed`-запись,
которую более поздний документ уже перевёл дальше по жизненному циклу, никогда не предлагается.

## Параметры

| Поле | Тип | Обязательно | Описание |
|------|-----|-------------|----------|
| `userId` | string | ✅ | Идентификатор пользователя |
| `text` | string | ✅ | Что сказал пользователь, на естественном языке — не `medicationId` |

`start_medication` не поддерживает `subjectId` — как и `log_event`/`complete_medication`, действует
только от имени `userId`, никогда не над данными другого пользователя, даже расшарившего доступ на
чтение (см. `01-overview.md` §11: совместный доступ даёт только чтение).

## Ответ

```json
{
  "medicationId": "med_01J...",
  "drugName": "Амоксициллин",
  "status": "active",
  "startedAt": "2026-08-22"
}
```

`startedAt` — момент вызова этого tool'а, а не дата назначения из документа: весь смысл этого tool'а в
том, что фактическая дата начала приёма может не совпадать с тем, что успел зафиксировать документ.

## Возможные ошибки

| Код | Описание |
|------|----------|
| `MEDICATION_NOT_FOUND` | У пользователя нет ни одного назначенного (`prescribed`), но ещё не начатого препарата, либо ни один из текущих не соответствует уверенно тексту `text`. Сообщение перечисляет текущие названия, чтобы Miranda могла переспросить пользователя, какой именно препарат он имел в виду, вместо тихого no-op. |
| `USER_NOT_FOUND` | Неизвестный пользователь |
| `INVALID_EVENT` | Пустой `text` |
| `STORAGE_ERROR` | Ошибка хранения |

# 3. Tool: medical.complete_medication

Помечает один из текущих активных препаратов пользователя (см. `medical.profile`'s `activeMedications`)
завершённым — по тому, что сказал пользователь ("я закончил принимать курс антибиотиков", "закончил
пить витамины"), а не по `medicationId`, тем же принципом, что и `medical.start_medication`.

Кандидатами выступают только записи со статусом `active` из текущего, агрегированного
`Medication Resolver`'ом набора (`../domain/06-medication.md` §3) — устаревшая `active`-запись, которую
более поздний документ уже отменил, никогда не предлагается.

## Параметры

| Поле | Тип | Обязательно | Описание |
|------|-----|-------------|----------|
| `userId` | string | ✅ | Идентификатор пользователя |
| `text` | string | ✅ | Что сказал пользователь, на естественном языке — не `medicationId` |

`complete_medication` не поддерживает `subjectId` — та же причина, что и у `start_medication`.

## Ответ

```json
{
  "medicationId": "med_01J...",
  "drugName": "Амоксициллин",
  "status": "completed",
  "endedAt": "2026-08-22"
}
```

`endedAt` — момент вызова этого tool'а, а не дата из документа. `status` всегда становится `completed`
независимо от того, был ли препарат отменён врачом или курс пройден полностью — этот tool не различает
эти два случая (см. §"Чего нет в этих tool'ах").

## Возможные ошибки

| Код | Описание |
|------|----------|
| `MEDICATION_NOT_FOUND` | У пользователя нет ни одного активного препарата, либо ни один из текущих не соответствует уверенно тексту `text`. |
| `USER_NOT_FOUND` | Неизвестный пользователь |
| `INVALID_EVENT` | Пустой `text` |
| `STORAGE_ERROR` | Ошибка хранения |

# 4. Чего нет в этих tool'ах

Нет `medicationId`-based варианта ни у одного из них — Miranda никогда не должна сама разбирать текст
пользователя на составляющие (тот же принцип, что и у `medical.log_event`/`medical.resolve_diagnosis`),
только передавать его как есть.

Нет способа отличить "курс пройден по плану" от "отменён/брошен" — оба случая `medical.complete_medication`
переводит в один и тот же `completed`; более тонкое разделение, если понадобится, проектируется отдельно.

Нет пути назад: ни `medical.start_medication`, ни `medical.complete_medication` не умеют откатить статус
на шаг раньше (например, если пользователь передумал/ошибся) — такая ручная коррекция, если понадобится,
проектируется отдельно.
