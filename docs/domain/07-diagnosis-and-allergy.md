# 1. Назначение

Обе сущности представляют относительно статичные факты о состоянии пользователя, извлечённые из документа: установленный диагноз и известная аллергическая реакция. Сгруппированы в один документ из-за схожей формы (код/название + статус/дата), не из-за смыслового родства.

# 2. Diagnosis

## Поля

| Поле | Тип | Обязательно | Описание |
|------|-----|-------------|----------|
| `id` | string (`dx_...`) | ✅ | Идентификатор. |
| `userId` | string | ✅ | Владелец. |
| `documentId` | string | ✅ | Документ-источник. |
| `code` | `MedicalCode` (VO, см. `11-value-objects.md` §10) | ❌ | Код диагноза (ICD-10 и т.п.), если распознан. Отсутствие кода не блокирует создание сущности — см. `../architecture/02-processing-pipeline.md` §16 "автоматическое определение ICD-10" как будущее расширение. |
| `name` | string | ✅ | Название диагноза как в документе. |
| `diagnosedAt` | date | ❌ | Дата постановки. |
| `status` | enum (`suspected`, `active`, `chronic`, `resolved`) | ✅ | См. "Определение `status`" ниже. |
| `notes` | text | ❌ | Дополнительный контекст из документа. |
| `expectedResolutionFrom`, `expectedResolutionTo` | date, date | ❌ | Оценочный диапазон даты разрешения — только для `status = active`. См. ниже. |
| `statusReasoning` | text | ❌ | Объяснение модели, почему выбран этот `status`/`expectedResolution*`. Не клинический факт — см. ниже. |

## Определение `status`

Значение берётся из того, что сказано **в этом документе**, без сопоставления с другими документами. Дословная формула
вида "диагноз установлен"/"диагноз снят" на практике почти никогда не встречается — подавляющее большинство реальных
документов формулирует диагноз как факт под заголовком "Диагноз:"/"Заключение:" или в таблице МКБ-10, без единого
явного маркера статуса. Поэтому, в отличие от `Medication.status` (см. `06-medication.md` §3), `status` — не поиск
конкретной фразы, а суждение модели по **всему тексту документа целиком** (не только по предложению, где назван сам
диагноз):

- диагноз указан как факт документа (под "Диагноз:"/"Заключение:", в таблице МКБ-10 и т.п.) и ничто иное в документе
  не указывает на другой статус → `active` — значение по умолчанию для сформулированного диагноза;
- где-то ещё в этом же документе (например, в разделе "Манипуляция/операция"/"Лечение") указано, что именно эта
  находка уже устранена в рамках этого визита → `resolved`, даже без отдельной фразы "диагноз снят" — например,
  диагноз "Серная пробка" + отдельно "Выполнено удаление серной пробки" → `resolved` именно для этого диагноза, не для
  остальных из того же списка;
- само название диагноза содержит квалифицирующее слово ("хронический" и т.п.) — учитывается, даже если рядом нет
  отдельной уточняющей фразы → `chronic`;
- "предполагаемый диагноз"/"под вопросом"/"?" → `suspected`;
- `status` не проставляется только если текст вообще не утверждает, что это актуальный диагноз пациента (например,
  диагноз упомянут исключительно как семейный анамнез, а не находка этого документа).

Агрегация "актуальные диагнозы на сегодня" — задача `Diagnosis Resolver` при пересборке `MedicalProfile` (см. `05-medical-profile.md`), не поле самой сущности.

## `expectedResolutionFrom`/`expectedResolutionTo`

Оценочный диапазон даты, к которой диагноз со `status = active` ожидаемо разрешится — например, "ОРВИ" даёт диапазон
примерно 7–14 дней. Всегда пусто для `chronic` (у хронического состояния нет ожидаемого разрешения), `suspected` и
`resolved`, и для `active`-диагнозов, для которых нет разумной оценки.

Это единственное поле `Diagnosis` (вместе с самим `status`), для которого источником осознанно является **общее
медицинское знание о типичном течении состояния, а не текст документа** — во всём остальном Extraction обязана
опираться только на то, что буквально написано (см. `internal/extraction/extraction.go`'s `Prompt`). Технически это
устроено так же, как `PlannedAction.dueAmountMin/Max/dueUnit` (`14-planned-action.md`, `docs/adr/004-planned-actions.md`
"Диапазон дат, а не точечная дата"): LLM выдаёт относительный диапазон (число + единица) от даты постановки диагноза,
а не абсолютную дату — конкретная дата вычисляется детерминированно в `internal/normalization` (`ComputeDueDateRange`,
переиспользуется тот же код, что и для `PlannedAction`), заякоренная на `diagnosedAt`, либо на дату документа, если
`diagnosedAt` не указана.

Поскольку это оценка, а не факт из документа, `medical.ask` обязан явно помечать её как оценочную, а не как
задокументированный факт (см. `internal/ask/providers.go`'s `DiagnosisProvider`).

## `statusReasoning` — отдельное поле, не часть `notes`

Extraction дополнительно просит модель коротко объяснить, почему выбран именно такой `status` (и, если задан,
`expectedResolutionAmount*`). Значение доходит до домена и хранится в БД, но в **своей собственной колонке**, не
внутри `Diagnosis.notes` — `notes` это контекст из документа для пользователя/агента, а причина выбора статуса
моделью — техническая информация для анализа качества экстракции, а не клинический факт. Держать их раздельно, а не
дописывать одно в другое, даёт возможность в любой момент явно проверить обоснование статуса по каждому диагнозу
(прямым запросом к `diagnoses`, а не парсингом `extraction_records.raw`), не рискуя тем, что оно попадёт в контекст
`medical.ask` вперемешку с настоящими клиническими заметками. `internal/ask/providers.go`'s `DiagnosisProvider`
намеренно не включает `statusReasoning` в то, что видит агент — это поле для человека, проверяющего работу
экстракции, не для ответа пациенту.

## Timeline

Порождает `TimelineEvent{type: "diagnosis"}` с датой `diagnosedAt`.

# 3. Allergy

## Поля

| Поле | Тип | Обязательно | Описание |
|------|-----|-------------|----------|
| `id` | string (`allergy_...`) | ✅ | Идентификатор. |
| `userId` | string | ✅ | Владелец. |
| `documentId` | string | ✅ | Документ-источник. |
| `substance` | string | ✅ | Вещество/препарат, вызывающий реакцию. |
| `reaction` | string | ❌ | Описание реакции (например `Rash`). |
| `severity` | enum (`mild`, `moderate`, `severe`) | ❌ | Если указана в документе. |
| `notedAt` | date | ❌ | Дата, когда аллергия зафиксирована (не обязательно дата первой реакции). |

## Особенность: нет explicit-статуса

В отличие от `Medication`/`Diagnosis`, `Allergy` не имеет поля `status` — аллергии в модели считаются действующими бессрочно с момента фиксации, если более поздний документ явно не указывает на её опровержение (что на практике редкость и в v1 не обрабатывается отдельно). `MedicalProfile.allergies` включает все известные записи без фильтрации.

## Timeline

Не порождает отдельного типа `TimelineEvent` в базовом перечне `../mcp/06-timeline.md` §6 — фиксация аллергии отражается через `TimelineEvent{type: "document"}`, ссылающийся на документ, где она впервые упомянута.

# 4. Общие инварианты

- Обе сущности принадлежат ровно одному документу; повторная обработка документа полностью заменяет набор `Diagnosis`/`Allergy` для этого `documentId` (документ-скоуп replace).
- `Diagnosis.name` и `Allergy.substance` обязательны даже при отсутствии кода/дополнительных полей — минимальный факт, который Extraction обязан извлечь.
