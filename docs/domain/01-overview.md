# Domain Model

> **Статус:** Draft
>
> **Раздел:** Domain
>
> **Версия:** 1.0

---

# 1. Назначение

Domain Layer описывает бизнес-модель Medical Service.

Он не зависит от:

- SQLite;
- LLM;
- Embeddings;
- OCR;
- MCP;
- CLI;
- Processing Pipeline.

Домен содержит исключительно медицинские сущности и бизнес-правила.

---

# 2. Архитектурные принципы

Domain Layer является единственным источником бизнес-логики.

Все остальные слои работают через него.

```text
MCP

↓

Application

↓

Domain

↓

Repository
```

Ни один внешний компонент не работает напрямую с SQLite.

---

# 3. Aggregate Root

В центре модели находится пользователь.

```text
User

├── Documents

├── Timeline

├── Medical Profile

├── Medications

├── Diagnoses

├── Procedures

├── Lab Results

├── Instrumental Findings

├── Files

├── Self-Reported Events

└── Medication Intakes
```

Все данные принадлежат конкретному пользователю.

---

# 4. Основные сущности

## User

Представляет пользователя Medical Service.

Хранит:

- UserID
- имя
- дополнительные метаданные
- список пользователей, которым разрешён доступ на чтение к его данным (`shared_with`)
- флаг шифрования данных (`encryption`) — взаимоисключающ с непустым `shared_with`, см. `../architecture/06-storage.md` §14

Пользователи загружаются из конфигурационного файла и являются неизменяемыми во время работы сервиса.

---

## MedicalDocument

Представляет импортированный медицинский документ.

Документ является источником знаний.

Он содержит:

- ссылку на исходный файл;
- метаданные;
- распознанный текст;
- Summary;
- извлечённые медицинские сущности.

Документ никогда не изменяется вручную после успешного импорта.

---

## File

Представляет бинарный файл.

Содержит только информацию, необходимую для доступа к оригинальному содержимому.

Не содержит медицинской логики.

---

## Timeline

Материализованное представление истории болезни.

Содержит последовательность Timeline Events.

Не является источником истины.

---

## Timeline Event

Представляет одно медицинское событие.

Например:

- анализ;
- операция;
- назначение препарата;
- постановка диагноза.

Все события имеют дату возникновения и могут ссылаться на документ-источник.

---

## Medical Profile

Агрегированное текущее состояние здоровья пользователя.

Содержит только актуальную информацию.

Автоматически перестраивается после изменения медицинских данных.

Не редактируется вручную.

---

## Medication

Представляет назначение лекарственного препарата.

Содержит информацию о:

- препарате;
- дозировке;
- периоде применения;
- статусе назначения.

---

## Diagnosis

Представляет установленный диагноз.

Может содержать:

- код;
- название;
- дату постановки;
- статус.

---

## Procedure

Представляет медицинскую процедуру.

Например:

- операция;
- вакцинация;
- обследование.

---

## Lab Result

Представляет результат лабораторного исследования.

Содержит:

- показатель;
- значение;
- единицу измерения;
- референсные значения;
- дату исследования.

---

## Vital Sign

Представляет показатель жизнедеятельности.

Например:

- давление;
- рост;
- вес;
- пульс;
- температура.

---

## Allergy

Известная аллергическая реакция пользователя.

---

## Medical Knowledge

Представляет структурированные знания, извлечённые из документа.

Является промежуточной сущностью между Processing Pipeline и Knowledge Providers.

Knowledge не предназначен для прямого использования через MCP.

---

## Embedding

Представляет векторное представление части медицинских знаний.

Используется исключительно Search Engine.

Не содержит бизнес-логики.

---

## Self-Reported Event

Медицинский факт, зафиксированный пользователем напрямую через диалог с Miranda, без исходного документа (например "приступ головной боли").

Второй, помимо документа, вид первичного источника — исходный текст неизменяем так же, как оригинальный файл.

---

## Medication Intake

Факт однократного приёма лекарства. Не то же самое, что `Medication` — не имеет статуса и не описывает курс лечения, только момент и вещество.

---

## Instrumental Finding

Один измеренный или описанный параметр из инструментального исследования (УЗИ, МРТ, КТ, ЭКГ и т.п.) — размер органа, эхогенность, толщина стенки. Параллельна `Lab Result`, но для инструментальных, а не лабораторных методов; часто не числовая (описательные находки тоже трендятся).

---

# 5. Value Objects

В доменной модели рекомендуется использовать Value Objects вместо примитивных типов.

Например:

- BloodPressure
- Dosage
- LabValue
- DateRange
- MedicationStatus
- DocumentType
- TimelineEventType
- MedicalCode

Это позволяет инкапсулировать бизнес-правила внутри модели.

---

# 6. Repository

Каждая Aggregate Root имеет собственный Repository.

Например:

- UserRepository
- DocumentRepository
- TimelineRepository
- ProfileRepository

Repository скрывает детали хранения данных.

Domain не знает о SQLite.

---

# 7. Domain Services

Сложная бизнес-логика должна располагаться в Domain Services.

Например:

- Timeline Builder
- Profile Builder
- Medication Resolver
- Diagnosis Resolver

`Medication Resolver` и `Diagnosis Resolver` вычисляют связность между документами (например, "это тот же курс лечения") на лету — группировкой сущностей по канонизированному названию/коду при каждой пересборке Profile, а не чтением заранее сохранённых связей. Normalization намеренно не создаёт постоянных связей между сущностями разных документов — см. `../architecture/02-processing-pipeline.md` §6.

Domain Services не используют LLM.

---

# 8. Application Services

Application Layer координирует работу Domain.

Например:

```
Upload Document

↓

Pipeline

↓

Repositories

↓

Timeline Builder

↓

Profile Builder
```

---

# 9. Knowledge Providers

Knowledge Providers не являются частью Domain Layer.

Они относятся к Application Layer.

Их задача — собрать необходимые доменные объекты и подготовить структурированный контекст для LLM.

Knowledge Providers работают исключительно через Domain Services и Repository.

---

# 10. Search

Search Engine также не входит в Domain.

Search предоставляет сервис поиска.

Domain не знает:

- как построены Embeddings;
- как работает FTS;
- какая модель используется.

---

# 11. LLM

LLM полностью находится за пределами Domain.

Domain никогда не вызывает LLM.

Взаимодействие с моделью осуществляется только через Application Layer.

---

# 12. Главный принцип

Domain отвечает только на один вопрос:

> **"Как устроена медицинская информация?"**

Он никогда не отвечает на вопросы:

- как она хранится;
- как индексируется;
- как ищется;
- как анализируется LLM;
- как отображается через MCP.

Это делает доменную модель простой, независимой и устойчивой к изменениям инфраструктуры.
