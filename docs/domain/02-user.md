# 1. Назначение

User — корневая сущность (Aggregate Root) доменной модели. Все остальные сущности принадлежат конкретному пользователю и существуют только в его контексте.

User не создаётся и не изменяется через MCP или во время работы сервиса — он полностью определяется статической конфигурацией (см. `../architecture/01-overview.md` §4).

---

# 2. Поля

| Поле | Тип | Обязательно | Описание |
|------|-----|-------------|----------|
| `id` | string | ✅ | Уникальный идентификатор пользователя внутри сервиса (например `alex`). Используется как значение параметра `userId` во всех MCP Tools. |
| `displayName` | string | ✅ | Отображаемое имя. |
| `birthDate` | date | ❌ | Дата рождения. Используется для расчёта возраста в Medical Profile и для возрастных референсных диапазонов Lab Result. |
| `sex` | enum (`male`, `female`) | ❌ | Используется для референсных диапазонов, специфичных по полу. |
| `sharedWith` | string[] | ❌ | Список `id` других пользователей, которым разрешено **читать** данные этого пользователя. Пусто по умолчанию — данные видны только владельцу. См. §4. |
| `encryption` | bool | ❌ | Включает шифрование данных этого пользователя (см. `../architecture/06-storage.md` §14). По умолчанию `false`. |

---

# 3. Источник данных

User не хранится в SQLite.

Источник истины — статический YAML-файл, загружаемый в память при старте сервиса (см. `../architecture/01-overview.md` §4).

Это делает User единственной сущностью домена, не имеющей собственного Repository поверх SQLite — `UserRepository` в данном случае оборачивает in-memory конфигурацию, а не таблицу.

---

# 4. Совместный доступ (`sharedWith`)

`sharedWith` — это allowlist на чтение, не более.

## Что разрешает

Пользователь `B`, присутствующий в `A.sharedWith`, может получить данные `A` через MCP Tools, поддерживающие параметр `subjectId` (`medical.ask`, `medical.profile`, `medical.timeline`, `medical.list_documents`) и через Tools, работающие с конкретным ресурсом (`medical.download_file`, `medical.get_document`, включая оригинальный файл по `fileUri` из его ответа) — см. `../mcp/01-overview.md` §11.

## Что не разрешает

- изменение данных `A` пользователем `B` (`medical.upload_document`, `medical.reprocess_document`, `medical.log_event`, `medical.delete_event` не учитывают `sharedWith` — всегда требуют точного совпадения владельца);
- транзитивный доступ (`sharedWith` не образует граф — если `A` разрешил `B`, а `B` разрешил `C`, это не даёт `C` доступа к данным `A`);
- обратный доступ (наличие `B` в `A.sharedWith` не означает, что `A` может читать данные `B`; направление всегда одно).

## Отказ в доступе

Если `subjectId` (или владелец запрашиваемого ресурса) не совпадает с `userId` и не входит в `sharedWith`, сервис отвечает так же, как если бы `subjectId`/ресурс не существовал — см. `../mcp/01-overview.md` §11 и `feedback`-принцип "не раскрывать существование чужих данных".

# 5. Инварианты

- `id` уникален и неизменяем в рамках запущенного процесса сервиса; изменение состава пользователей требует перезапуска сервиса (конфигурация загружается один раз при старте).
- `encryption == true` и непустой `sharedWith` взаимоисключающи — конфигурация с обоими значениями должна быть отклонена при загрузке (см. `../architecture/06-storage.md` §14).
- Каждый вызов, принимающий `userId`/`subjectId`, обязан проверить существование пользователя с этим `id` в конфигурации до выполнения любой операции; иначе — ошибка `USER_NOT_FOUND`.

# 6. Отношения

```text
User (1) ──── (*) MedicalDocument
User (1) ──── (*) File
User (1) ──── (*) TimelineEvent
User (1) ──── (1) MedicalProfile
User (1) ──── (*) Medication
User (1) ──── (*) Diagnosis
User (1) ──── (*) Procedure
User (1) ──── (*) LabResult
User (1) ──── (*) VitalSign
User (1) ──── (*) Allergy
```

Каждая перечисленная сущность обязана хранить `userId` и участвовать в запросах, отфильтрованных по нему — независимо от `sharedWith` (см. `miranda-service-skeleton/CLAUDE.md` §"Multi-tenant / multi-user services").

# 7. Repository

`UserRepository`

```text
FindByID(id string) (User, error)
List() ([]User, error)
```

Только для чтения — User не имеет операций записи через доменный слой.
