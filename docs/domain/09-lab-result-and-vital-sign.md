# 1. Назначение

Обе сущности представляют измеренное значение показателя на определённую дату — лабораторный анализ и показатель жизнедеятельности соответственно. Сгруппированы вместе из-за идентичной формы (показатель + значение + дата).

---

# 2. LabResult

## Поля

| Поле | Тип | Обязательно | Описание |
|------|-----|-------------|----------|
| `id` | string (`lab_...`) | ✅ | Идентификатор. |
| `userId` | string | ✅ | Владелец. |
| `documentId` | string | ✅ | Документ-источник. |
| `indicatorName` | string | ✅ | Название показателя, канонизированное (например `ALT`, `LDL`) — см. `../architecture/02-processing-pipeline.md` §6. |
| `code` | `MedicalCode` (VO, см. `11-value-objects.md` §10) | ❌ | LOINC-код показателя, если распознан. Отсутствие кода не блокирует создание сущности — см. §8 за механизмом распознавания. |
| `value` | `LabValue` (VO) | ✅ | Значение (числовое `value` и/или описательное `qualitativeValue`) + единица измерения + референсный диапазон, см. `11-value-objects.md` §3. |
| `takenAt` | date | ✅ | Дата забора/исследования. |

## Timeline

Порождает `TimelineEvent{type: "lab_result"}`.

# 3. VitalSign

## Поля

| Поле | Тип | Обязательно | Описание |
|------|-----|-------------|----------|
| `id` | string (`vital_...`) | ✅ | Идентификатор. |
| `userId` | string | ✅ | Владелец. |
| `documentId` | string | ✅ | Документ-источник. |
| `type` | enum (`blood_pressure`, `weight`, `height`, `pulse`, `temperature`) | ✅ | Тип показателя. |
| `bloodPressure` | `BloodPressure` (VO) | ❌ | Заполнено только при `type == blood_pressure`. |
| `value` | number | ❌ | Числовое значение для всех типов, кроме `blood_pressure` (там используется `bloodPressure` — систолическое/диастолическое давление не одно число). |
| `unit` | string | ❌ | Единица измерения (`kg`, `cm`, `bpm`, `°C`). |
| `measuredAt` | date | ✅ | Дата измерения. |

## Timeline

Порождает `TimelineEvent{type: "vital_sign"}`.

# 4. Общие инварианты

- Обе сущности принадлежат ровно одному документу; повторная обработка документа полностью заменяет набор `LabResult`/`VitalSign` для этого `documentId`.
- Показатель без числового **и** описательного значения (например "анализ не завершён") не создаёт сущность — Extraction обязан иметь название показателя и хотя бы одно из `value`/`qualitativeValue`, иначе факт не считается извлечённым. Показатель с нечисловым результатом (например группа крови `A(II) Rh+`, результат теста `положительно`/`отрицательно`) создаёт сущность через `qualitativeValue` — тот же принцип, что у `InstrumentalFinding` (`13-instrumental-finding.md` §2), см. `11-value-objects.md` §3.
- `LabValue.referenceRange`, если известен из документа, сохраняется как указано в документе — сервис не подставляет собственные референсные диапазоны в v1 (это отмечено как возможное будущее расширение через LOINC, см. `../architecture/04-search.md` §24).

# 5. "Последнее значение" в Medical Profile

`MedicalProfile.latestLabResults`/`latestVitalSigns` выбирают по одной записи на каждый уникальный `indicatorName`/`type` пользователя — правило агрегации описано в `05-medical-profile.md` §3, не является полем самой сущности.

---

# 6. Repository

`LabResultRepository`, `VitalSignRepository` — та же структура методов, что у `MedicationRepository` (см. `06-medication.md` §6), плюс:

```text
LatestByIndicator(userId string) (map[string]LabResult, error)   // используется ProfileBuilder
LatestByType(userId string) (map[string]VitalSign, error)        // используется ProfileBuilder
HistoryByIndicator(userId, indicatorName string) ([]LabResult, error) // используется Lab Provider, см. ../architecture/04-search.md §7
```

`ListByUser`/`ListByDocument`/`HistoryByIndicator` все возвращают результат в одном и том же порядке —
сначала самые новые (`taken_at DESC`, недатированные записи — последними), намеренно согласованно между
собой: Lab Provider (`../architecture/04-search.md` §7) обрезает результат по `limit`, полагаясь на то,
что "последние N" реально означает последние N, а не какие попало N. Lab Provider также умеет сузить
запрос по диапазону дат (`from`/`to`) или по `documentId` конкретного документа — оба фильтра
применяются поверх уже отсортированного списка, не в самой репозиторной сортировке.

# 7. Нормализация единиц измерения

`LabValue.normalizedValue`/`normalizedUnit` (см. `11-value-objects.md` §3) — размерное (не молярное) приведение к единой единице измерения для одного и того же `indicatorName` одного пользователя, чтобы можно было сравнивать значения из разных лабораторий, использующих разные единицы (например `г/л` vs `г/дл`, `10^9 клеток/л` vs `тыс/мкл`).

## Механизм

- Каноничная единица для пары `(userId, indicatorName)` — единица **первого когда-либо загруженного** значения этого показателя у этого пользователя ("первый увиденный побеждает"), а не заранее заданная "правильная" единица.
- Само приведение — чисто арифметическое умножение на известный коэффициент, не требует LLM/семантического решения — в отличие от связывания сущностей между документами (сознательно не персистится, см. `../architecture/02-processing-pipeline.md` §6), поэтому это единственное намеренное исключение из "Normalization работает только в рамках одного документа": она читает уже установленную каноничную единицу через `CanonicalUnitResolver`, ничего не решая семантически.
- Молярное приведение (например `ммоль/л` ↔ `мг/дл` для конкретного вещества) сознательно не реализовано — коэффициент зависит от того, какое именно вещество измеряется (молекулярная масса), а для этого сначала нужно решить ту же нерешённую задачу канонизации названий показателей, что и `indicatorName` в целом (см. `../architecture/02-processing-pipeline.md` §6).
- Если пара единиц не описана как эквивалентная, `normalizedValue`/`normalizedUnit` остаются пустыми — сервис не угадывает коэффициент, аналогично тому, как нераспознанная дата остаётся пустой, а не подставляется (см. `../architecture/02-processing-pipeline.md` §5).

## Производные данные, не факт

`normalizedValue`/`normalizedUnit` — **производный, перестраиваемый кэш** (см. `../architecture/06-storage.md` §"Производные данные можно перестроить"), а не независимый факт вроде самого измерения. Практическое следствие: если документ, первым установивший каноничную единицу для показателя, позже удаляется, переобработка оставшихся документов того же пользователя детерминированно (по тем же правилам "первый увиденный") может установить другую каноничную единицу и пересчитать `normalizedValue` для всех остальных записей этого показателя. `value`/`unit` (как в документе) при этом не меняются никогда.

# 8. LOINC-код показателя

`LabResult.code` (см. §2, VO `MedicalCode` — `11-value-objects.md` §10) заполняется одним из двух способов, в порядке приоритета:

1. **Транскрипция.** Если LOINC-код буквально напечатан в тексте документа, Structured Extraction переносит его как есть — тот же принцип, что уже используется для ICD-10 у `Diagnosis` (§2 `07-diagnosis-and-allergy.md`, "код только если явно присутствует в тексте, никогда не выдумывается"). На практике редкость: большинство лабораторий (в частности российские) не печатают LOINC на бланке результата.
2. **Словарь-фолбэк.** Если код не был транскрибирован, Normalization ищет `indicatorName`/сырое название показателя в небольшом вручную заполненном словаре алиасов (`internal/normalization/loinc.go`), сопоставляющем известные написания показателя (`"Гемоглобин"`, `"HGB"`, `"Гемоглобин (HGB)"`) одному LOINC-коду. Тот же принцип роста, что у словаря единиц измерения (`11-value-objects.md` §3, §7 выше) — запись добавляется только когда показатель реально встретился в документе, а не заранее для покрытия.

## Важная оговорка о точности

В отличие от словаря единиц измерения, где коэффициент — проверяемая арифметика, LOINC-код — внешний факт из базы данных LOINC, которую сервис не имеет проверенной копии. Коды в `loinc.go` внесены по общему знанию, без сверки с loinc.org или официальным LOINC-релизом на момент написания. Словарь **не является верифицированным источником** и требует ручной проверки перед тем, как на него можно полагаться за пределами информационной пометки. Это осознанное отступление от общего принципа "не выдумывать" — словарь как код существует, а его вручную вписанные значения ещё нет верификации по авторитетному источнику; см. `internal/normalization/loinc.go` за полным списком и пометкой на каждую запись.

Молярное сопоставление LOINC на основе распознавания вещества по названию (то есть автоматическое расширение словаря через LLM) сознательно не реализовано в этой итерации — см. §7 выше за аналогичным решением для единиц измерения и той же причиной (упирается в нерешённую задачу канонизации названий).
