# 1. Назначение

Knowledge Providers являются центральным архитектурным паттерном интеллектуальных сервисов Miranda.

Основная задача паттерна — разделить ответственность между LLM и кодом приложения.

LLM отвечает исключительно за:

- понимание вопроса пользователя;
- построение плана получения знаний;
- генерацию итогового ответа.

Код отвечает за:

- получение данных;
- поиск;
- фильтрацию;
- агрегацию;
- нормализацию;
- построение контекста.

Такое разделение позволяет использовать сильные стороны LLM, не перекладывая на нее задачи, которые лучше решаются детерминированным кодом.

---

# 2. Почему не RAG

Классическая архитектура Retrieval-Augmented Generation (RAG) строится вокруг поиска текстовых фрагментов.

```text
Question
    │
    ▼
Embedding Search
    │
    ▼
Document Chunks
    │
    ▼
LLM
```

Подобный подход хорошо работает для документации или статей, однако плохо подходит для предметных областей, содержащих большое количество структурированных данных.

Например, вопрос:

> Какие лекарства я принимал одновременно со статинами?

Не требует поиска текстовых фрагментов.

Ответ уже существует в виде структурированных данных.

Использование только Embedding Search в подобных случаях приводит к:

- лишним вычислениям;
- увеличению стоимости;
- снижению точности;
- невозможности использовать связи между сущностями.

Medical Service использует гибридную архитектуру, в которой LLM самостоятельно определяет, какие источники знаний необходимо использовать.

---

# 3. Общая схема

Начиная с `docs/adr/001-internal-agent-loop-implementation.md`, выбор Providers и генерация ответа — не два отдельных вызова LLM, а один открытый диалог (Agent Loop, см. `05-llm.md` §3 "Agent Loop (medical.ask)"): модель сама решает, вызвать ли ещё один Provider, видя результат предыдущего вызова, вместо того чтобы фиксировать план один раз в начале.

```text
                     User Question
                           │
                           ▼
                 ┌─── Agent Loop (LLM) ───┐
                 │                        │
                 │   вызвать инструмент?  │
                 │      да        нет     │
                 │      │          │      │
                 │      ▼          ▼      │
                 │  Provider    Final     │
                 │  (Timeline,  Answer ───┼──▶ Final Answer
                 │   Medication,          │
                 │   Lab, ...)            │
                 │      │                 │
                 │      └─────────────────┘
                 │   (результат — обратно в диалог)
                 └────────────────────────┘
```

---

# 4. Основная идея

LLM никогда не взаимодействует напрямую:

- с SQLite;
- с FTS;
- с Embedding Index;
- с файловым хранилищем;
- с репозиториями.

LLM работает исключительно с абстракцией знаний.

Для модели не существует таблиц, SQL-запросов или индексов.

Существуют только источники знаний.

---

# 5. Жизненный цикл вопроса

Рассмотрим пример.

Пользователь спрашивает:

> Какие лекарства мне назначили после операции на колене?

Последовательность обработки выглядит следующим образом.

```text
Question
    │
    ▼
Agent Loop: вызвать Timeline Provider
    │
    ▼
Agent Loop: видит результат, вызывает Medication Provider
    │
    ▼
Agent Loop: отвечает текстом без нового вызова — Final Answer
    │
    ▼
Response
```

---

# 6. Agent Loop

Модель, ведущая диалог `medical.ask` (см. `05-llm.md` §3), одновременно определяет, какие знания потребуются для ответа, и формирует сам ответ — это не отдельный, изолированный от генерации ответа шаг, а часть одного открытого диалога.

На каждом ходу модель может:

- вызвать один или несколько зарегистрированных Providers (как LLM tool calls) с нужными параметрами;
- увидеть результат вызова и решить, достаточно ли данных, или нужен ещё один Provider (тот же или другой, с другими параметрами);
- ответить обычным текстом без вызова инструмента — этот текст становится финальным ответом.

Модель никогда не выполняет поиск сама и не взаимодействует с хранилищем напрямую (см. §4) — она лишь решает, какой Provider вызвать, а поиск выполняет сам Provider.

---

## Пример

Вопрос:

> Когда у меня впервые повысился ALT?

Модель вызывает инструмент `lab_results` с аргументами:

```json
{
    "indicatorName": "ALT"
}
```

получает историю показателя, при необходимости вызывает `timeline`, чтобы уточнить дату первого события, и только затем отвечает пользователю текстом.

---

# 7. Выбор Providers — часть диалога, а не отдельный план

В прежней архитектуре (Planner как отдельный одноразовый вызов, см. `05-llm.md` §3) выбор Providers фиксировался один раз в начале, в виде Execution Plan, до какого-либо реального обращения к данным.

Сейчас выбор происходит по ходу диалога: модель может обратиться к Provider'у, увидеть результат и на его основании решить, что нужен ещё один — с другими параметрами или к другому источнику. План не существует как отдельная структура данных; последовательность вызовов — это просто история диалога.

Как и раньше, модель **не определяет алгоритм поиска** — она только выбирает подходящие источники знаний и параметры вызова. Как именно будет происходить поиск, решает сам Provider.

---

# 8. Registry

Все Providers регистрируются в едином Registry.

```text
Provider Registry

├── Timeline

├── Self-Reported Events

├── Medication

├── Diagnosis

├── Procedures

├── Planned Actions

├── Lab Results

├── Instrumental Findings

├── Profile

├── Documents

└── Embeddings
```

Agent Loop получает информацию только о зарегистрированных Providers.

При добавлении нового Provider Agent Loop автоматически получает возможность использовать его — без изменения кода Agent Loop самого по себе, только регистрацией нового Provider (см. `cmd/miranda-medical-card/main.go`'s `ask.NewRegistry`).

Это позволяет расширять систему без изменения архитектуры.

---

# 9. Самоописывающиеся Providers

Каждый Provider обязан описывать собственные возможности.

Например:

```yaml
name: medications

description: |
  Предоставляет информацию
  о назначенных лекарствах,
  дозировках,
  курсах лечения,
  истории приема,
  активных препаратах,
  отмененных препаратах
  и причинах назначения.
```

Именно эти описания становятся описанием инструмента (LLM tool), которое модель видит при выборе необходимых источников знаний в Agent Loop.

---

# 10. Интерфейс Provider

Все Providers реализуют единый интерфейс.

Пример:

```go
type KnowledgeProvider interface {

    Metadata() ProviderMetadata

    Collect(ctx context.Context, request KnowledgeRequest) ([]KnowledgeChunk, error)

}
```

Provider самостоятельно принимает решение:

- использовать SQLite;
- использовать FTS;
- использовать Embeddings;
- обратиться к другому сервису;
- объединить несколько источников.

Для модели, ведущей Agent Loop, это полностью прозрачно.

---

# 11. Knowledge Request

Вызывая инструмент, модель передаёт Provider не SQL-запрос и не текст вопроса, а структурированное описание требуемых знаний — аргументы вызова, ограниченные JSON Schema конкретного инструмента (см. `internal/ask/tools.go`).

Например, вызов `lab_results` (см. `internal/ask/tools.go`'s `toolParameters`):

```json
{
    "indicatorName": "ALT",
    "from": "2024-01-01"
}
```

Некоторые Providers также принимают `documentId` — id, который модель уже получила из результата более раннего вызова (`timeline`, `lab_results`, `documents`), чтобы получить все данные именно этого документа/события одним вызовом, вместо перебора параметров вслепую.

Конкретная структура определяется самим Provider — единой универсальной схемы Knowledge Request нет, есть только JSON Schema каждого конкретного инструмента.

---

# 12. Knowledge Chunks

Все Providers возвращают знания в едином формате.

```go
type KnowledgeChunk struct {

    Source string

    Title string

    Content string

    Confidence float64

    Metadata map[string]any

}
```

Chunk представляет собой небольшой законченный фрагмент знаний.

Он должен быть понятен человеку.

---

## Хороший пример

```
Rosuvastatin

Назначен 14 мая 2025

Дозировка 10 мг

Продолжает принимать
```

---

## Плохой пример

```json
{
    "medication_id": "...",
    "dose": 10
}
```

LLM не должна получать внутренние структуры базы данных.

---

# 13. Context Builder

Роль Context Builder изменилась вместе с переходом на Agent Loop (см. `05-llm.md` §3): вместо того чтобы один раз собрать единый Prompt-блок для отдельного вызова Answer Generator, он теперь применяется в двух разных местах.

**По ходу диалога** — каждый вызов инструмента форматируется в текст этого конкретного вызова (см. `internal/ask/format.go`'s `formatToolResult`), а не в общий блок со всеми источниками разом:

```text
- ALT 54.7 (2025-03-14)
- ALT 41.2 (2024-11-02)
```

Такой результат становится содержимым одного сообщения роли `tool` в диалоге — модель видит его и решает, продолжать ли поиск.

**В конце диалога**, когда модель ответила текстом без нового вызова инструмента, — только для формирования итогового списка `sources` в ответе `medical.ask`: все `KnowledgeChunk`, собранные за весь ход диалога, объединяются, дедуплицируются и ранжируются (`RankChunks`) — та же логика дедупликации/ранжирования по Confidence и приоритету Provider, что и раньше, просто больше не служит для построения Prompt.

---

# 14. Финальный ответ

Больше нет отдельного второго вызова LLM (Answer Generator) поверх готового контекста: как только модель в Agent Loop отвечает обычным текстом без нового вызова инструмента, этот текст **и есть** финальный ответ, возвращаемый пользователю без изменений (см. `internal/ask/agent_loop.go`'s `Ask`).

Клинические правила формулировки ответа (обоснованность источниками, разграничение документально подтверждённых и самостоятельно сообщённых фактов) по-прежнему часть системного prompt модели (см. `05-llm.md` §3, `internal/ask/prompt.go`'s `answerRules`), просто больше не являются отдельным вызовом. Сами правила периодически пересматриваются как осознанные продуктовые решения (см. git-историю `answerRules`) — на 2026-08-12 единственное жёсткое ограничение — не рекомендовать конкретные препараты/дозировки/схему лечения; называть вероятный диагноз, объяснять отклонение показателя от нормы и давать общие советы по питанию/образу жизни разрешено, если это обосновано фактами, полученными за этот диалог.

---

# 15. Последовательность вызовов инструментов

В прежней архитектуре Planner мог выбрать несколько Providers за один раз, и они выполнялись параллельно.

Agent Loop устроен иначе: модель запрашивает вызов инструмента (одного или нескольких сразу в один ход) и получает его результат обратно в диалог, прежде чем решить, нужен ли ещё один вызов. Несколько вызовов, запрошенных моделью в один ход, выполняются последовательно (см. `internal/ask/agent_loop.go`'s `Ask`) — это осознанное упрощение: Providers у Medical Service — быстрые операции над SQLite, ограниченные собственным таймаутом (см. §16), поэтому выигрыш от параллельного выполнения нескольких вызовов одного хода незначителен по сравнению с усложнением кода. Если это когда-либо станет узким местом, вызовы одного хода можно распараллелить без изменения внешнего поведения — сама многоходовая природа диалога (несколько последовательных ходов, каждый видит результат предыдущего) при этом не меняется.

---

# 16. Таймауты

Каждый Provider должен иметь собственный таймаут.

Ошибка одного Provider не должна приводить к отказу всего ответа.

Например:

```
Timeline ✓

Medication ✓

Embeddings ✗
```

Ответ все равно может быть сформирован.

---

# 17. Приоритет Providers

Agent Loop может вызвать большое количество Providers за один диалог.

Итоговый список `sources` (§13) может ограничивать объём данных.

Приоритет рекомендуется определять следующим образом.

1. Timeline
2. Medication
3. Lab Results
4. Instrumental Findings
5. Diagnosis
6. Procedures
7. Planned Actions
8. Medical Profile
9. Documents
10. Embeddings

Конкретный порядок может изменяться в зависимости от сервиса.

---

# 18. Почему Provider — это не Repository

Repository работает с хранением данных.

Например:

```
FindMedicationById()
```

или

```
Save()
```

Provider работает со знаниями.

Например:

```
История приема статинов
```

или

```
Последние анализы печени
```

Это принципиально разные уровни абстракции.

Provider может использовать один или несколько Repository внутри себя.

---

# 19. Почему выбор Providers делает LLM

Определение намерения пользователя относится к задачам понимания естественного языка.

Попытка реализовать подобную логику при помощи кода приводит к:

- большому количеству условий;
- сложным правилам;
- плохой масштабируемости;
- низкой точности.

LLM значительно лучше определяет, какие знания потребуются для ответа — причём не только один раз в начале, но и по ходу диалога, когда становится ясно, что первоначально выбранных источников недостаточно (см. §6-7).

Поэтому именно LLM принимает решение о выборе Providers, теперь на каждом ходу Agent Loop, а не один раз в начале диалога.

---

# 20. Расширяемость

Добавление нового Provider должно состоять из следующих шагов.

1. Реализовать интерфейс KnowledgeProvider.
2. Зарегистрировать Provider в Registry.
3. Добавить описание возможностей.

После этого Agent Loop автоматически получает возможность использовать новый источник знаний — как новый инструмент в списке, доступном модели.

Изменение существующего кода Agent Loop не требуется.

---

# 21. Использование в других сервисах

Паттерн Knowledge Providers не зависит от предметной области.

Он может использоваться в:

- Medical Service;
- Nutrition Service;
- Finance Service;
- Smart Home Service;
- Calendar Service;
- Diary Service.

Архитектура остается одинаковой независимо от типа данных.

---

# 22. Архитектурные решения

В основе паттерна лежат следующие принципы.

- LLM отвечает за понимание вопроса, но не за поиск данных.
- Все знания предоставляются через единый интерфейс.
- Provider самостоятельно выбирает оптимальный способ получения данных.
- LLM (Agent Loop) ничего не знает о внутреннем устройстве системы хранения.
- Внешний MCP API остается минимальным и стабильным независимо от роста внутренних возможностей сервиса.

---

# 23. Будущие расширения

Многошаговые вызовы уже реализованы (Agent Loop, §6-7) — далее в следующих версиях паттерна могут быть добавлены:

- зависимости между Providers;
- параллельное выполнение нескольких вызовов инструментов одного хода (см. §15);
- оценка стоимости диалога (число ходов, токены);
- кеширование результатов Agent Loop;
- обучение выбору Providers на истории запросов;
- динамическое подключение Providers;
- распределенные Providers, работающие через MCP или HTTP.

Базовая архитектура при этом останется неизменной.
