# 1. Назначение

Knowledge Providers являются центральным архитектурным паттерном интеллектуальных сервисов Miranda.

Основная задача паттерна — разделить ответственность между LLM и кодом приложения.

LLM отвечает исключительно за:

- понимание вопроса пользователя;
- построение плана получения знаний;
- генерацию итогового ответа.

Код отвечает за:

- получение данных;
- поиск;
- фильтрацию;
- агрегацию;
- нормализацию;
- построение контекста.

Такое разделение позволяет использовать сильные стороны LLM, не перекладывая на нее задачи, которые лучше решаются детерминированным кодом.

---

# 2. Почему не RAG

Классическая архитектура Retrieval-Augmented Generation (RAG) строится вокруг поиска текстовых фрагментов.

```text
Question
    │
    ▼
Embedding Search
    │
    ▼
Document Chunks
    │
    ▼
LLM
```

Подобный подход хорошо работает для документации или статей, однако плохо подходит для предметных областей, содержащих большое количество структурированных данных.

Например, вопрос:

> Какие лекарства я принимал одновременно со статинами?

Не требует поиска текстовых фрагментов.

Ответ уже существует в виде структурированных данных.

Использование только Embedding Search в подобных случаях приводит к:

- лишним вычислениям;
- увеличению стоимости;
- снижению точности;
- невозможности использовать связи между сущностями.

Medical Service использует гибридную архитектуру, в которой LLM самостоятельно определяет, какие источники знаний необходимо использовать.

---

# 3. Общая схема

```text
                     User Question
                           │
                           ▼
                  Planner (LLM)
                           │
                           ▼
                   Execution Plan
                           │
          ┌────────────────┼────────────────┐
          ▼                ▼                ▼
 Timeline Provider   Medication Provider   Lab Provider
          │                │                │
          └────────────────┼────────────────┘
                           ▼
                  Knowledge Chunks
                           │
                           ▼
                   Context Builder
                           │
                           ▼
                 Answer Generator (LLM)
                           │
                           ▼
                     Final Answer
```

---

# 4. Основная идея

LLM никогда не взаимодействует напрямую:

- с SQLite;
- с FTS;
- с Embedding Index;
- с файловым хранилищем;
- с репозиториями.

LLM работает исключительно с абстракцией знаний.

Для модели не существует таблиц, SQL-запросов или индексов.

Существуют только источники знаний.

---

# 5. Жизненный цикл вопроса

Рассмотрим пример.

Пользователь спрашивает:

> Какие лекарства мне назначили после операции на колене?

Последовательность обработки выглядит следующим образом.

```text
Question
    │
    ▼
Planner
    │
    ▼
Execution Plan
    │
    ├── Timeline Provider
    │
    └── Medication Provider
            │
            ▼
     Knowledge Chunks
            │
            ▼
     Context Builder
            │
            ▼
 Answer Generator
            │
            ▼
        Response
```

---

# 6. Planner

Planner представляет собой первый вызов LLM.

Его задача — определить, какие знания потребуются для ответа.

Planner:

- не отвечает пользователю;
- не выполняет поиск;
- не получает медицинские данные;
- не строит выводы.

Он лишь составляет план выполнения.

---

## Пример

Вопрос:

> Когда у меня впервые повысился ALT?

Planner может вернуть следующий план.

```json
{
    "providers": [
        {
            "name": "lab_results",
            "reason": "Необходимо получить историю показателя ALT"
        },
        {
            "name": "timeline",
            "reason": "Необходимо определить первое событие"
        }
    ]
}
```

---

# 7. Execution Plan

Execution Plan описывает последовательность обращения к Providers.

Важно понимать, что Planner **не определяет алгоритм поиска**.

Он только выбирает подходящие источники знаний.

Как именно будет происходить поиск, решает Provider.

---

# 8. Registry

Все Providers регистрируются в едином Registry.

```text
Provider Registry

├── Timeline

├── Medication

├── Diagnosis

├── Procedures

├── Lab Results

├── Documents

└── Embeddings
```

Planner получает информацию только о зарегистрированных Providers.

При добавлении нового Provider Planner автоматически получает возможность использовать его.

Это позволяет расширять систему без изменения архитектуры.

---

# 9. Самоописывающиеся Providers

Каждый Provider обязан описывать собственные возможности.

Например:

```yaml
name: medications

description: |
  Предоставляет информацию
  о назначенных лекарствах,
  дозировках,
  курсах лечения,
  истории приема,
  активных препаратах,
  отмененных препаратах
  и причинах назначения.
```

Именно эти описания используются Planner при выборе необходимых источников знаний.

---

# 10. Интерфейс Provider

Все Providers реализуют единый интерфейс.

Пример:

```go
type KnowledgeProvider interface {

    Metadata() ProviderMetadata

    Collect(ctx context.Context, request KnowledgeRequest) ([]KnowledgeChunk, error)

}
```

Provider самостоятельно принимает решение:

- использовать SQLite;
- использовать FTS;
- использовать Embeddings;
- обратиться к другому сервису;
- объединить несколько источников.

Для Planner это полностью прозрачно.

---

# 11. Knowledge Request

Planner передает Provider не SQL-запрос и не текст вопроса, а структурированное описание требуемых знаний.

Например:

```json
{
    "goal": "MedicationHistory",
    "timeRange": {
        "from": "2024-01-01"
    },
    "filters": {
        "activeOnly": false
    }
}
```

Конкретная структура определяется самим Provider.

---

# 12. Knowledge Chunks

Все Providers возвращают знания в едином формате.

```go
type KnowledgeChunk struct {

    Source string

    Title string

    Content string

    Confidence float64

    Metadata map[string]any

}
```

Chunk представляет собой небольшой законченный фрагмент знаний.

Он должен быть понятен человеку.

---

## Хороший пример

```
Rosuvastatin

Назначен 14 мая 2025

Дозировка 10 мг

Продолжает принимать
```

---

## Плохой пример

```json
{
    "medication_id": "...",
    "dose": 10
}
```

LLM не должна получать внутренние структуры базы данных.

---

# 13. Context Builder

После завершения работы Providers запускается Context Builder.

Его задача:

- объединить результаты;
- удалить дубликаты;
- отсортировать знания;
- ограничить объем контекста;
- сформировать Prompt.

---

## Пример

```text
QUESTION

Когда впервые повысился ALT?

========================

Timeline

...

========================

Lab Results

...

========================

Summary
```

---

# 14. Answer Generator

После построения контекста выполняется второй вызов LLM.

На этом этапе модель уже не принимает архитектурных решений.

Она получает:

- вопрос пользователя;
- готовый контекст.

Ее задача — сформировать понятный и обоснованный ответ.

---

# 15. Параллельное выполнение

Providers не должны зависеть друг от друга.

Если Planner выбрал несколько Providers,

они могут выполняться параллельно.

```text
Planner
    │
    ├────────────┐
    ▼            ▼
Timeline      Medication
    │            │
    └──────┬─────┘
           ▼
 Context Builder
```

Это значительно уменьшает время ответа.

---

# 16. Таймауты

Каждый Provider должен иметь собственный таймаут.

Ошибка одного Provider не должна приводить к отказу всего ответа.

Например:

```
Timeline ✓

Medication ✓

Embeddings ✗
```

Ответ все равно может быть сформирован.

---

# 17. Приоритет Providers

Planner может выбрать большое количество Providers.

Context Builder может ограничивать объем данных.

Приоритет рекомендуется определять следующим образом.

1. Timeline
2. Medication
3. Lab Results
4. Diagnosis
5. Procedures
6. Medical Profile
7. Documents
8. Embeddings

Конкретный порядок может изменяться в зависимости от сервиса.

---

# 18. Почему Provider — это не Repository

Repository работает с хранением данных.

Например:

```
FindMedicationById()
```

или

```
Save()
```

Provider работает со знаниями.

Например:

```
История приема статинов
```

или

```
Последние анализы печени
```

Это принципиально разные уровни абстракции.

Provider может использовать один или несколько Repository внутри себя.

---

# 19. Почему Planner использует LLM

Определение намерения пользователя относится к задачам понимания естественного языка.

Попытка реализовать подобную логику при помощи кода приводит к:

- большому количеству условий;
- сложным правилам;
- плохой масштабируемости;
- низкой точности.

LLM значительно лучше определяет, какие знания потребуются для ответа.

Поэтому именно LLM принимает решение о выборе Providers.

---

# 20. Расширяемость

Добавление нового Provider должно состоять из следующих шагов.

1. Реализовать интерфейс KnowledgeProvider.
2. Зарегистрировать Provider в Registry.
3. Добавить описание возможностей.

После этого Planner автоматически получает возможность использовать новый источник знаний.

Изменение существующего кода Planner не требуется.

---

# 21. Использование в других сервисах

Паттерн Knowledge Providers не зависит от предметной области.

Он может использоваться в:

- Medical Service;
- Nutrition Service;
- Finance Service;
- Smart Home Service;
- Calendar Service;
- Diary Service.

Архитектура остается одинаковой независимо от типа данных.

---

# 22. Архитектурные решения

В основе паттерна лежат следующие принципы.

- LLM отвечает за понимание вопроса, но не за поиск данных.
- Все знания предоставляются через единый интерфейс.
- Provider самостоятельно выбирает оптимальный способ получения данных.
- Planner ничего не знает о внутреннем устройстве системы хранения.
- Внешний MCP API остается минимальным и стабильным независимо от роста внутренних возможностей сервиса.

---

# 23. Будущие расширения

В следующих версиях паттерна могут быть добавлены:

- зависимости между Providers;
- многошаговые планы выполнения;
- оценка стоимости выполнения плана;
- кеширование результатов Planner;
- обучение Planner на истории запросов;
- динамическое подключение Providers;
- распределенные Providers, работающие через MCP или HTTP.

Базовая архитектура при этом останется неизменной.
