# 1. Назначение

Storage Architecture определяет принципы хранения данных Medical Service.

Основной целью является не просто сохранение документов, а построение долговременной базы медицинских знаний, пригодной для поиска, анализа и повторной обработки.

Архитектура хранения должна обеспечивать:

- воспроизводимость обработки;
- независимость от конкретной LLM;
- возможность повторной обработки документов;
- эффективный поиск;
- масштабируемость модели данных;
- минимальную связанность между уровнями хранения.

---

# 2. Основные принципы

## Единственный источник истины

Для каждого типа данных существует только один источник истины.

Например:

| Данные | Источник истины |
|---------|-----------------|
| Оригинальный файл | Artifact |
| Извлеченные факты | Extraction |
| Структурированные знания | Domain Entities |
| Медицинская история | Timeline |
| Актуальное состояние | Medical Profile |

Запрещается хранить одну и ту же информацию одновременно в нескольких независимых местах.

---

## Неизменяемость Artifact

После загрузки Artifact никогда не изменяется.

Разрешается:

- пересчитать хэш;
- проверить целостность;
- повторно обработать.

Запрещается:

- изменять содержимое;
- заменять файл;
- выполнять OCR поверх измененной версии.

---

## Производные данные можно перестроить

Все остальные уровни хранения являются производными.

При необходимости допускается полностью удалить:

- Extraction;
- Timeline;
- Embeddings;
- Summary;
- Domain Entities.

После чего восстановить их повторным запуском Pipeline.

---

## Независимость уровней

Каждый уровень хранения отвечает только за собственную задачу.

Например:

Artifact ничего не знает о Timeline.

Timeline ничего не знает об Embeddings.

Embeddings ничего не знают о Medical Profile.

Это значительно упрощает сопровождение системы.

---

# 3. Общая схема хранения

```text
                Uploaded File
                      │
                      ▼
                 Artifact
                      │
                      ▼
             MedicalDocument
                      │
                      ▼
                Extraction
                      │
         ┌────────────┼────────────┐
         ▼            ▼            ▼
   Domain Entities  Summary   Timeline
         │            │            │
         └────────────┼────────────┘
                      ▼
                Medical Profile
                      │
         ┌────────────┴────────────┐
         ▼                         ▼
      Embeddings                 FTS Index
```

Архитектура представляет собой последовательность уровней абстракции.

Каждый следующий уровень зависит только от предыдущих.

---

# 4. Уровни хранения

## Artifact Layer

Хранит исключительно оригинальные файлы.

Содержит:

- путь к файлу;
- MIME Type;
- SHA256;
- размер;
- дату загрузки.

Artifact не содержит медицинских данных.

---

## Document Layer

Описывает медицинский документ как логическую сущность.

Например:

```
MRI Report

или

Blood Test

или

Hospital Discharge
```

Document связан с Artifact отношением один к одному.

---

## Extraction Layer

Хранит структурированный результат работы LLM.

Extraction является промежуточным представлением.

Он:

- не используется напрямую при поиске;
- не используется при ответах пользователю;
- нужен для повторной нормализации;
- облегчает отладку качества извлечения.

---

## Domain Layer

Содержит структурированные медицинские сущности.

Например:

- Medication
- Diagnosis
- Procedure
- Lab Result
- Allergy
- Vital Sign

Именно этот уровень является основным источником знаний.

---

## Timeline Layer

Timeline хранится отдельно.

Несмотря на то что события могут быть построены на основе Domain Entities, рекомендуется материализовать Timeline в отдельной таблице.

Это значительно ускоряет ответы на вопросы, связанные со временем.

---

## Profile Layer

Medical Profile представляет собой агрегированное текущее состояние пользователя.

Это кэш знаний, построенный на основе всех документов.

Например:

- текущие препараты;
- хронические заболевания;
- аллергии;
- последние показатели.

Profile никогда не редактируется вручную.

---

## Search Layer

Включает:

- FTS Index;
- Embeddings.

Эти данные полностью производные.

Их всегда можно перестроить.

---

# 5. Физическое хранение

Архитектура хранения не зависит от конкретной файловой системы.

Минимально требуется:

```
SQLite

+

Local Files
```

В будущем возможно использование:

- S3;
- MinIO;
- NAS;
- Cloud Storage.

Смена способа хранения файлов не должна влиять на бизнес-логику.

---

# 6. SQLite

SQLite является основной базой данных Medical Service.

Причины выбора:

- отсутствие отдельного сервера;
- высокая производительность;
- простое резервное копирование;
- надежность;
- поддержка WAL;
- поддержка FTS5;
- достаточная производительность для персонального использования.

Архитектура не должна использовать специфические возможности SQLite, которые затруднят возможный переход на другую СУБД.

---

# 7. Хранение файлов

Файлы рекомендуется хранить отдельно от базы данных.

SQLite должна содержать только ссылку на Artifact.

Не рекомендуется хранить бинарные данные в BLOB-полях.

Это упрощает:

- резервное копирование;
- перенос файлов;
- проверку целостности;
- работу с большими PDF.

---

# 8. Версионирование производных данных

Некоторые уровни хранения должны поддерживать версионирование.

Например:

- Extraction;
- Summary;
- Embeddings.

Это позволит:

- сравнивать результаты разных моделей;
- тестировать новые Prompt;
- постепенно мигрировать между версиями.

Для большинства доменных сущностей актуальной считается только последняя успешно построенная версия.

---

# 9. Удаление данных

Удаление должно происходить сверху вниз.

Например:

```
Delete MedicalDocument

↓

Delete Timeline

↓

Delete Domain Entities

↓

Delete Extraction

↓

Delete Summary

↓

Delete Embeddings

↓

Delete FTS

↓

Delete Artifact
```

Такой порядок предотвращает появление "висячих" ссылок.

---

# 10. Повторная обработка

Storage Architecture должна позволять повторный запуск любого этапа.

Например:

```
Artifact

↓

New Prompt

↓

Extraction
```

или

```
Extraction

↓

Normalization
```

или

```
Timeline

↓

Medical Profile
```

Повторная обработка не должна требовать повторной загрузки документа.

---

# 11. Индексы

Каждый уровень хранения самостоятельно определяет необходимые индексы.

Например:

Domain Layer:

- userId;
- documentId;
- date.

Timeline:

- eventDate;
- userId;
- eventType.

Embeddings:

- provider;
- modelVersion.

Конкретная схема описывается в разделе Database.

---

# 12. Кэширование

Storage Layer может использовать кэш для ускорения доступа.

Допускается кэширование:

- Medical Profile;
- Knowledge Chunks;
- результатов FTS;
- результатов Embedding Search.

Не рекомендуется кэшировать содержимое Domain Entities.

SQLite уже обеспечивает высокую скорость доступа.

---

# 13. Резервное копирование

Архитектура должна обеспечивать возможность резервного копирования без остановки сервиса.

Минимальный набор для восстановления:

- SQLite;
- Artifact Storage;
- YAML-конфигурация пользователей.

Все остальные данные могут быть восстановлены повторным запуском Pipeline.

---

# 14. Шифрование

Архитектура хранения не зависит от способа защиты данных.

При необходимости могут использоваться:

- шифрование файловой системы;
- SQLite Encryption Extension (SQLCipher);
- шифрование резервных копий;
- шифрование Object Storage.

Все механизмы должны быть прозрачны для бизнес-логики.

---

# 15. Архитектурные решения

Storage разделяется на два принципиально разных класса данных.

## Первичные данные

Это данные, которые невозможно восстановить автоматически.

К ним относятся:

- Artifact;
- конфигурация пользователей.

Они требуют обязательного резервного копирования.

---

## Производные данные

Это данные, которые можно восстановить повторной обработкой.

К ним относятся:

- Extraction;
- Timeline;
- Summary;
- Medical Profile;
- Embeddings;
- FTS;
- Domain Entities.

При необходимости они могут быть полностью удалены и перестроены.

---

# 16. Будущие расширения

Архитектура хранения должна поддерживать постепенное развитие системы без изменения существующих компонентов.

Возможные направления:

- поддержка нескольких хранилищ файлов;
- хранение DICOM-изображений;
- хранение медицинских изображений в нескольких разрешениях;
- хранение аудиозаписей консультаций;
- автоматическая дедупликация файлов по SHA256;
- архивирование редко используемых документов;
- распределенное хранение между устройствами;
- синхронизация с облачным хранилищем;
- прозрачное шифрование на уровне Storage Layer.

Добавление новых типов хранения не должно влиять на работу Knowledge Providers, Search Engine или LLM Integration.
