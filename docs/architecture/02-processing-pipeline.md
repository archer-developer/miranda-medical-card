# 1. Назначение

Processing Pipeline отвечает за преобразование загруженного пользователем файла в набор структурированных знаний, пригодных для поиска, анализа и использования LLM.

Pipeline является одним из ключевых компонентов Medical Service.

Его задача — один раз обработать документ и извлечь из него максимум полезной информации.

После завершения обработки ответы на большинство вопросов должны строиться без повторного анализа оригинального документа.

---

# 2. Основные принципы

Pipeline проектируется исходя из следующих принципов.

## Неизменяемость исходного файла

После загрузки файл никогда не изменяется.

Любая повторная обработка всегда начинается с оригинального файла.

Это обеспечивает:

- воспроизводимость результатов;
- возможность смены LLM;
- возможность изменения Prompt;
- возможность улучшения алгоритмов нормализации.

---

## Независимость этапов

Каждый этап Pipeline является самостоятельным.

Например можно:

- перестроить Embeddings;
- повторно выполнить Extraction;
- перестроить Timeline;
- перестроить FTS Index.

Без повторного выполнения остальных этапов.

---

## Идемпотентность

Каждый этап Pipeline должен быть идемпотентным.

Повторный запуск не должен приводить к появлению дубликатов.

Например:

```
MedicalDocument

↓

Normalize()

↓

Diagnosis
```

Повторный запуск `Normalize()` должен заменить существующие сущности, а не создать новые.

---

## Синхронная обработка (v1)

На данном этапе Pipeline выполняется синхронно в рамках вызова `medical.upload_document`: инструмент возвращает управление только после завершения всех этапов (см. `../mcp/03-documents.md` §5).

Это осознанное упрощение для первой версии: ожидаемый размер документов не предполагает обработку дольше типичного таймаута MCP-вызова.

Если в будущем это перестанет быть верным (например, из-за больших многостраничных документов), обработку можно вынести в фон без изменения внешнего контракта — `fileId` уже отделён от `documentId` (см. `../mcp/02-files.md`), а статус документа (`PENDING` / `READY` / ...) уже заложен как поле сущности. Переход потребует добавить механизм опроса статуса на уровне MCP API, которого сегодня нет.

# 4. Этапы обработки

## 4.1 Upload

### Вход

Файл пользователя.

Поддерживаемые типы:

- PDF
- JPEG
- PNG
- HEIC
- TIFF
- DICOM (будущая версия)
- DOCX (опционально)

### Действия

Сервис:

- вычисляет SHA256;
- определяет MIME Type;
- сохраняет файл;
- создает Artifact.

### Выход

```
Artifact
```

---

## 4.2 Create MedicalDocument

После создания Artifact создается сущность MedicalDocument.

На данном этапе еще неизвестно содержимое документа.

Заполняются только технические данные.

Например:

- владелец;
- дата загрузки;
- ссылка на Artifact;
- статус обработки.

После этого документ получает статус

```
PENDING
```

---

## 4.3 OCR / Vision

Следующий этап использует Vision-возможности LLM.

В текущей архитектуре предполагается использование Gemini.

На вход модели передается оригинальный документ.

LLM должна:

- прочитать текст;
- определить структуру;
- распознать таблицы;
- извлечь даты;
- определить язык;
- определить тип документа.

Результатом является полный текст документа.

Этот этап является единственным местом,
где используется OCR.

# 5. Structured Extraction

После получения текста выполняется основной этап анализа.

LLM получает инструкцию извлечь максимально возможное количество структурированной информации.

На данном этапе модель **не должна ничего интерпретировать**.

Она должна только извлекать факты.

Например:

```
Документ

↓

LLM

↓

JSON
```

Пример результата:

```json
{
  "documentType": "Laboratory Report",
  "documentDate": "2025-03-14",
  "organization": "...",
  "doctor": "...",
  "diagnoses": [],
  "medications": [],
  "labResults": [],
  "procedures": [],
  "recommendations": []
}
```

Полученный JSON сохраняется как сущность **Extraction**.

Extraction считается "сырой" структурой.

## Вариативность результата и автоматический ретрай

Structured Extraction — не детерминированная операция, даже при низкой температуре (см. `05-llm.md` §12). На реальных документах в ходе разработки неоднократно наблюдалось: один и тот же документ, один и тот же промпт и схема, при повторном вызове давали то полностью корректный результат, то результат с пустыми структурированными категориями при этом полностью корректном и содержательном распознанном тексте (`fullText`) — без единой ошибки или предупреждения от LLM-провайдера (`finishReason: STOP`, не обрезка по лимиту токенов). Наблюдался и второй, более тонкий вариант той же проблемы: добавление ещё одной крупной категории в схему (см. `../domain/13-instrumental-finding.md`) снижало надёжность извлечения *остальных* категорий в том же вызове, а не только новой — увеличение общего объёма запрашиваемого структурированного вывода в одном вызове само по себе снижает надёжность.

Из этого следуют три архитектурных решения:

1. **Каждый большой, самостоятельный по смыслу блок схемы — отдельный вызов LLM**, а не одна большая схема на всё. Так разделены OCR/Vision (§4.3) и Structured Extraction (этот раздел), и внутри Structured Extraction — клинические сущности (диагнозы, медикаменты, лабораторные показатели, процедуры, рекомендации) отдельно от `InstrumentalFinding`. Критерий разделения — не тип данных сам по себе, а наблюдаемая надёжность: если добавление категории ощутимо увеличивает объём ожидаемого вывода (например, ~20-40 записей для плотного УЗИ-протокола), она получает собственный вызов.
2. **Автоматический ретрай при явно неправдоподобном результате.** Если распознанный текст содержательный, а структурированные категории, которые должны были бы в норме найтись, пусты — это не принимается как окончательный результат сразу: этап перезапускается автоматически против того же провайдера (1 дополнительная попытка — намеренно немного, см. решение 3 ниже), прежде чем результат передаётся дальше по Pipeline. Эта проверка возможна только там, где "пустой результат подозрителен" отличимо от "пустой результат — нормальное состояние для этого документа" — для категорий, которые редко бывают непустыми в принципе (например, `InstrumentalFinding` в документе, не являющемся результатом визуализации), слепой ретрай при каждом пустом результате тратил бы вызовы LLM впустую и поэтому не применяется безусловно.

   Изначально эта проверка требовала, чтобы **все** клинические категории были пусты одновременно — а не только та, что реально ожидается для этого типа документа. На реальных данных это оказалось недостаточно: `documentType` — единственное обязательное поле Structured Extraction, значит известен уже после первой же попытки, ещё до решения о ретрае. Модель может честно заполнить общее, почти всегда присутствующее поле (например, `recommendations` — типовая фраза-дисклеймер) на попытке, где категория, которая для этого типа документа реально имеет значение (например, `labResults` для `lab_report`), так и осталась пустой — и старая проверка ошибочно принимала это за "результат правдоподобен", останавливая ретрай раньше, чем нужно. Теперь для типов документа с известным ожидаемым набором категорий (`lab_report` → `labResults`, `prescription` → `medications` и т.д., см. `internal/extraction.expectedCategoriesByDocumentType`) проверяется пустота именно этого набора, а не всех категорий сразу; для типов без известного набора (`other`) поведение не изменилось — по-прежнему требуется полная пустота.
3. **Эскалация на другого провайдера, если ретрай против того же провайдера не помог.** Если после решения 2 результат всё ещё подозрительно пуст, делается одна попытка против отдельно сконфигурированного провайдера-эскалации (`llm.providers[].escalation.target_provider`, см. `05-llm.md` "Конфигурация провайдеров и caller-side эскалация") — другой модели, которая не обязательно разделяет то, из-за чего первая не справилась. Именно поэтому решение 2 намеренно ограничено одной дополнительной попыткой, а не тремя: наблюдалось, что три подряд попытки одного и того же провайдера на одном и том же документе иногда одинаково пусты (см. пример ниже) — третья попытка того же провайдера тратит вызов LLM с низкой ожидаемой отдачей, тогда как переход к другому провайдеру — реальная диверсификация. Живой пример, наблюдавшийся при разработке: лабораторный бланк, где единственный реальный результат (тест на ВИЧ) занимал одну строку среди ~6КБ не относящегося к делу информационного текста (памятка по профилактике) — 3 попытки того же провайдера подряд не нашли результат вообще; отдельно проверено (`finishReason: STOP` на каждой попытке — см. `miranda-llm/gemini`'s `logStructuredFinish`), что это не фильтрация по безопасности контента, а именно ненадёжность извлечения на разреженном документе.

Эта проверка (во всех трёх решениях) ловит только один, наиболее частый и наиболее дёшево обнаружимый паттерн сбоя — пустоту той категории, что должна была найтись, при содержательном тексте. Более тонкие частичные пропуски (например, не все строки таблицы лабораторных показателей попали в `labResults`, при том что массив не пуст) автоматически не обнаруживаются; для них по-прежнему предусмотрен только пользовательский путь — увидеть результат сразу после обработки и запросить повторную обработку (`medical.reprocess_document`, см. `../mcp/03-documents.md` §6).

# 6. Normalization

Extraction не используется напрямую.

Следующий этап преобразует его в доменные сущности.

Например:

```
Extraction

↓

Diagnosis

Medication

TimelineEvent

Procedure

LabResult
```

На данном этапе:

- нормализуются единицы измерения;
- приводятся даты;
- удаляются дубликаты (в пределах фактов, извлечённых из одного и того же документа);
- канонизируются названия (действующее вещество, код диагноза и т.п.).

Normalization **не создаёт постоянных связей между сущностями разных документов**. Это намеренное архитектурное решение — см. ниже.

## Идемпотентность Normalization

Поскольку Normalization работает строго в границах одного документа и не создаёт постоянных междокументных связей, идемпотентность достигается дёшево и без сопоставления отдельных сущностей: все сущности, ранее созданные из данного `documentId`, удаляются и создаются заново из нового `Extraction`. Заменяется весь набор целиком — сопоставлять старую версию конкретной сущности с новой не требуется.

## Почему нет постоянных междокументных связей

Ранняя версия этого документа предполагала, что Normalization должна сама сопоставлять связанные факты из разных документов — например, связать "Aspirin, назначенный в документе A" с "продолжает принимать Aspirin" из документа B, загруженного позже, в единую цепочку. От этого решено отказаться.

Проблема с постоянными связями: они превращают Normalization из детерминированной, документ-скоуп операции в задачу entity resolution над всей историей пользователя. Переобработка документа A (новый prompt, другая модель) могла бы менять решение о том, с чем он был связан, а уже построенные на основе старой связи Timeline Events и Medical Profile — расходиться с реальностью без явного сигнала об ошибке.

Вместо этого связность между документами вычисляется на лету, а не хранится:

- **`medical.ask`** — Knowledge Provider (например, Medication Provider) отдаёт LLM все структурированные факты по нужному веществу/диагнозу за всю историю (raw entities, не готовую цепочку), а вывод вида "принимает Aspirin с 14 мая, отменён 3 сентября" делает Answer Generator при формировании ответа — это ровно то, для чего в архитектуре существует связка Knowledge Providers + LLM (см. `03-knowledge-providers.md`), и вычисляется заново при каждом вопросе, а не читается из устаревающего кэша связей.
- **`medical.profile` / `medical.timeline`** — детерминированные, без LLM (см. `../mcp/05-profile.md` §1, `../mcp/06-timeline.md` §1), поэтому continuity ("это тот же курс лечения") здесь не может определяться моделью на лету. Но это не требует постоянных связей: Domain Services (`Medication Resolver`, `Diagnosis Resolver` — см. `../domain/01-overview.md` §7) при каждой пересборке Profile выполняют группировку/агрегацию сущностей (например, по канонизированному названию вещества и диапазону дат) как обычный запрос, а не читают заранее сохранённый граф связей. Пересборка Profile уже происходит при каждой обработке документа (см. §8) — этого достаточно, дополнительная инвалидация не нужна, потому что нечему становиться устаревшим.

Это устраняет саму причину проблемы идемпотентности между документами: раз связи нигде не хранятся, переобработке нечего оставлять в устаревшем состоянии.

# 7. Построение Timeline

После создания сущностей автоматически строится Timeline.

Каждая сущность,
имеющая дату,
должна создать хотя бы одно событие Timeline.

Например

```
Medication

↓

Medication Started
```

или

```
LabResult

↓

Blood Test
```

или

```
Procedure

↓

MRI
```

Timeline является главным источником информации
о последовательности медицинских событий.

---

# 8. Построение профиля пользователя

После завершения нормализации сервис обновляет агрегированную сущность MedicalProfile.

Она представляет собой "текущее состояние" медицинской истории пользователя.

Например:

- активные диагнозы;
- хронические заболевания;
- текущие лекарства;
- аллергии;
- непереносимости;
- последние лабораторные показатели;
- последние жизненно важные показатели.

MedicalProfile не вводится пользователем вручную.

Он полностью строится автоматически.

---

# 9. Генерация Summary

Для каждого MedicalDocument создается краткое описание.

Например:

> Общий анализ крови. Повышен ALT. Остальные показатели в пределах нормы.

Summary используется:

- при поиске;
- в Timeline;
- в списке документов;
- при построении контекста.

Summary не должен содержать размышлений модели.

Только факты.

---

# 10. Построение Embeddings

После завершения структурирования создаются Embeddings.

Embeddings строятся не только для текста документа.

Отдельные Embeddings могут иметь:

- Summary;
- Diagnosis;
- Procedure;
- Timeline Event;
- Recommendations.

Это позволяет значительно повысить качество семантического поиска.

---

# 11. Построение FTS Index

После завершения обработки обновляется полнотекстовый индекс.

В индекс рекомендуется помещать:

- полный текст документа;
- Summary;
- рекомендации;
- заключения врача.

Структурированные сущности индексировать не требуется.

Для них используется SQLite.

---

# 12. Завершение обработки

После успешного выполнения всех этапов

```
MedicalDocument.status = READY
```

Документ становится доступен:

- для поиска;
- для Timeline;
- для Knowledge Providers;
- для ответов LLM.

---

# 13. Повторная обработка

Pipeline должен поддерживать повторный запуск отдельных этапов.

Например:

```
Artifact

↓

NEW PROMPT

↓

Extraction

↓

Normalization

↓

Timeline
```

или

```
MedicalDocument

↓

Embedding v2

↓

Embedding v3
```

Повторная обработка не должна требовать повторной загрузки файла.

---

# 14. Обработка ошибок

Каждый этап имеет собственный статус выполнения.

Рекомендуемые статусы:

```
PENDING
RUNNING
READY
FAILED
SKIPPED
```

Ошибка одного этапа не должна повреждать результаты предыдущих этапов.

Например ошибка построения Embeddings не должна делать документ недоступным для Timeline.

## Границы транзакций

Поскольку обработка документа синхронна (см. §2), нет необходимости в отдельной инфраструктуре очередей/воркеров для восстановления после частичного сбоя — большую часть Pipeline можно и нужно выполнять в одной SQLite-транзакции.

**В одной транзакции**: сохранение Extraction, Normalization (Domain Entities), построение Timeline Events, пересчёт Medical Profile, обновление FTS5-индекса. Все эти шаги — чистые операции над SQLite (FTS5 — виртуальная таблица в том же соединении, тоже участвует в транзакции), без обращения к внешним сервисам. При ошибке на любом из них транзакция откатывается целиком: документ остаётся в состоянии до начала обработки (либо явно помечается `FAILED`), Timeline и Profile не могут разойтись с Domain Entities.

**Вне этой транзакции**: построение Embeddings. Это единственный шаг, зависящий от внешнего вызова LLM (см. `05-llm.md`), и именно для него в начале этого раздела сформулировано явное исключение — ошибка Embeddings не должна делать документ недоступным для Timeline. Если бы Embeddings были частью общей транзакции, эта гарантия была бы невыполнима: откат из-за сбоя Embeddings откатил бы и уже успешно построенные Timeline/Profile. Поэтому Embeddings — отдельный шаг после коммита основной транзакции, с собственным статусом (`PENDING` / `READY` / `FAILED`) и возможностью повторного запуска независимо от остального документа.

# 15. Архитектурные решения

В данной архитектуре выделяются три уровня данных:

```
Artifact
```

Источник истины.

---

```
Extraction
```

Источник фактов, извлеченных LLM.

---

```
Domain Entities
```

Источник знаний, используемых системой.

Такое разделение позволяет независимо улучшать каждый уровень без изменения остальных.

# 17. Альтернативный вход: Self-Reported Events

Помимо `Upload` (§4.1), у Pipeline есть второй, более короткий вход — `medical.log_event` (см. `../mcp/07-events.md`), для фактов, о которых пользователь сообщает напрямую в диалоге, без документа (например "приступ головной боли, принял ибупрофен").

```text
                     Текст пользователя
                              │
                              ▼
             Save SelfReportedEvent (rawText, occurredAt)
                              │
                              ▼
             Structured Extraction (текст, не OCR)
                              │
                              ▼
                       Normalization
             (канонизация вещества, если есть MedicationIntake)
                              │
                              ▼
                         Timeline
                              │
                              ▼
                    Embeddings / FTS
                              │
                              ▼
                           READY
```

Отличия от основного Pipeline:

- нет этапа `Upload`/`Save Artifact` — нет бинарного файла, нечего сохранять и дедуплицировать;
- нет этапа `OCR / Vision` — вход уже является текстом;
- нет `Summary` как отдельного этапа — `SelfReportedEvent.description` заполняется тем же вызовом, что и `category` (см. `../mcp/07-events.md` §3), поскольку исходный текст и так короткий;
- неудача Structured Extraction не переводит запись в `FAILED` — см. `../mcp/07-events.md` §3 "Возможные ошибки": исходный текст пользователя сохраняется даже без структурированных полей, поскольку, в отличие от документа, здесь нет отдельного `download_file`, к которому можно было бы вернуться, если структурирование не удалось.

Оба входа сходятся начиная с `Normalization` и используют один и тот же `TimelineBuilder`. `ProfileBuilder` в v1 не читает `MedicationIntake`/`SelfReportedEvent` — Medical Profile по-прежнему строится только из документально подтверждённых сущностей (см. `../domain/12-self-reported-events.md` §6 и `../domain/05-medical-profile.md`).
