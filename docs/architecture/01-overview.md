# Medical Service

## Архитектурная спецификация

**Версия:** 1.0 (Draft)

# 1. Назначение сервиса

## 1.1 Общая информация

Medical Service --- специализированный микросервис экосистемы Miranda,
предназначенный для хранения, структурирования, индексирования и анализа
медицинской информации пользователей.

Сервис реализует MCP Server и предоставляет набор инструментов (Tools),
которые позволяют Miranda работать с медицинскими данными на высоком
уровне без необходимости знать внутреннее устройство сервиса.

Medical Service является единственным источником медицинской информации
для Miranda.

## 1.2 Основные задачи

Сервис должен обеспечивать:

-   хранение оригинальных медицинских документов;
-   автоматическое извлечение структурированных данных из документов;
-   хранение медицинской истории пользователя;
-   хранение истории лабораторных показателей;
-   хранение истории назначений лекарств;
-   построение медицинской временной шкалы (Timeline);
-   интеллектуальный поиск по медицинским данным;
-   ответы на вопросы пользователя при помощи LLM.

## 1.3 Что НЕ входит в обязанности сервиса

Сервис не занимается:

-   аутентификацией пользователей;
-   авторизацией пользователей;
-   управлением аккаунтами;
-   пользовательским интерфейсом;
-   загрузкой файлов напрямую из браузера;
-   хранением истории диалогов.

Все перечисленные задачи выполняет Miranda.

# 2. Место сервиса в архитектуре Miranda

``` text
                Пользователь
                      │
                      ▼
                Miranda Client
                      │
                      ▼
                 Miranda Core
                      │
                  MCP Client
                      │
      ┌───────────────┴────────────────┐
      │                                │
      ▼                                ▼
 Medical Service                 Другие MCP сервисы
```

Medical Service является независимым микросервисом.

Miranda обращается к нему исключительно через MCP Tools.

Сервис не знает ничего о существовании Web UI, Telegram, Home Assistant
или других клиентов.

# 3. Ответственность Miranda

Miranda отвечает за:

-   аутентификацию пользователя;
-   определение текущего пользователя;
-   проверку прав доступа;
-   загрузку файлов от пользователя;
-   скачивание файлов пользователю;
-   маршрутизацию запросов к MCP Tools.

При каждом вызове MCP Tool Miranda передает идентификатор пользователя:

``` json
{
  "userId": "alex"
}
```

# 4. Пользователи

Несмотря на то, что сервис предназначен для домашнего использования, он
должен поддерживать нескольких пользователей (например членов семьи).

Источником информации о пользователях является статический YAML-файл.

Пример:

``` yaml
users:
  - id: alex
    display_name: Alexander
    birth_date: 1988-04-12
    sex: male

  - id: anna
    display_name: Anna
    birth_date: 1992-08-03
    sex: female

  - id: kid
    display_name: Kid
    birth_date: 2020-01-01
    sex: male
    shared_with: [alex, anna]  # родители могут читать данные ребёнка
    encryption: false          # см. п.5 ниже: shared_with и encryption взаимоисключающи
```

`shared_with` — необязательный список `userId`, которым разрешено читать (но не изменять и не удалять) данные этого пользователя. По умолчанию пуст: данные каждого пользователя видны только ему самому. См. `../mcp/01-overview.md` §11 про то, как это влияет на параметры MCP Tools, и `06-storage.md` §14 про несовместимость с `encryption`.

При запуске сервис загружает файл в память.

Все MCP Tools принимают параметр:

``` text
userId string
```

Перед выполнением операции сервис обязан проверить существование
пользователя.

Если пользователь отсутствует в конфигурации, возвращается ошибка
`Unknown user`.

# 5. Принципы хранения данных

Сервис разделяет информацию на несколько независимых уровней.

``` text
Файл
 ↓
Документ
 ↓
Структурированные данные
 ↓
Timeline
 ↓
Embeddings
 ↓
Ответы LLM
```

Каждый уровень может быть полностью перестроен без изменения
предыдущего.

Это позволяет:

-   менять LLM;
-   менять prompts;
-   переиндексировать документы;
-   перестраивать embeddings;
-   перестраивать timeline.

Без повторной загрузки оригинальных документов.

# 6. Основные архитектурные принципы

## Оригинальные документы никогда не изменяются

После загрузки документ становится неизменяемым.

Любая повторная обработка должна использовать оригинальный файл.

## Все извлеченные данные являются производными

Источником истины всегда остается оригинальный документ.

## Максимально структурированные данные

При обработке документа сервис должен максимально извлекать:

-   диагнозы;
-   лекарства;
-   процедуры;
-   лабораторные показатели;
-   даты;
-   врачей;
-   рекомендации;
-   исследования.

## Timeline является основной сущностью анализа

Все значимые события автоматически преобразуются в события Timeline.

При анализе медицинской истории LLM в первую очередь использует
Timeline, а уже затем обращается к исходным документам.

## Приоритет источников данных

1.  Timeline
2.  Medications
3.  Lab Results
4.  Diagnoses
5.  Другие структурированные сущности
6.  FTS
7.  Embeddings
8.  Исходный документ

## Использование общего LLM-пакета

Рекомендуется использовать общий пакет, разделяемый с Miranda и другими
микросервисами, который предоставляет:

-   маршрутизацию запросов между LLM-провайдерами;
-   автоматическую эскалацию моделей;
-   ротацию API-ключей;
-   Structured Output;
-   Embeddings;
-   Vision/OCR;
-   Retry;
-   единые политики обработки ошибок.

Medical Service должен зависеть только от абстракций этого пакета, а не
от конкретного LLM-провайдера.
