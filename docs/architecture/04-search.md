# 1. Назначение

Search Architecture определяет способы получения медицинских знаний из различных источников данных.

Цель поиска — не вернуть документы пользователю, а предоставить Knowledge Providers максимально релевантные знания для формирования ответа.

Поиск является внутренним механизмом сервиса и никогда не вызывается напрямую пользователем.

---

# 2. Принципы

Поиск строится вокруг следующих принципов.

## Использовать наиболее структурированный источник

Если информация существует в виде структурированной сущности, необходимо использовать именно ее.

Например:

Вопрос:

> Какие лекарства я принимаю сейчас?

Ответ должен быть получен из таблицы Medication.

Повторный анализ документов в данном случае недопустим.

---

## Не использовать LLM для поиска

LLM не должна выполнять поиск.

Она:

- определяет намерение пользователя;
- выбирает необходимые Knowledge Providers;
- формирует итоговый ответ.

Поиск выполняется исключительно кодом приложения.

---

## Минимизировать объем контекста

Лучше передать LLM пять качественных фрагментов знаний, чем сто страниц текста.

Каждый Provider обязан возвращать минимальный объем информации, достаточный для ответа.

---

## Поиск должен быть детерминированным

Одинаковые входные данные должны приводить к одинаковому результату.

Это особенно важно для медицинских данных.

---

# 3. Общая схема

```text
                  User Question
                        │
                        ▼
                 Planner (LLM)
                        │
                        ▼
               Knowledge Provider
                        │
                        ▼
                 Search Engine
                        │
        ┌───────────────┼────────────────┐
        ▼               ▼                ▼
     SQLite           FTS5          Embeddings
        │               │                │
        └───────────────┼────────────────┘
                        ▼
               Knowledge Chunks
                        │
                        ▼
               Context Builder
```

# 4. Источники знаний

Medical Service использует несколько механизмов поиска.

Каждый предназначен для собственного типа информации.

---

# 5. SQLite Search

SQLite является основным источником знаний.

Используется для поиска:

- лекарств;
- диагнозов;
- процедур;
- лабораторных показателей;
- Timeline;
- Medical Profile.

SQLite обеспечивает:

- максимальную точность;
- минимальную стоимость;
- предсказуемый результат.

---

## Пример

Вопрос:

> Какие препараты я принимаю сейчас?

Выполняется SQL-запрос.

Никакие Embeddings и LLM не используются.

---

# 6. Timeline Search

Timeline является наиболее важным источником знаний.

Практически любой вопрос содержит временной аспект.

Например:

> Что произошло прошлой весной?

или

> Что было после операции?

или

> Когда появились первые симптомы?

Timeline позволяет быстро получить последовательность событий.

---

# 7. Lab Search

Поиск лабораторных результатов выполняется исключительно по структурированным данным.

Например:

> Покажи историю ALT.

или

> Как изменялся холестерин?

Provider самостоятельно выбирает необходимые показатели.

---

# 8. Medication Search

Поиск лекарств использует только структурированные данные.

Возможные типы поиска:

- текущие препараты;
- история назначения;
- история отмены;
- пересечения курсов;
- препараты по действующему веществу;
- препараты по торговому названию.

---

# 9. Diagnosis Search

Позволяет получать:

- активные диагнозы;
- исторические диагнозы;
- предполагаемые диагнозы;
- диагнозы за период.

---

# 10. Procedure Search

Используется для поиска:

- операций;
- обследований;
- госпитализаций;
- вакцинаций;
- консультаций.

---

# 11. Document Search

Не вся информация может быть преобразована в структуру.

Например:

- субъективные жалобы;
- особенности состояния;
- свободные комментарии врача.

В подобных случаях используется поиск по документам.

---

# 12. Full Text Search (FTS5)

FTS5 используется только тогда, когда структурированных данных недостаточно.

В индекс рекомендуется включать:

- полный текст документа;
- Summary;
- рекомендации;
- заключения.

Не рекомендуется индексировать структурированные сущности.

Они уже представлены в SQLite.

---

## Пример

Вопрос:

> В каком документе упоминалась бессонница?

Подходит FTS Search.

---

# 13. Embedding Search

Embedding Search используется исключительно для семантического поиска.

Например:

> Когда были проблемы с печенью?

Хотя слово "печень" может отсутствовать.

Embedding Search позволяет найти:

- похожие описания;
- связанные симптомы;
- косвенные упоминания.

Свободный текст самостоятельно зафиксированных событий (`SelfReportedEvent.rawText`/`description`, см. `../domain/12-self-reported-events.md` §6 и `../mcp/07-events.md`) — один из лучших кандидатов для Embedding Search: вопросы вида "когда мне было плохо" чаще относятся именно к тому, что пользователь сам о себе рассказал, чем к формальным документам.

---

## Когда использовать Embeddings

Хорошие примеры:

- "когда мне было плохо"
- "что было не так с сердцем"
- "были ли проблемы с печенью"

---

## Когда НЕ использовать

Плохие примеры:

- ALT
- LDL
- Rosuvastatin
- MRI

Для подобных запросов существуют структурированные данные.

---

# 14. Гибридный поиск

Provider может объединять несколько источников.

Например:

```
SQLite

+

FTS

+

Embeddings

↓

Merge

↓

Ranking

↓

Knowledge Chunks
```

Именно Provider определяет стратегию объединения.

---

# 15. Ranking

После получения результатов они сортируются.

Приоритет рекомендуется определять следующим образом.

1. Структурированные сущности
2. Timeline
3. Medical Profile
4. FTS
5. Embeddings

Это позволяет минимизировать влияние вероятностных механизмов поиска.

---

# 16. Merge

Результаты разных механизмов могут содержать одинаковую информацию.

Например:

Timeline может ссылаться на тот же документ, который найден через FTS.

Перед передачей данных LLM необходимо:

- удалить дубликаты;
- объединить связанные результаты;
- сохранить ссылки на источники.

---

# 17. Confidence

Каждый найденный результат должен иметь оценку уверенности.

Например:

```text
Timeline Event (документ)        1.00

Medication / Lab Result          1.00

Timeline Event (self-reported)   0.90

FTS                              0.82

Embedding                        0.74
```

Данные, извлечённые из документа, верифицируемы третьей стороной (врач, лаборатория) и получают полную уверенность. Самостоятельно зафиксированные события (`symptom`, `medication_taken` — см. `../domain/12-self-reported-events.md` §6) остаются структурированными фактами в SQLite и поэтому приоритетнее FTS/Embeddings, но не наравне с документальными — они неверифицируемы, поэтому используют собственную, более низкую ступень Confidence.

Confidence используется только внутри Search Engine.

LLM не должна самостоятельно вычислять надежность найденных данных.

---

# 18. Search Scope

Каждый Provider самостоятельно определяет область поиска.

Например.

Medication Provider никогда не использует Embeddings.

Lab Provider редко использует FTS.

Document Provider практически всегда использует FTS.

Embedding Provider использует только Vector Search.

---

# 19. Семантический поиск не заменяет структурированный

Embedding Search является дополнением.

Он никогда не должен заменять:

- SQL;
- Timeline;
- Domain Entities.

Это один из основных архитектурных принципов Medical Service.

---

# 20. Оптимизация

Provider должен стремиться получить ответ минимальной стоимостью.

Пример.

Вопрос:

> Какие препараты я принимаю?

Стоимость поиска:

SQLite — очень низкая

FTS — выше

Embeddings — выше

LLM — самая высокая

Следовательно используется SQLite.

---

# 21. Кэширование

Допускается кэширование:

- результатов Embedding Search;
- результатов FTS;
- часто используемых SQL-запросов;
- Knowledge Chunks.

Не рекомендуется кэшировать итоговые ответы LLM.

Ответ зависит от Prompt и версии модели.

---

# 22. Источники истины

Для каждого типа данных существует основной источник.

| Тип данных | Источник |
|------------|----------|
| Лекарства | SQLite |
| Диагнозы | SQLite |
| Анализы | SQLite |
| Процедуры | SQLite |
| Timeline | SQLite |
| Medical Profile | SQLite |
| Самостоятельные события (symptom/medication_taken) | SQLite |
| Документы | FTS |
| Семантика | Embeddings |

Если информация существует в основном источнике, альтернативные механизмы использовать не следует.

---

# 23. Архитектурные решения

Поиск строится вокруг трех уровней.

## Structured Search

Максимально быстрый и точный поиск.

Используется всегда, когда возможно.

---

## Text Search

Используется для поиска свободного текста.

---

## Semantic Search

Используется только тогда, когда предыдущие два уровня не позволяют получить ответ.

---

Такое разделение обеспечивает:

- минимальную стоимость;
- максимальную точность;
- воспроизводимость;
- независимость от конкретной LLM.

---

# 24. Будущие расширения

Архитектура поиска должна позволять добавлять новые механизмы без изменения существующих Providers.

Возможные расширения:

- Knowledge Graph Search;
- ICD-10 Search;
- LOINC Search;
- SNOMED CT Search;
- Drug Interaction Search;
- External Medical Knowledge Base;
- Medical Guideline Search;
- Apple Health Search;
- Google Fit Search;
- Nutrition Service Search;
- Federated Search между несколькими сервисами Miranda.

Все новые механизмы должны интегрироваться через существующую архитектуру Knowledge Providers и не требовать изменений Planner.
