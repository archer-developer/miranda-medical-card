# 1. Назначение

LLM является одним из ключевых компонентов Medical Service, однако не является источником данных.

Все долговременные знания хранятся внутри сервиса.

LLM используется исключительно для задач, в которых современные языковые модели значительно превосходят традиционные алгоритмы:

- понимание естественного языка;
- анализ документов;
- извлечение структуры;
- построение плана получения знаний;
- генерация итогового ответа.

Во всех остальных случаях предпочтение должно отдаваться детерминированному коду.

---

# 2. Архитектурный принцип

Medical Service проектируется по принципу:

> **LLM думает. Код знает.**

LLM принимает решения только там, где требуется понимание естественного языка.

Код отвечает за:

- хранение данных;
- поиск;
- фильтрацию;
- агрегацию;
- бизнес-логику;
- работу с базой данных.

---

# 3. Ответственность LLM

В рамках Medical Service LLM может выполнять только следующие задачи.

## OCR / Vision

Извлечение текста из изображений и PDF.

Примеры:

- анализ фотографии рецепта;
- анализ результатов лабораторных исследований;
- анализ выписки;
- анализ МРТ.

---

## Structured Extraction

Извлечение фактов из медицинского документа.

Например:

- диагнозы;
- лекарства;
- анализы;
- процедуры;
- рекомендации;
- даты.

LLM должна извлекать информацию максимально полно, не интерпретируя медицинские данные.

---

## Planner

Первый вызов LLM во время ответа пользователю.

Получает:

- вопрос пользователя;
- список зарегистрированных Knowledge Providers;
- описание возможностей каждого Provider.

Возвращает Execution Plan.

---

## Answer Generator

Последний вызов LLM.

Получает:

- вопрос пользователя;
- подготовленный контекст.

Возвращает ответ.

---

## Embeddings

LLM используется для генерации Embeddings.

Embeddings применяются исключительно для семантического поиска.

---

# 4. Что LLM делать запрещено

LLM никогда не должна:

- выполнять SQL-запросы;
- знать структуру базы данных;
- читать SQLite напрямую;
- определять способ хранения данных;
- выполнять бизнес-логику;
- самостоятельно вычислять лабораторные показатели;
- изменять медицинские записи;
- придумывать отсутствующие факты.

Все подобные задачи решаются кодом приложения.

---

# 5. Общая схема

```text
                   Upload Document
                          │
                          ▼
                     OCR / Vision
                          │
                          ▼
                Structured Extraction
                          │
                          ▼
                     Normalization
                          │
                          ▼
                    SQLite / Search

===================================================

                    User Question
                          │
                          ▼
                     Planner (LLM)
                          │
                          ▼
                 Knowledge Providers
                          │
                          ▼
                   Context Builder
                          │
                          ▼
                 Answer Generator
                          │
                          ▼
                     Final Answer
```

# 6. Многоэтапная работа LLM

Один пользовательский запрос может включать несколько независимых вызовов модели.

Например:

```
Planner

↓

Knowledge Providers

↓

Answer Generator
```

Каждый вызов решает только одну задачу.

Это позволяет:

- уменьшить сложность Prompt;
- снизить стоимость;
- упростить отладку;
- заменить отдельные модели независимо.

---

# 7. Использование разных моделей

Разные этапы могут использовать разные модели.

Например:

| Этап | Требования |
|-------|------------|
| OCR | Vision |
| Structured Extraction | высокая точность |
| Planner | быстрый вывод, хорошее понимание языка |
| Answer Generator | качественная генерация текста |
| Embeddings | embedding model |

Архитектура не должна предполагать использование одной универсальной модели.

---

# 8. Общая библиотека LLM

Medical Service не должен зависеть от конкретного API поставщика.

Вместо этого используется единая библиотека взаимодействия с LLM, общая для всех сервисов Miranda.

Библиотека предоставляет единый интерфейс независимо от используемой модели.

Это позволяет изменять поставщика или стратегию выбора моделей без изменения бизнес-логики сервиса.

---

# 9. Требования к библиотеке

Библиотека должна поддерживать следующие возможности.

## Несколько провайдеров

Например:

- Gemini
- OpenAI Compatible API
- Claude

Добавление новых провайдеров не должно требовать изменения кода Medical Service.

---

## Маршрутизация моделей

Разные задачи могут использовать разные модели.

Например:

```
Planner

↓

Gemini Flash
```

```
Answer Generator

↓

Claude Sonnet
```

```
OCR

↓

Gemini Pro Vision
```

Выбор модели определяется конфигурацией, а не кодом приложения.

---

## Автоматическая эскалация

При ошибке выполнения библиотека должна иметь возможность автоматически переключиться на альтернативную модель.

Например:

```
Gemini

↓

Ошибка

↓

OpenAI Compatible

↓

Ошибка

↓

Claude
```

Стратегия переключения полностью скрыта от Medical Service.

---

## Ротация API-ключей

Библиотека должна поддерживать несколько API-ключей одного провайдера.

При достижении лимита автоматически используется следующий ключ.

Эта возможность особенно важна для бесплатных тарифов и персонального использования.

---

## Structured Output

Все этапы, возвращающие структурированные данные, должны использовать строгие схемы.

Примеры:

- Extraction
- Planner
- Summary

Использование свободного текста для подобных задач не рекомендуется.

---

## Streaming

Для генерации длинных ответов библиотека должна поддерживать потоковую передачу результата.

---

## Retry

Повторные попытки должны быть реализованы внутри библиотеки.

Medical Service не должен реализовывать собственную логику повторов.

---

## Timeout

Каждый вызов модели должен иметь ограничение по времени.

Таймаут определяется вызывающим компонентом.

---

## Telemetry

Библиотека должна предоставлять информацию о каждом вызове:

- использованная модель;
- провайдер;
- длительность;
- количество токенов;
- стоимость (если доступна);
- причина переключения модели.

---

# 9.1 Готовая реализация: miranda-llm

Общая библиотека, описанная в §8-9, реализована как отдельный Go-модуль `github.com/archer-developer/miranda-llm` (репозиторий `../miranda-llm`), извлечённый из `internal/llm` сервиса Miranda и доступный для подключения как обычная `go.mod`-зависимость — без копирования кода и без вынесения LLM в отдельный сетевой микросервис.

**Важно:** сама Miranda пока не переведена на этот модуль — она продолжает использовать собственную внутреннюю копию (`miranda/internal/llm`). Медкарта подключает `miranda-llm` независимо от этого. См. `miranda-llm/CLAUDE.md` за деталями извлечения.

Соответствие требований §9 конкретным пакетам:

| Требование | Пакет / тип |
|---|---|
| Несколько провайдеров | `gemini.Provider`, `anthropic.Provider`, `openaicompat.Provider` — каждый реализует общий интерфейс `llm.Provider` |
| Маршрутизация моделей | `router.Router` — провайдер на каждый этап (OCR/Extraction/Planner/Answer Generator) конфигурируется отдельно вызывающим сервисом |
| Автоматическая эскалация | `router.Router.Chat` — reliability fallback (следующий провайдер при ошибке) работает всегда; tool-based эскалация (модель сама решает передать ход) — опциональна per-provider, см. ниже |
| Ротация API-ключей | `keyrotation` (внутри `gemini.Provider`) |
| Structured Output | `llm.StructuredProvider` / `router.Router.Structured` — отдельный однократный (не потоковый) вызов, возвращающий `json.RawMessage` по JSON Schema |
| Streaming | `llm.Provider.Chat` — потоковый по умолчанию |
| Retry | `keyrotation.Run` (ротация ключей) + reliability fallback `router.Router` |
| Timeout | через `context.Context`, передаваемый вызывающей стороной — библиотека не навязывает собственный таймаут |
| Telemetry | `llmtrace.Logger` — пишет request/response каждого вызова текстовым блоком в лог; структурированного per-call учёта токенов/стоимости в виде отдельного API пока нет — это открытый пробел, а не реализованная возможность |

## Structured Output — основной способ использования для Extraction/Planner/Summary

Именно `router.Router.Structured` (а не `Chat`) — правильный вызов для этапов Structured Extraction (§5), Planner (`03-knowledge-providers.md` §6) и генерации Summary (`02-processing-pipeline.md` §9): один непотоковый запрос, схема JSON Schema, результат без интерпретации моделью.

`Structured` **не** проходит через цепочку эскалации `Chat` — у одноразового structured-вызова нет открытого диалога, в рамках которого модели имело бы смысл самой решать "передать вопрос более сильной модели". Она использует только reliability fallback (следующий провайдер при ошибке).

## Tool-based эскалация — вероятно, не нужна Medical Service

`router.Router` поддерживает два разных механизма, объединённых в один API:

1. **Reliability fallback** — при отказе провайдера (ключи исчерпаны, таймаут) автоматически пробуется следующий сконфигурированный провайдер. Работает всегда, ничего не нужно включать.
2. **Tool-based эскалация** — провайдеру предъявляется инструмент вида `escalate_to_claude`, который модель может вызвать сама, если решит, что вопрос ей не по силам. Это имеет смысл в открытом многоходовом диалоге (agent loop Miranda), но не для одноразовых structured-вызовов Medical Service (Extraction/Planner/Answer Generator), где у модели просто нет пространства для такого самостоятельного решения посреди генерации одного структурированного ответа.

Механизм (2) полностью опционален: он включается только если передать непустой `escalations` в `router.New`. Medical Service должен по умолчанию передавать `nil`, полагаясь только на (1).

# 10. Prompt Management

Промпты являются частью приложения.

Они должны:

- храниться отдельно от кода;
- иметь версии;
- быть легко заменяемыми;
- поддерживать тестирование.

Не рекомендуется размещать большие Prompt непосредственно в исходном коде.

---

# 11. Structured Output

Все задачи, предполагающие машинную обработку результата, должны использовать строгие схемы.

Например:

Planner возвращает:

```json
{
  "providers": [...]
}
```

а не свободный текст:

> Думаю, стоит посмотреть лекарства и анализы.

---

# 12. Температура

Для большинства задач рекомендуется использовать минимальную температуру.

Например:

| Этап | Температура |
|-------|-------------|
| Planner | низкая |
| Extraction | низкая |
| Summary | низкая |
| Answer Generator | средняя |

Главным приоритетом Medical Service является воспроизводимость результатов.

---

# 13. Контекст

LLM должна получать только ту информацию, которая необходима для решения текущей задачи.

Например Planner получает:

- вопрос пользователя;
- список Providers;
- описание Providers.

Planner не получает медицинские данные.

---

Answer Generator получает:

- вопрос пользователя;
- готовый контекст.

Answer Generator не получает информацию о структуре базы данных или механизмах поиска.

---

# 14. Галлюцинации

Архитектура должна минимизировать вероятность появления недостоверной информации.

Для этого:

- используются структурированные данные;
- ограничивается объем контекста;
- запрещается самостоятельный поиск LLM;
- запрещается генерация отсутствующих фактов.

Ответ должен строиться исключительно на основе предоставленного контекста.

Если информации недостаточно, модель должна явно сообщить об этом.

---

# 15. Версионирование моделей

Изменение модели не должно требовать повторной загрузки документов.

При смене модели может быть повторно выполнен любой этап Pipeline:

- OCR;
- Structured Extraction;
- Summary;
- Embeddings.

Это является одной из причин хранения исходного Artifact и промежуточной сущности Extraction.

---

# 16. Тестирование

LLM-интеграция должна поддерживать автоматическое тестирование.

Рекомендуется иметь:

- эталонные документы;
- эталонные вопросы;
- ожидаемые структуры Extraction;
- ожидаемые Execution Plan;
- ожидаемые ответы Planner.

Это позволит оценивать влияние изменения моделей и Prompt.

---

# 17. Архитектурные решения

Medical Service проектируется независимо от конкретной LLM.

Все взаимодействие с моделями происходит через общую библиотеку.

Это обеспечивает:

- заменяемость моделей;
- поддержку нескольких провайдеров;
- единый интерфейс;
- минимальную связанность бизнес-логики и инфраструктуры.

---

# 18. Будущие расширения

Архитектура должна позволять без изменений бизнес-логики добавлять новые возможности общей LLM-библиотеки.

Возможные направления развития:

- автоматический выбор модели на основе сложности задачи;
- локальные модели для офлайн-режима;
- кэширование ответов моделей;
- пакетная обработка документов;
- автоматическая оценка качества ответов;
- A/B-тестирование моделей;
- поддержка мультимодальных запросов (текст, изображения, аудио);
- специализированные медицинские модели;
- централизованное управление Prompt для всех сервисов Miranda.

Все эти возможности должны появляться на уровне общей библиотеки и быть прозрачными для Medical Service.
